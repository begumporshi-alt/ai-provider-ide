### Durable gotchas found this pass

- **Reinstalling invalidates the keychain ACL.** Replacing the binary makes macOS ask again before the app may
  read `ai-provider-router`/`masterkey`. Until approved, **every** request (even unauthenticated) answers
  `503 master key unavailable … approve the keychain prompt`, `Retry-After: 5`. `pgrep SecurityAgent` is the
  tell. Approve it and it recovers at once — 455 models on the next request. Do NOT confuse it with the
  post-relaunch stale-heartbeat 503, which clears on its own. Same status, different message.
- **`memory_enabled` is in-memory only and off by default after a restart** (`gateway.rs:842`). So after a
  reinstall `aip-memory: write` reports `reason=disabled`, not `write_only` — `Disabled` outranks `WriteOnly`.
  That is correct precedence, not a regression; the live `write_only` observation from pass 1 was on a build
  where the switch had been turned on. Re-checking needs the Memory screen's master switch, not HTTP.
- **The probe harness returns lowercase header names.** `dict(r.getheaders())` keeps the server's casing, and
  axum sends lowercase, so `h.get("Retry-After")` is always `None` while `h.get("retry-after")` works. That
  nearly produced a false "the header is missing" conclusion. Dump all headers before claiming absence.
- `tauri build` embeds the frontend in the binary, but string-searching it can miss: the reliable marker is
  the **asset filename hash** referenced once inside the binary (e.g. `store-CBy7P-dH.js`) — if it matches the
  freshly built `dist/assets/`, the bundle is current.

## F. The §3.5 concurrency bound was never enforced (found while closing the last open item)

`ARCHITECTURE.md` §3.5 says "max concurrent routed requests (default 8) with a bounded queue (default 32)".
The gateway had **one** semaphore — `const MAX_TOTAL: usize = 8 + 32` — and `try_slot` dispatched as soon as
it admitted a permit. So there was no queue and no cap of 8: **up to 40 requests could be routed at once**.
Nothing asserted either number. It also explains the first pass's "upstream rate-limits first": 40
simultaneous calls to one provider draw a 429 long before a 40-deep gateway gate.

**Fix:** two tiers. `permits` (40) admits; a new `dispatch` semaphore (`MAX_CONCURRENT` = 8) is awaited before
the request reaches the worker — that wait *is* the queue. `Semaphore::acquire_owned` is cancel-safe and hyper
drops the future on client disconnect, so a queued request never holds a slot for a caller that has gone.
`Slot` now holds both permits so a routed request keeps its slot until it finishes.

Two tests, both falsified: 20 concurrent with a slow worker -> the worker must be handed exactly 8 (reverting
the cap fails with "the worker was handed 20"); holding 8+32 permits -> the next request is 429 + Retry-After.
Gate ALL GREEN, rebuilt, installed, pass-2 live checks re-verified.

**Live proof of the ceiling is not reachable against `agnes`.** 20 concurrent: 4 × 200, 16 ×
`429 all attempts failed … [agnes/key-01:RATE_LIMITED]` — the provider's rate limit, then its key cooldown.
The upstream caps before the gateway does. Needs a slow local upstream, never a real single-key provider.

## FIXED — Anthropic ingress now maps the tool protocol instead of flattening it (blocker 2)

## Refinement — the ZCode 429 vs WorkBuddy success comparison

Tushu re-ran the same prompt through the same router in WorkBuddy: **24 consecutive `ok` requests,

## FIXED — the router discarded the provider's Retry-After entirely (stage 1)

Found while measuring the ZCode 429s. The engine's own header comment claims §3.6 "backoff
honoring Retry-After". It was never implemented — the value was dropped at two points:

1. `ManifestHttpError` (`manifest-interpreter.ts:152`) carried only `status`, `body`, `kind`.
   **Response headers were never captured**, so the provider's `Retry-After` was unreachable.
2. `AttemptOutcome.retryAfterMs` existed in the interface but was **never assigned**
   (`execution-engine.ts:122` built the outcome without it), so `health.recordResult(..., undefined)`
   hit `Math.max(undefined ?? 0, 1000)` — a flat **1 second** cooldown for every rate-limited key,
   regardless of what the provider asked for.

Net effect: keys came back after 1s and the gateway answered `Retry-After: 1`
(`ensure_retry_after` fills it in only when absent), so a client retried straight back into a
window the provider had told it to wait out. That is the seven-429s-in-thirteen-seconds pattern.

**Fix (TS only, 3 files):**
- `manifest-interpreter.ts`: added `headerValue` (case-insensitive — `HttpPort` returns a plain
  `Record`, not a `Headers`), `parseRetryAfter` (RFC 9110: seconds *or* HTTP-date; unreadable →
  undefined so the caller keeps its floor), and `retryAfterFrom(headers)`.
- `ManifestHttpError` gained a 4th ctor arg `retryAfterMs?`; both `res.status >= 400` throw sites
  now pass `retryAfterFrom(res.headers)`.
- `execution-engine.ts:122` now propagates `e.retryAfterMs` into the outcome.

**Tests:** new `packages/router-core/test/retry-after.test.ts` — 3 tests driving a real
`ManifestInterpreter` over a fake `HttpPort` that 429s with a header: 60-second delay, HTTP-date
form, and an absent header (regression guard for the 1s floor). Built the HttpPort fake on the
pattern in `concurrency.test.ts` (`headers` is `Record<string,string>`, not `Headers`).

**Falsification:** 2 failed / 1 passed before the fix. After: 3 passed. Then reverted just the
propagation line to `retryAfterMs: undefined` and watched 2 fail again — restored.

**Verification:** `pnpm --filter @aiprovider/router-core test` → **237 passed, 20 files**. Root

### The min-vs-max question, resolved — and the fold was wrong

Stage 2 shipped `maxRetryAfterMs()` (the *longest* wait any provider named) and left the inverse as an
open product question. Asked Tushu; he chose **min**. The evidence made it a one-way door rather than a
taste call:

**`route-planner.ts:156` filters on health** — `keys.filter((k) => health.isKeyUsable(k, now))`. A cooled
key is not deprioritised, it is **excluded from the plan**, and the plan is rebuilt per request. So the
router serves the retry when the *first* cooled key frees up. Reporting the longest made the client wait
for a key the planner would never have chosen. The stage-2 example inverted: keys cooling in 58 s / 42 s /
71 s returned `71`, forcing a 29-second idle that bought nothing.

`AllAttemptsFailedError.minRetryAfterMs()` now takes the minimum, floored at `COOLDOWN_FLOOR_MS`, over
**every** named wait — not only `RATE_LIMITED` ones. That last part is the one judgement call: a 503
carrying `Retry-After: 30` does not cool its key (`recordResult` only cools on `RATE_LIMITED`), so
filtering it out would tell the client to retry in a second, straight back into an overloaded provider.
I wrote the class filter first, then removed it — see "the first probe lied" below for why the
distinction matters. A test now pins the choice so a later tidy-up fails loudly.

`COOLDOWN_FLOOR_MS` is exported from `health-tracker.ts` and used by both the tracker and the fold. Two
hardcoded `1000`s were free to drift, and the whole point is that the wait the client is *told* matches
the wait the tracker *enforces*.

## The `glib` claim, verified with a positive control

The plan asserted "`glib` is Tauri's Linux/GTK tree and this ships macOS only." Asserted from reasoning,
not tested. Tested:

```
cargo tree --target aarch64-apple-darwin -i glib    → nothing to print
cargo tree --target x86_64-apple-darwin  -i glib    → nothing to print
cargo tree --target x86_64-unknown-linux-gnu -i glib
  glib v0.18.5 → gtk v0.18.2 → … → tauri v2.11.5 → ai-provider-router v1.0.0
```

**The Linux run is the load-bearing half.** A negative from `cargo tree -i` is indistinguishable from a typo
or from the crate simply not existing under that name — "nothing to print" is also what you get for a package
that was never a dependency. Running the same query on a target where the crate *is* present proves the query
works, so the negatives then mean absent. **A negative result needs a positive control before it means
anything** — same shape as "prove a spec fails before trusting it passes."

Why RustSec reports it anyway: a lockfile is target-independent, so `cargo audit` sees crates that no shipped
binary compiles.

run prints a wall of `Downloaded` lines; the tree follows after.

Before picking the next task I measured the three candidates instead of arguing from the docs.

### The clippy backlog is ~90% cosmetic, but hides two real defects

`cargo clippy --all-targets --message-format=json`, grouped by lint: **64 warnings, 18 lint kinds.**
The bulk is mechanical — `uninlined_format_args` 13, `empty_line_after_doc_comments` 12,

is true but far more pessimistic than the evidence: the remedy is mostly a command.

Only **two** warnings carry real signal, both `clippy::if_same_then_else` — a branch whose two arms are
identical:

1. **`crash_report.rs:155`** — `if backtrace.is_empty() { format!("{msg} — {location}") } else { format!("{msg} — {location}") }`.
   Both arms identical. Dead branch, in crash reporting, where a no-op is invisible.
2. **`gateway_gemini.rs:355`** — `let finish_reason = if has_tool_calls { "STOP" } else { "STOP" };`.

### The Gemini one is the interesting find, and the obvious fix is wrong

Every other dialect *does* distinguish the tool-call case:

| dialect | tool calls present | otherwise |
|---|---|---|
| Anthropic (`gateway_anthropic.rs:700`) | `"tool_use"` | `"end_turn"` |
| OpenAI (`gateway_handlers.rs:231`) | `"tool_calls"` | `"stop"` |
| **Gemini (`gateway_gemini.rs:355`)** | `"STOP"` | `"STOP"` |

So the guard exists because the author intended a distinction — and then wrote the same literal twice.
**But the correct fix is to delete the `if`, not to invent a second literal.** Gemini's `FinishReason`
enum has no tool-call member; function calls are signalled by `functionCall` parts and `finishReason`
stays `STOP`. The defect is a *dead branch that implies a distinction the protocol does not make*.

That distinction matters because **the test suite cannot tell the two fixes apart.** The only Gemini
`finishReason` assertion is `gateway_tests.rs:641`, in `gemini_generate_content` — a plain `"hi"` prompt
with no tools. **No Gemini test reaches the tool-call path at all**, so a `--fix`-style repair that
picked a plausible-looking second literal would pass the suite and be wrong. This is the argument for
doing the real-signal lints by hand, and letting `--fix` take only the mechanical ones.

### `manual_div_ceil` — measured, and it is not a bug

`gateway.rs:1585`, `cooldown_secs`: `((ms + 999) / 1000).max(1)`. Overflow needs `ms > u64::MAX - 999`;

(`gateway_handlers.rs:231`) — so the guard existed because the author intended a distinction, then wrote
the same literal twice.

**But the correct fix is to delete the branch, not to invent a second literal.** Gemini's `FinishReason`
enum has no tool-call member; function calls are signalled by `functionCall` parts and `finishReason`
stays `STOP`. The defect was a dead branch implying a distinction the protocol does not make.

**And the suite could not tell the two fixes apart.** The only Gemini `finishReason` assertion
(`gateway_tests.rs:641`) uses a plain `"hi"` prompt — **no Gemini test reached the tool-call path at all**.
So a `--fix`-style repair that picked a plausible literal would have passed everything and been wrong.

Order, therefore, was: write the test, falsify it, then fix.
- Added `gemini_tool_turn_still_reports_stop`. It asserts the parts are `functionCall` (proving the path
  was actually reached, so the test is not vacuous) *and* that `finishReason` is still `STOP`.
- Falsified by setting the tempting `"FUNCTION_CALL"` literal → failed with `left: "FUNCTION_CALL",
  right: "STOP"`, i.e. exactly the failure mode it guards.
- Then deleted the branch. Test passes; `if_same_then_else` is now clear across the crate.

the formatter; it is the formatter being told the style the code already uses. That reframes the decision:
adopting rustfmt with this config **preserves** the existing look rather than imposing a new one.

**Instrument bug, third of the day.** My first line count came back **0 removed / 0 added** against 638 hunks —
internally impossible. Cause: `cargo fmt --check` writes **ANSI escapes even when redirected**, so every diff
line begins `\e[32m+` and `^[-+]` never matches. `-- --color=never` fixed it. The bash `grep` shim returned the
same 0 for the same reason, so two instruments agreed on a false reading.

the whole `docs/dev-book/` (10 chapters, README, `book.html`), three new `scripts/*.mjs`, two vitest configs,
