## Increment 25j — the builtin profiles, and D41's second facet

Took the recommendation: **close D41** — the missing `PROVIDER_PROFILES[slug]` branch in `core::activation`.
Chosen over Phase 6 because it is reachable by an ordinary UI action (`Providers.tsx:298` creates a builtin
provider), while Phase 6 is UI-heavy and would be built against a release pipeline still blocked on the Apple
Developer Program.

**The reference's loop, `store.ts:367-381.** Runs **over providers**; for each one tries
`PROVIDER_PROFILES[p.slug]` **first**, registering `withBaseUrl(profile(), p.baseUrl)` and `continue`ing, only
then falling back to that provider's active manifest row (from `manifests_active`). The old Rust iterated
*manifest rows*.

**Two facets — D41 recorded only the first.**

1. **A builtin provider with no manifest row went unregistered.** Reachable: `addProvider` writes the provider
   row (`store.ts:495`) **before** the manifest row (`:497-502`), and its `catch` rolls back in-memory state
   only (`adapters.unregister` + `refreshFromHost`). Nothing deletes the provider row — so a failure between the
   two writes leaves a row-less provider permanently.
2. **A builtin provider *with* a row was served the stale one.** The row is written once, at creation, with
   `version: 1`; nothing re-seeds it on upgrade (no migration, no boot path rewrites a `builtin-template` row).
   The reference ignores that row for a builtin slug and serves the *current* profile. **Facet 2 needs no
   failure — only a second release.** This is the facet the register did not state, and it is the broader one.

**`core/builtin_templates.rs` (new, 9 tests).** `openai_compat(base_url, extras)`, `anthropic_compat(base_url)`,
`provider_profile(slug, base_url)`, `PROFILE_SLUGS`. The base URL is a **parameter** — `withBaseUrl` composed
rather than applied. Consequences: (a) the profile path dials `providers.base_url`, the column `recompute_allow`
derives the allowlist from, so **a builtin provider cannot trip D46**; (b) the pinned default URLs are *not*
duplicated in Rust — nothing consumes them, and a copy would be a second answer to "where does OpenRouter live".

**Details that cost care.**
- **The slug is the key, not `type`.** `store.ts:368` is `PROVIDER_PROFILES[p.slug]`. Keying on `type` would have
  diverged in the other direction, invisibly, for the same reason this one was.
- **An omitted key is not a null one.** `opencode` passes `{ imageEndpoint: false }`, so
  `headers: extra?.textHeaders` is `undefined` and `JSON.stringify` drops it. Emitting `"headers": null` would
  produce a manifest the reference never generates. Same for `modalityRules`.
- `BUILTIN_TEMPLATES` was deliberately **not** ported — its two callers (`adapter-generator.ts`,
  `fingerprinter.ts`) are both TypeScript, so the id enum would have no Rust selector.
- `PROFILE_SLUGS` is exported **so a test can walk every profile**; a test using only `openrouter` would pass
  with the `b.ai` arm dropped.

**Activation now iterates providers.** `Skipped.version` → `Option<i64>` (`None` = no row involved, not a `0`
sentinel). Both log consumers updated (`aiproviderd.rs`, `tauri/gateway_cmds.rs`).

**One additive divergence:** a provider with neither a profile nor a row is **reported**, naming the slug and the
write order. The reference is silent there — and that silence is what hid D41; the symptom arrives later from
`adapter_runtime` as `no active manifest for provider …`.

**Four probes, one at a time.**
- Remove the profile branch → reddens the **5** profile tests **alone**.
- `provider_profile` ignores its `base_url` argument → reddens **8** across both modules.
- Remove the no-row report → reddens its own test **alone**.
- Invert precedence (row first) → reddens the 2 tests that are about precedence. **2 further failures there were
  artefacts of the probe's own simplified row path, not of precedence** — recorded as such rather than claimed.

## Increment 25k — one authority for "which manifest serves this provider" (D49)

**The stated rationale was false.** The recommendation was "seed builtin providers at boot, or the port will drift
again on the next template change". That drift was already closed: 25j made activation read the *profile*, not the
row, so serving no longer diverged. What *did* diverge was the second consumer: `workbuddy::tool_support` still read
the row, so a builtin provider was **served** by its current profile and **reported on** from its snapshot row — two
answers to one question, produced by one increment (**D49**).

**`activation::serving_manifest` is the one function.** Takes `(slug, base_url, Option<(body_json, version)>)` and
returns `Result<Option<Serving>, UnreadableRow>`. Both `register_provider` and `tool_support` read it. `Serving`
carries `body: Value` and `version: Option<i64>` — `None` for a profile (no row), `Some` for a row so a failure can
name which one. `UnreadableRow` carries `version` and `detail` so the parse error is reported with its version.

**`tool_support` now outer-joins `manifests`.** The join is load-bearing: a builtin provider may have no row and still
be served by its profile. An inner join would answer "unknown" → false for a provider that is serving and forwarding
tools right now.

**`manifest_forwards_tools` now takes `&Value`.** Re-serializing after `serving_manifest` returns a `Value` would be a
second parse for no reason.

**Four tests, four claims.** `a_builtin_provider_reports_tool_support_from_its_profile_not_its_row` (row has no
`tools`, so `true` can only come from the profile). `a_builtin_provider_with_no_manifest_row_still_reports_tool_support`
(outer join is load-bearing). `a_provider_without_a_profile_still_answers_from_its_row_in_both_directions` (fix is
not "builtins are always true"). `a_row_that_is_not_json_is_unknown_rather_than_either_answer` (corrupt row → None).

**Three probes, one at a time.** Remove profile branch from `serving_manifest` → reddens the 2 new builtin tests + 5

**Six routes:** `GET/POST /admin/settings`, `GET/POST /admin/keys`, `DELETE /admin/keys/{id}`,

**Three deliberate departures from a literal port of the commands.**
1. **The settings write merges, server-side.** The IPC path merged in TypeScript

2. **`POST /admin/keys` returns the secret once.** The IPC command copied it to the clipboard and

## Increment 26g — the memory and context routes (17 + 3)

**Why memory is service-owned, not app-owned.** `core/memory.rs` and `core/context_scope.rs`
are Rust core modules the headless binary already links, and the gateway injects a memory block
at system position 0 on every request (§5.5, `AIP-Memory`). So the headless service could *use*
memory before this increment; what it could not do was let anyone *manage* it.

**17 memory routes** (list/capture/batch/recall/forget/update/pin/scope/session/clear/stats/
supersede/unsupersede/conflicts/prune/principals) and **3 context-graph routes**
(record/graph/clear). The History screen's `history_sessions` / `history_timeline` are
**deliberately not ported** — 26e measured them as app-owned UI state.

**Two spellings on one surface, and it is not a mistake.** The `persist::*` rows are camelCase
(symmetric read+write registry rows). `memory::MemoryInput` is **snake_case with
`deny_unknown_fields`**, because serde's default silently turns a misspelled key into `None` —
which is exactly how `memory_capture_batch` dropped `session_id` for months and disabled the
per-session ring cap in `prune`. The routes reuse the struct rather than reshaping it, so the
wire spelling cannot drift. Two tests pin both halves: the snake_case `session_id` survives, and
the camelCase `sessionId` is **refused**.

**The finding that cost a redesign.** A typed `Query<{ layer: String }>` extractor **runs before
the handler body**, so a request with no `layer` got a 400 from `authorize` never having run — a
route answering a caller it had not authenticated. `GET /admin/memory/session/{id}` now reads the
query as a raw map and parses **after** auth, and `GET /admin/memory` was converted too so the
rule holds across the surface rather than holding approximately. (Body `Json` extractors have the
same property; the pre-existing routes tolerate it as 422, which the auth test allows.)

**Capture is not injection.** A row is born `Unscoped` — capture-only, never injected — and
`assign_scope` is the only way in. Pinned by
`admin_memory_a_captured_row_is_not_injectable_until_scoped` (stats go 0 → 1 across the bind).
Nothing auto-binds.

## Increment 26h — the gateway tool toggles (and the authority they had two of)

**"Are gateway tools on" had two authorities, and the route reports both rather than picking
one.** (1) The in-memory `AtomicBool` on `GatewayCore::settings`, read per request by
`gateway_handlers.rs` in the in-app gateway. (2) `gatewayToolsEnabled` in the **`router`**
settings row — *not* the `gateway` row the settings routes own — read per request by the headless
host via `RouterSettings::from_store`.

**The consequence, and the design it forced.** A route writing only the in-memory flag would be a
toggle that appears to work and does nothing on the service; one writing only the row would leave
the running in-app gateway unchanged. So `POST /admin/tools` writes **both**, and `GET` returns
both (`enabled` + `persistedEnabled`) so a caller can see them disagree instead of being handed a
single number true of only one process. `mutationEnabled` is in-memory **only** — no persisted
counterpart exists — and the module header says so.

**The row write is a merge**, for the same reason `POST /admin/settings` is: `router` also carries
`failoverEnabled`, `systemAi` and `perProviderConcurrency`, and `settings` is a whole-row UPSERT.
`admin_tools_set_writes_both_the_flag_and_the_row` seeds `failoverEnabled` and asserts it survives.

**The bug the tests caught.** `ToolsPatch` was written without `rename_all`, so the response
(`ToolsStatus`, camelCase) emitted `mutationEnabled` while the request silently ignored it — a
patch that reports success and changes nothing. Same failure class as the memory `session_id`
one. Fixed and pinned by `admin_tools_patch_leaves_an_omitted_toggle_alone`.

**Measured:** lib 1259 → **1263** (+4), headless 1195 → **1199** (+4), binary 5. fmt, clippy

## D51 — the TypeScript migration is blocked, and it was stopped rather than built around

**The pure-HTTP migration's enabling premise is false.** `gateway_admin.rs`'s module header says
"the UI holds the master key in memory for the session". **TypeScript has no key and never can.**
Measured: a Grep for `master` over `apps/desktop/src` returns no variable holding one; `store.ts`
handles `secretRef` (a reference) not secrets; the UI's three master-key operations
(`gateway_key_copy` / `_generate` / `_revoke`) are `invoke` calls that never return it, and
`Gateway.tsx:238` says "never shown here". A Grep for `fetch(` over the tree returns **one** call,
in `Assistant.tsx` — there is no HTTP client, because there has never been a credential to send.

**Consequence:** every `/admin/*` route from 26c–26h answers 401 to the only client the decision
was written for. The routes are sound; their stated enabler does not exist.

**Why no gate could see it:** the tests supply `Bearer sk-aip-test` themselves. A test that hands
itself a credential cannot discover that its caller has none.

**Stopped, not worked around.** The migration was halted at the client rather than producing 43
call sites that all 401. Three options recorded in the register: (1) host-mediated short-lived
session credential — preserves invariant 2's purpose (TS never holds a *provider* credential)
while giving it something to send; (2) loopback auth exemption — simple and wrong, any local
process could admin the gateway; (3) keep admin on IPC — concedes the decision.

## Increment 26i — the TypeScript migration (provider/key group, memory, context, tools)

**The host-mediated session credential (D51 fix) landed first.** `core/ui_session.rs` mints a
reserved app key (`ak-ui`) on first call, stores it in the keychain, and returns it via the
`ui_session_key` command. The TypeScript client (`gateway-client.ts`) caches it in `let` — never
persisted — and supplies it as a `Bearer` token on every `fetchAdmin` call. Five tests pin idempotency,
row repair, keychain failure reporting, reserved-id recognition, and revoked-row replacement.

**Migrated `store.ts` functions to `fetchAdmin`.** The provider/key group first (the proof case),
then memory, context-graph, ledger read, and tools — every function whose HTTP route exists in
26c–26h. Remaining `invoke` calls (~12) are for app-owned UI state (skills, agent runs, service
management, router settings, ledger append) or commands with no HTTP route yet (manifest history,
model context publish/count, workbuddy sync).

**Two wire-spelling hazards caught and preserved.**
1. `MemoryInput` is snake_case with `deny_unknown_fields` — the HTTP route deserializes it directly,
   so `session_id` (not `sessionId`) is required. `captureMemory` was corrected; `captureMemories`

2. `captureMemories` returns `{ captured: n }` over HTTP, not `n` directly — the Tauri command

**Type check clean.** `pnpm typecheck` (tsc --noEmit --noUnusedLocals --noUnusedParameters) passes.
Web-test typecheck has one pre-existing error in `service-status.spec.ts` (`gatewayStatus` missing
from `Host` type), unrelated to this increment.

**D51 → Closed.** The drift register entry is updated: the host-mediated session credential is the
chosen resolution, and the TypeScript migration is underway.

## Increment 26j — the transport seam, and the three wires D51 left unconnected

## Increment 26k — the shim serves `/admin/*`, and the browser suite runs as a gate again

**The increment.** `web-test/shim.ts` now intercepts `fetch` for loopback URLs under `/admin/*` and
dispatches to the **same in-memory store** the `invoke` cases use. All **29 path templates** are served
(43 method+path pairs), not just the ones with a caller today. Each route is a thin adapter — parse
path/query/body, call the `dispatch` case the `invoke` path already calls, reshape into what
`core/gateway_admin.rs` answers. One store, two entry points: the shape the Rust half has.

**Why it was needed.** 26i moved `store.ts` from `invoke` to `fetchAdmin`, which dials
`127.0.0.1:<port>/admin/*`. The harness stood in for the **IPC** host only, so every migrated call left
the page for a dead port. `tsc` cannot see a transport, and `web-test:types` was itself red until 26j,
so the suite had not run as a gate since 26b.

**The live bug it found.** `persistAliases` sent `{ rows }` (the IPC command's shape) while
`aliases_replace_h` takes `Json<Vec<AliasRow>>` — a bare array, which `admin_aliases_replace_*` posts
and `POST /admin/memory/batch` already uses. Nothing had walked the pair: 26f's test posts the array,
26j's fake accepts anything. Because `persistAliases` is in the **boot** path, the app came up with
"App data could not be opened" and no screen rendered. **Fixed on the client** — the HTTP route is the
surviving contract, so the IPC spelling is the one that goes.

**Two more transport consequences, both fixed at the layer that owns them.**
- **`doPin` lagged a round-trip.** It awaited the write then re-read, so the checkbox only moved after
  the host answered — invisible at one IPC hop, visible over HTTP, and a control that lags the click
  reads as a write that did not land. `Memory.tsx` updates optimistically; the re-read still
  reconciles and a failure reads the truth back.
- **`memory-recall.spec.ts` waited on the wrong element.** `div.whitespace-pre-wrap` also matches the
  user's own echoed message, so the wait returned before the request existed and the egress log read
  `""`. It now waits on the request it asserts on. Assertions unchanged; only the wait was wrong.

**Deliberate design points.** Auth first, before anything is parsed (26g's rule, since an axum
extractor runs before the handler body). `ui_session_key` mints on first ask, the way
`ui_session::ensure` does, so the harness models a healthy host; `__webTest.uiSessionKey` arranges the
401. `failNext` accepts `METHOD path` alongside a command name so a failed read stays arrangeable.
`__webTest.adminCalls()` records what the UI sent. **CORS cannot be modelled** — the interceptor
answers before the network stack, so the browser never runs the preflight `cors_headers` exists to
satisfy. Said in the module header rather than implied.

**Measured.** Browser suite **106 passed / 0 failed (1.5 m)** — first green since 26b. Baseline: red
from test 18 onward, each failure costing the full 120 s timeout (a full red run would have taken
~3 h, which is why the baseline was taken per-spec). `web-test:types` clean, `pnpm typecheck` clean,
vitest **181/181**, `key-leak-grep` OK, `check-doc-links` 52 files / 127 links, book **782.0 KB** /
207 ids. **No Rust changed.**

**Falsified, one probe.** With the interception removed (`globalThis.fetch = nativeFetch`),
`smoke.spec.ts` goes **13/14** — the Memory screen renders "No memories yet" again. Probe reverted;
`shim.ts` back at its committed size (111,093 B).
