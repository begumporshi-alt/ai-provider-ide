### Per-app budgets: the documented gap understates the work

`09-status.md` said "Per-app keys exist; per-app limits do not". Measured against the live DB, that is only
half the story — **there is no per-app attribution either**, so a budget would have nothing to sum.

The trap is a name collision. Two different things are called `key_id`:

| | What it is | Join |
|---|---|---|
| `ledger.key_id` | the **provider credential** (`api_keys.id`), e.g. `2f4b37eb-…` | **713** of 792 gateway rows |
| `gateway_keys.id` | the **gateway app key** the client presented, e.g. `ak-fc85350a2fb1dc67` | **0** rows |

The ledger's 16 columns contain no app-key column at all. The first join I tried — `ledger.key_id IN (SELECT id
FROM gateway_keys)` — returned **0**, which reads as "no attribution" but was really "wrong table". The second
join against `api_keys` returned 713/792 and settled it.

So the work is three parts, and the first is a prerequisite nobody documented: (1) migration 0016 adds
`app_key_id` to the ledger **and the TS router must start passing it** — a column alone proves nothing, which
is this project's own rule; (2) a cap column on `gateway_keys`; (3) enforcement, which changes
`SpendProvider`'s signature — it is `Arc<dyn Fn() -> (i64, i64)>`, **zero arguments**, so the gate cannot tell
callers apart today — touching every construction site and test, then `SpendStatus`, the UI and the shim.

### `thinking` blocks: not "quality-only, last" — unmeasurable, like `cache_control`

The plan files it as backlog item 5, "quality-only, last", with no spec. Measured:

- **Nothing exists.** Zero handling anywhere in the codebase.
- **The drop is deliberate and documented** — `gateway_anthropic.rs:204-206`: *"Anything else (thinking,
  images) has no OpenAI equivalent here and is dropped rather than guessed at."* A turn of only-unrecognised
  blocks still emits an empty message, so the assistant turn it answers is not left dangling.
- **Four things are dropped, not one.** The `thinking: {type, budget_tokens}` **request parameter** is
  discarded by `to_chat_body`, which builds a fixed field set (`model`, `messages`, `stream`, `max_tokens`,
  plus `tools`/`tool_choice`/`response_format`) with no passthrough. `thinking` blocks in history are dropped.
  Non-stream responses never emit one. And the stream **does** multiplex blocks — text at index 0, `tool_use`
  at `1 + idx` (`gateway_anthropic.rs:446`) — but only those two kinds, and the ordering constraint is already
  load-bearing: index 0 is closed *before* index 1 opens, because Anthropic orders blocks strictly and an open
  block makes the client's parser wait for a stop that never comes (`:429-432`). A `thinking` block must
  *precede* text, so it would take index 0 and shift every tool index.
  *(Corrected 2026-09-23: this note first claimed "the stream hardcodes a single `content_block_start` … there
  is no block multiplexing". The code contradicts that — the index scheme is right there at `:446`.)*
- **The bridge protocol cannot express it.** `BridgeMsg` is `Delta(String)` · `ToolCalls` · `Result` ·
  `Usage{prompt_tokens, completion_tokens}` · `Done` · `Error`. No reasoning variant. So this is a bridge
  protocol change across Rust *and* TS, not an adapter-local edit.
- **There is nothing to test against.** `SELECT COUNT(*) FROM models_cache WHERE raw_json LIKE '%reasoning%'`
  → **0**, across all 455 cached models. No provider in this install advertises reasoning support.

Same shape as `cache_control`, which the plan parked as "BLOCKED on measurement": **measure → decide →
rework**, and the measurement is not available. Doing it blind means building a protocol change with no
provider that can exercise it.

## CI went red on the pushed commit: toolchain drift, not the code

`7dcbf0f` pushed, and the clippy step failed. **Not formatting** — the new `cargo fmt --check` gate was fine.

Root cause: `dtolnay/rust-toolchain@stable` on the runner is **1.98.1**; this machine was on **1.88.0**. Ten
minor releases, four new lints, no code change in between. Reproduced with `rustup update stable`.

Fixed all four:

- `model_context.rs` — `ModelContextRow` was dead. No command, no TS bridge, no test constructs it; the UI
  shows a *count* (`Memory.tsx:224` → `router_model_context_count`), never rows. Its own doc comment claimed a
  purpose it never had. Removed, plus the `Serialize` import it was the only user of.
- `crash_report.rs` — `is_leap` hand-rolled `% n == 0` → `is_multiple_of`.
- `context_scope.rs` — `sort_by` on one bool → `sort_by_key` + `Reverse`. Both are stable sorts, so the
  documented "everything else keeps `recall_scoped`'s order" property is unchanged.
- `gateway.rs` — `try_slot` returns `Result<Slot, Response>`, over the 128-byte threshold. **Kept it, behind a
  local `#[allow]` with the reason written down.** Boxing would have been the wrong fix: the value is built
  once and consumed once, and the five call sites are **not uniform** — three return it to hyper, two
  (`gateway_gemini.rs:209`, `gateway_anthropic.rs:351`) read only `status()` and rebuild the envelope, one
  maps it. No caller uses `?`. Boxing would add a heap allocation to every refusal, including the at-capacity
  429, which is the one refusal that is hot *by construction*.

Verified: the same clippy command reported 6 warnings before and none after; `cargo fmt --check` exits 0 —
checked **without a pipe**, since `${PIPESTATUS[0]}` is empty in zsh and a piped exit code is `head`'s, which
proves nothing; gate ALL GREEN 14/14.

Also corrected a stale claim in `ci.yml`: it named "the two remaining judgement calls … (a test helper with 8
positional args, three counts from three statements)". The `type_complexity` allow no longer exists — both
sites now return a named type and cite the lint in a comment (`store.rs:323`, `gateway_tests.rs:10`).

**Open decision:** the clippy step runs against whatever `stable` is, so a Rust release can turn CI red with no
code change. Pinning (`rust-toolchain.toml` + the action's `toolchain:` input) would stop that, at the cost of
not adopting new lints automatically. The repo pins nothing today — no `engines`, no `.nvmrc`, no
`rust-version`.

## `$HOME` contamination from the ESLint install — reverted in part

`npm install` run in a directory with no `package.json` walks *up* to the nearest one. The managed node
workspace has none, so it installed into `~/node_modules` and wrote to `~/package.json` and
`~/package-lock.json`. `~/node_modules` pre-existed with 27 entries (an axios/ws/`@openzeppelin` closure); the
install added ~69 and put two lines into `~/package.json`.

Reverted with npm's own bookkeeping: `npm uninstall eslint typescript-eslint` restored `~/package.json` to its
three original dependencies and shrank `.package-lock.json` from 120 entries to **25** — exactly the predicted
closure, which is what makes the revert verifiable rather than hopeful.

**What npm did not clean up, and why it matters.** The tree still holds ~67 full package directories renamed
to `.name-hash` staging names, plus 8 populated scoped dirs and 6 `.bin` staging links. npm renames victims
*before* deleting them, so the bulk-delete guard refusing the delete leaves the packages on disk under the
staging names while `npm ls` reports success and `npm uninstall` says "up to date". That is a new instance of
the guard trap already in `MEMORY.md`, now recorded there. **Cleaned up on approval, 2026-09-23.** Approved as "move them to Trash". 78 items moved via `/usr/bin/trash`
in batches of 10 with a stop-on-first-failure loop — 63 staging dirs, 8 scoped dirs, 6 `.bin` links, and the
`$HOME` scratch config. The target list was built and **inspected before anything moved**: a grep confirmed no
`@openzeppelin`/`axios`/`ws`/`.vite`/`.package-lock.json` entry was in it, and that exactly one path reached
outside `~/node_modules`.

End state verified: `~/node_modules` back to **29 entries** (4 dotfiles + the 25-package axios/ws closure),
`.bin` empty, `~/package.json` at its three original dependencies, `.package-lock.json` at 25 entries, and the
survivors intact (`@openzeppelin/contracts` 377 files, `axios` 86, `ws` 19).

**A trap worth remembering: `-e` follows symlinks, so it reports npm's `.bin` staging links as absent.** The
first inventory said "0 `.bin` links" when there were 6 — they are *broken* symlinks by construction, so the
test has to be `-L`. The count went from 72 to the correct 78 only after that fix.

**The Trash could not be listed to take a receipt** — `~/.Trash` is TCC-protected (`Operation not permitted`)
and Finder automation is blocked too (`privilege violation, -10004`). So the evidence for "moved, not deleted"
comes from the binary rather than from the Trash: `/usr/bin/trash` is `com.apple.trash` and references
`trashItemAtURL:resultingItemURL:error:` — the `NSFileManager` call that *moves* to Trash. A deleting tool
would reference `removeItemAtURL:error:` instead. Recorded because "gone from where it was" is not the same
evidence as "recoverable", and only the second one was promised.

Also removed: the project-root scratch config `eslint.measure.cjs`.

## Per-app attribution — part 1 of 3, landed

Migration 0016, the writer, the TypeScript producer chain, and the bridge. 14 files, +509/−80.

**The bridge was the piece that made "wired" a claim rather than a hope.** `BridgeRequest` (`gateway.rs:302`)
carried `request_id`, `kind`, `body`, `headers` — and no app key. So the column, the `LedgerEntry` field and the
`store.ts` mapping were all correct and the value still could not physically arrive: the ledger is written on the
*webview* side, and the identity was only known on the Rust side. Adding a field to a struct on one side of a
process boundary is not wiring.

**`check_gateway_key` now returns the identity it was already computing** — `Result<Option<String>, GateRefusal>`
where `Ok(Some(id))` is the per-app key, `Ok(None)` is the master key and `Err` denies. The alternative was
calling the existing `app_key_for` at each dispatch site, which would have been six edits instead of nine but
would have made a *second* authority for "who is this" — and the project's own rule is that an identity needs
one authority, not two that must be kept in step. All nine call sites converted; the compiler found every one,
and found the one dispatch site I had missed (`models_h`).

**Four tests, each falsified before being trusted.** The valuable one asserts the key at the *bridge*, not on the
function's return value, because the return value is only half the wiring. Falsified twice: forcing
`app_key_id: None` at the dispatch made it fail `Some(None)` vs `Some(Some("ak-1"))`, and making the lookup
report the first active key instead of the matched one failed `ak-1` vs `ak-2`. The second probe is what proves
the test checks *which* key rather than merely *that* some key arrived.

**The gate failed on `cargo fmt`, and the failure was not from this session.** Both hunks were `query_map`
chains in `persist.rs` and `store.rs` — test code written in the previous session and never formatted. Worth
noting because it is the third time the lesson has landed: uncommitted work is not verified work, and only
running the gate says otherwise. `cargo fmt` then touched exactly those two files.
