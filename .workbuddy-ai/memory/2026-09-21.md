## Finding — the read path is dry

The Phase 2 read path is complete but can return **nothing**, because no row satisfies the
injectable predicate.

- Live DB (`~/Library/Application Support/dev.aiprovider.router/ai-provider-router.db`) is at
  `schema_version = 8`; migration `0009_memory_scope` has **not** run against it yet.
- 55 memories: 41 L0, 12 L1, 0 L2, 2 L3.
- `backfill_memory_scope` gives every pre-existing row `scope_project = NULL, scope_global = 0`.
  With a resolved project the predicate is `scope_global = 1 OR (scope_project = ? AND ...)`, which
  excludes NULL; with no project it is `scope_global = 1 AND pinned = 1`. **Both exclude legacy rows.**
- So after migration there are still **0 injectable rows**, and `recall_scoped` is only ever called
  with L1/L2/L3 — 14 of the 55 rows are even eligible by layer.

Consequence: the next phase has to *produce scoped data*, or nothing downstream is demonstrable.
Retroactively assigning a project to unscoped rows is exactly the contamination the reviewers
warned against, so the fix is a scoped write path, not a backfill.

## §5.6 — hard deadline on the memory path (landed)

`Deadline` in `apps/desktop/src-tauri/src/context_scope.rs`; `MEMORY_DEADLINE = 15ms` (midpoint of
the design's 10–20ms band). `inject_context` now delegates to `inject_context_deadline(core,
headers, source, body, budget)` — the extra parameter exists so a test can force an overrun with
`Duration::ZERO` instead of seeding enough memories to make recall genuinely slow.

### Three check sites, all between stages
The expensive steps are single SQLite calls that cannot be interrupted once started, so the deadline
bounds *how many a request may pay for*, not how long one may take:
1. `"recall"` — before `recall_scoped` (covers parse + principal + window lookups).
2. `"context"` — before `live_context` (covers recall + rank + trim + compose).
3. `"prepend"` — after `live_context`, before the body is mutated.

### The claim that matters
**A miss aborts the writes, not just the read.** Live context does five SQLite reads/writes on the
same connection; those writes are the thing contending for the lock. A deadline that dropped the
read and still let them through would protect nothing. The acceptance test asserts it from the
outside: an aborted request records no turn, so the *next* request with a real budget finds
`ctx=0`. Disable only checks 1+2 and that becomes `ctx=1` while `reason=deadline` still holds —
i.e. the two claims fail independently.

### Falsification (two separate probes)
- `check` forced to always pass → 2 failures (the `Deadline` unit test + the acceptance test at the
  `reason == Deadline` assert).
- checks 1+2 disabled only → 1 failure at `ctx=0` (`injected=1;items=0;tokens=12;ctx=1`).
Restored both; confirmed with the Grep tool that no `if false` / `if true` survived.

## §5.5 — prompt-cache stability (landed)

Two halves. `MEMORY_FREEZE_TTL = 10min` on `GatewayCore::memory_freeze` (keyed `(scope, session)`
via `context_scope::freeze_key`), 256-entry cap with oldest-out eviction, swept on insert.

### 1. Deterministic ordering — total, in two places
`m.id` is the last key of BOTH the SQL `ORDER BY` in `recall_inner` and `rerank`. Both are needed:
`rerank` can only reorder what it is shown, and `LIMIT` truncates the shortlist *before* that, so
which rows survive to be ranked at all was plan-dependent too.

**Falsification gotcha worth remembering:** the first attempt at the e2e test
(`atoms_that_tie_on_every_real_key_come_back_in_id_order`) passed even with the `rerank` tie-break
removed — the SQL fix alone was already producing id order, so the two fixes masked each other.
Fixed by adding `rerank_breaks_ties_on_id`, which drives `rerank` directly with a deliberately
shuffled `Vec<Memory>`; removing the tie-break there leaves the input order intact
(`["m-3","m-1","m-2"]` vs `["m-1","m-2","m-3"]`). **When two fixes target the same property, test
the inner one directly or you have proven nothing.**

`a_truncated_shortlist_is_the_same_rows_every_time` is honestly labelled: it does NOT fail when the
SQL `m.id` key is removed (this SQLite build returns tied rows stably), so it pins the property
rather than proving the key load-bearing. The key is defensive — unspecified guarantee + LIMIT.

### 2. The freeze
- **Only the memory block freezes; live context does not.** Context carries the latest turns. It is
  concatenated *after* memory, which is what makes the freeze worth anything — providers cache the
  longest matching prefix, so the stable bytes must come first. Asserted in the test.
- **An empty result is never frozen** — it would pin "nothing to recall" for the whole TTL and the
  first atom distilled in a new project would be invisible for 10 min.
- **A block that no longer fits the budget is re-composed, not served** (budgets shrink as prompts
  grow); re-composing costs one cache miss, over-injecting is a correctness bug.
- **Invalidation is TTL-only** (webview distils, host has no write hook) except the memory toggle,
  which clears. Documented trade: a newly scoped atom can wait up to 10 min.

**Test gotcha:** the E2E freeze test originally used the same body for every request, so §5.4
stripped the turn the client had just sent and `<context>` never appeared — the "memory is the
prefix" assertion panicked on `unwrap()`. Three different phrasings of the same question fixed it.

### Falsification (three separate probes)
- `rerank` tie-break neutralised → `rerank_breaks_ties_on_id` fails (isolated).
- SQL `m.id` removed → nothing fails (documented above; SQLite is stable here).
- `frozen_memory` short-circuited to `None` → all 3 freeze tests fail, E2E at the byte-identical
  assertion.

## Phase 5 (retention) — pruning landed, stale detection cut

### The actual defect
`gateway_prune_live_context` had existed since Phase 3 and was **never called from anywhere**;
`memories` had no prune at all. Both tables grew without limit. That, not the missing policy, was
the thing to fix.

### `memory::prune` (host, `src/memory.rs`)
L0: TTL 30d + 200-row ring **per session** (window function `ROW_NUMBER() OVER (PARTITION BY
session_id …)` — the correlated-subquery form is quadratic). L1/L2: deleted once recency decays
below `PRUNE_FLOOR` (0.05 → ~4.3 half-lives ≈ 130 days). Cutoff derived from `PRUNE_FLOOR` and
`RECENCY_HALF_LIFE_DAYS`, not hardcoded. **Pinned and L3 are absolutely exempt.** `DELETE` is safe
against FTS — the `memories_ad` trigger fires per row (pinned by its own test).

### Scheduling (`src/lib/memory/retention.ts`, started in `App.tsx` beside the drain)
- Runs off the request path (the design's real requirement). No idle *signal* exists for a Tauri
  webview, so "idle" = 30-min timer + one pass at start. Documented as an approximation.
- **Gated on the master toggle** — with memory off neither table is written either (live context is
  only recorded past the mode gate), so there is nothing to prune, and the off-by-default guarantee
  has to include deletes. A failed toggle read reads as *off*, so an IPC blip cannot delete rows.
- One pass at a time (a prune is a table scan).

### Stale detection (§6.3) — CUT, with a reason
The rule assumes `subject` is a file/symbol reference. It is not: the distillation prompt asks for
"the shortest useful label" (2–4 words, e.g. `router work`). Nothing can stop resolving. Building
the validator would be speculative code that can never fire. Documented in the design doc.

### Still open
Conflict surfacing (§6.4): needs `superseded_at` + a Memory-screen surface. The design already
settles the hard part — contradiction is never auto-resolved (§6.4.5), so this is marking +
surfacing, not detection, and needs no model call.

### Falsification (four probes)
- `pinned = 0` guards dropped → both exemption tests fail.
- ring `rn <= ?1` widened → ring test fails.
- toggle gate stubbed out → both "touches nothing when off" tests fail.
- `running` guard stubbed out → overlap test fails.

### Gotchas
- **vitest does not typecheck.** `expect(x).toBe(true, "msg")` and `toHaveBeenCalledTimes(2, "msg")`
  ran green under vitest and failed `tsc`. Use `expect(x, "msg").toBe(true)`. The gate caught it.
- An overlap test hung 30s because the promise resolver was captured before the first pass reached
  the mocked call; `await vi.waitFor(() => expect(m))` before releasing fixed it.

  (`scope_project IS` — NULL-safe), different text. Narrow on purpose: real contradiction detection
  needs a model, and a broad list is noise. Scope is part of the match; two projects never meet.
- UI: `ConflictSection` in Memory.tsx with two honest answers — "the newer one is right" (unpin
  first, the host refuses otherwise) and "the pin is still right" (forget the newer). L3 held →
  first button disabled with the reason. `MemoryRow` dims superseded rows and offers "restore".

### Falsification
- `AND m.superseded_at IS NULL` → `AND 1 = 1` → the drop-out-of-recall test AND the conflict test fail.
- pinned/L3 refusal stubbed out → both the refusal test and the conflict test fail.

### Bug the gate caught (worth the general lesson)

## App-key principal — the last item in GATEWAY_MEMORY_LAYER.md, landed

Requirement (design, Phase 1): "resolving an `app_key_id` principal … needs a cached id→secret
map before it belongs on the request path."

### What changed
- `gateway.rs`: `AppKeyProvider` now returns `Vec<AppKey { id, secret }>` instead of
  `Vec<String>`. One keychain pass yields both, so identity costs nothing over auth.
- `AppKeyCache` on `GatewayCore` + `app_keys()` (memoised accessor) + `app_key_for(presented)`.
  `check_gateway_key` now goes through `app_keys()` too.
- `presented_key(headers)` extracted so auth and the memory path cannot disagree about who asked.
- `principal::key_principal(id)` → `key:<id>`; `allows()` takes `app_key` as a second identity;
  `list()` unions active `gateway_keys` so the operator can find the name.
- `context_scope.rs`: both `inject_context` and `prepare_capture` resolve the key, **only when
  memory is enabled**.

### Four decisions, each forced
1. **The memo is keyed on the active-id set, not on a TTL.** `active_gateway_key_ids` is one
   indexed SQLite scan; revoking/creating changes it, so revocation still takes effect on the next
   request — the contract `gateway_app_key_create` documents. A bare TTL cache would keep a revoked
   key authenticating for the rest of its window.
2. **No store ⇒ no caching.** The store is the only thing that can validate the memo.
3. **Either identity can deny.** One winner is a hole both ways: label-only lets a denied key come
   back on an unlisted label; key-only lets a client drop its label to escape a denial.
4. **Explicit cache invalidation was impossible** — `gateway_app_key_create/revoke/delete` take
   `State<Arc<Store>>` only, no core. That is *why* the id-set keying had to be self-maintaining.

### Falsification (6 probes, all confirmed failing then reverted)
- ignore the id set → `revoking_a_key…` + `creating_a_key…` FAIL
- remove the TTL → `the_memo_stops_being_served_once_its_ttl_expires` FAIL
- `fresh → false` → `the_app_key_map_is_read_once…` FAIL
- **`(None, _) => true` → `r4_revoked_app_key_rejected_immediately` FAILS** — a *pre-existing*
  contract broken by caching blind. Strongest evidence in the batch.
- label alone decides → 3 principal tests FAIL
- drop the `memory_enabled()` guard → `a_disabled_layer_does_not_read_the_app_key_map` FAIL

### A test that could not prove what it claimed
`a_presented_key_resolves_to_its_id…` asserted resolution of the *second* key and I first wrote a
comment claiming it proved the scan does not stop at the first match. It does not — `find` returns
the correct id either way. Replaced with
`resolving_a_key_scans_every_candidate_rather_than_stopping_at_the_first`, which gives two keys the
*same* secret: `find` answers `ak-1`, a full scan answers `ak-2`. Confirmed it FAILS when `break`
is added. Timing properties need an observable proxy.

### Verification
`env -u NODE_OPTIONS pnpm ci:local --skip-browser` → **ALL GREEN**, Rust **394** (+13). No TS
files changed. `GATEWAY_MEMORY_LAYER.md` Phase 1 note rewritten as landed.

A screenshot cannot tell you why a page is blank. **Attach `page.on("pageerror")` and dump

undefined field blanking a route — silently converts into "N tests time out with a black

## §10(2) — distillation spend is capped (landed)

Decision, written into `GATEWAY_MEMORY_LAYER.md` §10 item 2: **60 distillations per rolling hour**,
host-wide, counted by rows **claimed** (not completed) in the last hour.

- `capture.rs`: `pub const DISTILL_BUDGET_PER_HOUR: usize = 60`, `const DISTILL_WINDOW_MS`,
  `fn budget_left(conn)`. Wired inside `claim()` — `let budget = budget_left(&conn); if budget == 0
  { return Ok(Vec::new()); } let limit = CLAIM_LIMIT.min(budget);`.
- Why inside `claim()` and not at call time: a claimed row costs an `attempt`, and **three attempts
  retire the row as `failed`**. A cap that claimed then declined to call would silently *delete* the
  work it meant only to delay. There is a test for exactly that.
- `QueueStatus.budget_left` added; `queue_status` fills it. No migration — `claimed_at` was already
  written on every claim.
- `Memory.tsx` shows it (`data-testid="distill-budget"`): "N distillations left this hour", or
  "holding — hourly distillation budget spent" when `budget_left === 0 && outstanding > 0`.
  Defensive: `budget_left` is optional on the wire, `?? null` not `?? 0`, because "0 left" on a host
  that has no cap is a lie about work being withheld.

**Five Rust tests, all falsified**: `budget_left` returning `usize::MAX` fails all five; replacing
`CLAIM_LIMIT.min(budget)` with `CLAIM_LIMIT` fails only

## §10(5) — cross-vendor privacy stated in the UI (landed)

`PRIVACY_NOTE` in `Memory.tsx`, rendered beside the master switch (`data-testid="memory-privacy-note"`).
The substantive part of the decision was naming the **two egresses separately**, because they have

## Found and fixed a real bug: captures silently dropped after every restart

While re-running the budget check I noticed only one of two requests had been captured. Root cause,
and it is not a test artefact:

`GatewayCore.next_id` is `AtomicU64::new(1)` — it **starts at 1 on every launch**. But
`memory_pending.request_id` is UNIQUE for the life of the *database*, and finished rows are retained
seven days. So after a restart the ids repeat, the §3.5.5 idempotency guard reads each repeat as a
replay, and the capture is dropped. Silently — `Enqueue::Skipped(AlreadyQueued)` is a normal return,
so nothing logs, nothing errors, and the queue just looks empty.

Reproduced live on the installed 13:07 build, with a control in the same batch (memory was on —
every response carried `aip-memory: injected=1`). Six requests hit ids 7..12:

| id | pre-existing? | outcome |
|---|---|---|
| gw-7 | yes (09:42:25) | **dropped** |
| gw-8 | yes (09:42:50) | **dropped** |
| gw-9 | free | captured |
| gw-10 | free | captured |
| gw-11 | yes (11:02:09) | **dropped** |
| gw-12 | free | captured |

The captures prove the queue was working; the drops are exactly the ids that already existed. The
loss window is not one request — it is every id in `1..=previous_high_water`, so the next launch
would lose 3, 5, 7, 8, 11, 14 and 15 all over again.

**Fix.** `capture::request_id(n)` → `gw-{boot_marker}-{n}`, where `boot_marker()` is a `OnceLock` of
`{unix_millis}-{pid}` computed once per launch. `context_scope.rs:727` repointed. The string stays
opaque: the only production query is `WHERE request_id = ?1`, and the client-visible completion id
(`gw-{id}`, `resp_gw_{id}`) is a different string built for the wire.

**Falsified.** `a_fresh_processs_request_ids_do_not_collide_with_a_previous_runs` plants a previous
run's `gw-1..3` and requires this process's ids 1..3 to still be accepted, and re-asserts that the
same id twice in one process is still refused. Reverting to the bare `format!("gw-{n}")` fails it on
the first id with "gw-1 from this process collided with the previous run's: gw-1".

Doc: new **§5.4a** with the live table and the generalisable lesson — *a guard is only as good as the
identity it is given*. The reviewer constraint was "don't distil a turn twice"; the implementation
satisfied it and broke the one next to it ("don't lose a turn"). No test could see it: every test
built its own ids, so the generator was never exercised.

## The session-id serde bug: fixed, falsified, and its real blast radius

`MemoryInput` had no `rename_all`, so the webview's `sessionId` never matched `session_id` and serde
dropped it silently (unknown fields are ignored by default). Fixed with
`#[serde(rename_all = "camelCase")]`.

**The blast radius is narrower than "every capture" — it is the *batch* path only.** `memory_capture`
takes `session_id` as a **Tauri command argument**, which Tauri maps camelCase→snake at the command
boundary, then builds the struct with a **literal** (`commands.rs:370`) — serde never sees it. Only
`memory_capture_batch` deserialises `Vec<MemoryInput>` from the payload, and that is the path
`rememberTurn`/`distillAndStore` use (`captureMemories` → `capture_batch`). So hand-testing the singular
path showed a working session id while every batched L0 row got NULL. That asymmetry is why it survived.

Falsified: with the attribute removed,
`capture_input_reads_the_camel_case_session_id_the_webview_sends` fails `left: None, right: Some("s-1")`
— the exact silent-drop signature. Restored, green. **`capture_input_still_accepts_a_missing_session_id`
passes with the fix removed**, so it *pins a property* (no hard failure on session-less writes), not
evidence of the fix — labelled as such on purpose.

## The harness shared the bug — in exactly one of three places

`toRustArgs` (`shim.ts:529`) renames **top-level** command args, and its own comment says nested payloads

## Swept the whole bug class — `MemoryInput` was the only instance

The `rename_all` bug was found by accident, so I enumerated every `#[tauri::command]` parameter that is a
**struct or collection** (`^\s+\w+: (Vec<)?[A-Z]\w+`) — the only shape that is deserialised by serde
rather than mapped by Tauri — and checked each Rust type against what the TS side actually sends.

| nested payload | Rust | TS sends | verdict |
|---|---|---|---|
| `memory::MemoryInput` | **no `rename_all`** | `sessionId` | **the bug — fixed** |
| `ModelContextInput` | none | `model_key`, `context_window`, `chars_per_token` | consistent |
| `context::ContextNode` / `ContextEdge` | none | `session_id`, `meta_json`, `from_id` | consistent |
| `EgressRequest` | none | `secret_ref`, `timeout_ms` | consistent |
| `ImageFetchRequest` | none | `timeout_ms` | consistent |
| `MemoryScopeInput` | none | `kind`, `project`, `agent` | single-word → immune |
| `PrincipalPolicyInput` | none | `principal`, `enabled` | single-word → immune |
| `persist::ProviderRow` + ~14 others | `camelCase` | camelCase | consistent |

**No other mismatch.** So the codebase has *two* conventions for nested payloads — snake matching the
Rust field name (4 types), and camelCase with `rename_all` (`persist::*`, ~15 types) — and `MemoryInput`
was the single place where the TS side wrote camelCase while Rust declared snake. Both sides now agree.

Worth noting as a latent trap, not a bug: two of these paths swallow a naming mistake. `publishModelContext`
ends `.catch(() => 0)` (`store.ts:506`) and `ImageFetchRequest.timeout_ms` / `EgressRequest.secret_ref` /
`.timeout_ms` are all `#[serde(default)]`, so a future mismatch degrades to the 8k default or a default
timeout with no error anywhere. Only `ModelContextInput`'s non-`Option` fields would fail loudly.

**Open convention question** (left for the user): the fix could equally have gone the other way — change
`captureMemories`' items to `session_id`. That would make the nested-payload rule uniform (snake
everywhere) *and* make the write spelling match the read spelling (`Memory` serialises `session_id`).
I kept `rename_all = "camelCase"` because it matches what the *caller* already writes for the singular
`memory_capture` (`sessionId`, Tauri-mapped) and matches `persist::*`. Both are defensible; only one
should be chosen deliberately.

## The convention decision: `MemoryInput` → snake_case + `deny_unknown_fields` (resolved)

The deferred question — `rename_all = "camelCase"` on `MemoryInput` vs. changing `captureMemories`' items to
the snake `session_id` — is settled. **Snake, plus strictness.** Chosen from measured evidence, not taste.

**What the codebase actually does (enumerated, not remembered).** 22 `rename_all = "camelCase"` structs
(overwhelmingly `persist.rs`, plus `gateway.rs`/`workbuddy.rs`) against ~6 snake ones (`egress`, `context`,
`model_context`, `memory::Memory`). So camelCase is the *majority* — but the split is by subsystem, and the
decisive fact is that **`Memory` (the read struct, `memory.rs:62`) has no `rename_all`** while `MemoryInput`
(the write DTO) had camelCase. One feature, two spellings, both working. The webview's own `Memory` type
(`store.ts:757`) confirms the read side: `session_id`, `created_at`, `superseded_at`.

**Why snake won.** (a) `MemoryInput` is a 5-field DTO with 3 production call sites in one module
(`engine.ts:110,200,285`); `Memory` is the feature's read contract with ~10 read sites — change the narrower
thing. (b) Cohesion: `session_id` is the *same string* in `memories` and `context_nodes`, and
`ContextNode`/`ContextEdge` are snake, so making `Memory` camelCase would give one value two spellings in one
subsystem. (c) `persist::*` staying camelCase is not a contradiction — those are symmetric read+write rows,
which is exactly why `providerToHost`/`keyToHost` can pass a record through unchanged.

**The mechanism matters more than the spelling.** `rename_all` makes one spelling work and still fails
silently for every other one; `#[serde(deny_unknown_fields)]` makes *any* mismatch a hard error naming the
key. Added to `MemoryInput`. This is what turns "we agreed on a convention" into something enforceable.

**Three guards, each falsified by flipping it back:**
- Rust: `capture_input_rejects_the_camel_case_spelling` — removing `deny_unknown_fields` made the parse
  *succeed* with `session_id: None`. The original bug, reproduced in the failure output.
- Shim: `memory_capture_batch` now validates the item key set and throws, mirroring the Rust attribute.
- Browser: `memory.spec.ts:338` drives the batch path both ways. Removing the shim's check failed it with
  `Received: null` — the camel payload silently accepted.

**The discovery that reframes the bug: the broken path had no coverage at all.** No browser spec ever
reached `memory_capture_batch` — the single-capture command was covered and correct, so hand-testing the
screen looked fine while every batched capture stored a NULL session. That is *why* it survived for months,
and it is now the first thing to check for a class like this: a green suite says nothing about a path it
never drives.

**Also fixed:** the three silent `catch {}` blocks that swallowed capture failures (`engine.ts:113,172,294`)
now log. The swallow is deliberate — "a memory write must never fail a chat" — so detection lives at the
boundary (`deny_unknown_fields`) and visibility at the consumer (the log). Without the first the second
never fires; without the second the first is invisible.

**Counts:** Rust lib **407 → 408**, browser **70 → 71**; desktop unchanged at 170. `pnpm ci:local` **ALL
GREEN** with `~/.cargo/bin` on PATH.

**Near-miss worth recording.** I changed `memory-recall.spec.ts:33` to `session_id` on the assumption that
every `sessionId` was wrong. It is a `memory_capture` (**singular**) call — a top-level command argument,
where `sessionId` is *correct* because `toRustArgs`/Tauri renames it. Writing snake there is the silent-drop
spelling: it passes in the harness (the shim reads `args.session_id`) and would be dropped by the real host.
Reverted. **Rule: check which boundary a call crosses before "fixing" its spelling** — the same `sessionId`
string is right in one place and wrong in another.

  read, and are always available"). Not in `MUTATING_TOOLS` (`gateway.rs:614`), so
  `gateway_tool_refusal` (`:1077-1087`) never fires for them.

  **false** (`:663`). Reads and writes are *already* on separate switches — that is the property to keep.

**Finding 1 — the doc's L3 premise is incomplete, and the omission is in the *safe* direction.**
`default_workspace_root()` is **`$HOME/AI-Provider-Router-Workspace`** (`gateway.rs:626-631`) — an
app-created folder, deliberately *not* `$HOME` and *not* cwd. So "reads are as broad as the workspace is"
is true but the workspace is a dedicated, empty-by-default folder, not the operator's data. Ungated reads
are materially less exposed than §8(1) implies.

**Finding 2 — the setter is unreachable, which cuts both ways.** `gateway_set_workspace_root` is registered
(`commands.rs:727`) and its only production call site is itself (`gateway_cmds.rs:564`); **nothing in
`apps/desktop/src` invokes it** — `Gateway.tsx:514` merely *documents* the default. So the gateway root is
always the default folder. Consequences: every key shares it (L1+L3 are one defect), and an operator who
wants a foreign agent in their real repo cannot point the gateway there. Lower risk, lower utility — decide
whether that is a bug or deliberate.

**Recommendation:** reads stay ungated (root confinement is verified, the default root is an app folder);
never fold reads into the mutation switch (that makes the gate coarser, not safer); make the grant an
explicit policy field so access is not expressed as *an absence from a denylist*; make the root
per-principal **and reachable**; add sensitive-path denial *inside* the root (`.env`, `.ssh`, `*.pem`,
`.git/config` — credentials can sit in a remote URL).

**Reusable audit procedure** (this is the transferable part): to test whether a host-enforced gate is real,
walk four steps — find the denylist and confirm the target is absent from it; find the *single* call site
that consults it and confirm it is on the execution path; read the confinement primitive for the resource;
and identify what the *default* resource actually is. A gate whose resource default is benign and whose
confinement is tight is a different decision from one whose resource is the user's home directory.

## Architectural tension worth remembering
Capture-only writes (§5.4: atoms written unscoped) + scope-excluding reads (fact 3: scoped recall
refuses Unscoped) are MUTUALLY EXCLUSIVE by construction. The write path produces rows the read path
refuses. So the 0-vs-14 rows is the STEADY STATE of a human-in-the-loop binding design, not a bug.
Consequence: the gateway memory read half (deadline, freeze, rank/trim/compose) is effectively
unexercised in production — only live context actually injects. Anyone "fixing" 0-vs-14 by loosening
the scope predicate would simultaneously activate all that dormant machinery AND break the
contamination guarantee. That is a dangerous one-line change.

## SESSION 11 — the third shape: a run the dashboard will never list

The item §4a.5 had deliberately scoped out: `startRun` / `recordStep` still swallowed plain omissions. Closed.

`agent_run_start` failing leaves **nothing** — no row, no status, no ending to mark — and every later step
append for that run fails for the same reason (FK in Rust, `unknown run` at `shim.ts:1262`). Counting each
would report "4 writes could not be recorded" for one lost run with three steps, and a two-run outage as eight
faults. So: `startRun` records the id in a module-level `unrecordedStarts` set; `recordStep` reports **only
when its run was recorded**. The set is never cleared — an append from an ended run can still be in flight, and
clearing on end would let a late failure be counted for a run already reported.

`agent_run` is a third `TrailId`. `TrailWriteWarning` moved out of `Providers.tsx` into
`components/TrailWriteWarning.tsx` and takes `noun` / `nounPlural` — **the noun is the screen's, not the
component's**: the provider cards lose *rows*, the run history loses *writes*, and hardcoding "row" would have
made the Agents warning say something false. The warning renders **above the empty-state branch**, because the
run whose start failed is absent — a warning gated on rows is invisible in exactly the case that matters.

The finish write contributes nothing here: `shim.ts`'s `case "agent_run_finish"` and `orchestrator.rs:123` both
update **without checking a row count**, so they report success for a run that does not exist.

**A probe changed the spec, not the code.** The first two probes both produce an inflated count, so with the
correct count asserted first all three failed on the same line with the same message — indistinguishable, so
weak evidence. Asserting the **inflated** count first gives the placement probe its own failure line; 3-vs-4 is
distinguished at the unit level. (Unit: 3 when the start is unrecorded, 4 when the suppression is dropped.)
The unit spec cannot reproduce the real cause — the fake host answers `undefined` for anything not arranged to
fail — so it tests the *suppression*, and the browser spec pins the real `unknown run` semantics.

**One thing to carry:** I left the tree broken across a context boundary — `Providers.tsx` importing a
component file that did not exist yet. Restored and typechecked before anything else next session.

## SESSION 12 — the fourth shape: a stranded repair whose card claimed work that had stopped

The last item the survey had left open. Measurement made it worse than recorded.

`onTrigger` (`store.ts:198-203`) sets `repairing` and fires `buildRepairPlan` with `.catch(() => undefined)`.
The card rendered "Building a repair plan…" for as long as `pendingRepairs` held no entry, so a failure before
the entry existed left that sentence up forever — in the same words as a genuine in-flight build. Waiting was
indistinguishable from broken.

Two ordinary causes. (1) `adapters.forProvider` throws `no active manifest` for a provider hydration could not
register — exactly what a corrupt manifest leaves behind, and `store.ts:350-357` promises "Phase 5 drift/repair
surfaces it". It sat *outside* the try, so the throw rejected `buildRepairPlan` itself. (2) `pendingRepairs` is
in-memory, never persisted — after a restart a still-`repairing` provider has no entry and nothing is building.

**And there was no way out**: `Check health` was hidden for `repairing` (`Providers.tsx:87`), so the only button
left, "Repair…", opened a modal saying "No drift event recorded" — also false, since the event *was* recorded;
the plan was what was missing. A provider stuck in `repairing` was unrecoverable through the UI.

Fix: the entry is registered **before** anything can fail, both silent early returns became errors, the card is
four-way (plan / error / still-building / **no entry** → "No repair is running in this session"), and
`Check health` is offered for `repairing` too — otherwise telling the truth is a dead end. Seeded as
`?seed=repair-stuck`.

**Two traps I paid for.** `adapters` is a module singleton and `approveRepair` hot-swaps an adapter in
(`store.ts:282`), so a spec reusing an id an earlier spec repaired gets the manifest it is trying not to have —
caught because it failed with the *next* error along. And `rm -rf apps/desktop/test-results` tripped the
bulk-delete guard (`count: 960`) and cost a gate run; move, never delete.

**A strict-mode violation I should have predicted**: the RepairModal renders `entry.error` too, so
`getByText(/no active manifest/)` resolved to two elements. Scoped to the card's own paragraph.
