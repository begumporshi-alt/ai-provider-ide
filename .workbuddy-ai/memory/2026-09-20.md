## The client-facing status was decided by a regex over the error message

Row 318 above is the evidence: a deterministic client error (Agnes rejecting a malformed tool
sequence) was answered **HTTP 502**, telling the caller the gateway was broken and inviting retries for
a request that can never succeed.

The cause was not the Rust status mapping I first suspected. `gateway.rs` enumerates 404/429/401/503 and
lets 400 fall through to `BAD_GATEWAY` — but the decision is actually made in the webview, in
`gateway-bridge.ts`:

```ts
const status = /no route|not found/i.test(msg) ? 404 : 502;
```

A regex over the error *message*, when `AllAttemptsFailedError.chain` was already in hand with each
attempt's real upstream status. Replaced with `gatewayStatus()`, which passes through only
client-attributable codes (400/404/413/422/429). Upstream 401/403 are deliberately **not** echoed: those
mean *our stored key* was rejected, not the client's. Same family as the ledger bug — asserting from a
message when the structured value was available.

4 specs added to `gateway-bridge.test.ts`, proven failing first with `expected 502 to be 400`.

## The gateway can be wedged completely — and silently

The end-to-end re-verification of the three status codes could not be completed, and the reason is a
defect of its own, not a flake.

**Symptom.** The listener binds, `lsof` shows a healthy LISTEN, `pgrep` shows a live process — and **no
request is ever answered**, `/v1/models` included. Nothing is logged (the failure is a hang, not an
error) and no ledger row is written. `pkill` + relaunch does not clear it: three consecutive launches
each logged a clean startup and each answered nothing.

**Diagnosis, via the marker.** `startup: key refs probed` appears ~21 s after a healthy startup. It is
absent from `gateway.log` for the current instance — and present for the last instance that worked
(epoch 1789844385, which wrote rows 317–319). That single grep is the whole test; a healthy restore
takes ~20 s, so "still starting" is not an explanation.

**Root cause, from `sample <pid> 2`.** Three of the app's own threads were queued on the one
process-wide Security-framework keychain mutex: `workbuddy::sync` *holding* it while blocked in a
securityd IPC round-trip (`ClientSession::decrypt` → `mach_msg2_trap`), `probe_key_refs` waiting on
`_pthread_mutex_firstfit_lock_wait`, and **a tokio-rt-worker behind them** — the request path, because
`gateway.rs:67` `vault_key_provider()` is a bare `vault::get(MASTER_ACCOUNT)`, uncached and unbounded,
called per request. The trigger is the reinstall: it invalidates the keychain ACL, and this time the
re-authorization never completed.

**Two wrong turns worth recording.** I first concluded the app was frozen and the main thread blocked —
the sample disproves it: the main thread idles normally in `__CFRunLoopRun` and is actively servicing
WebKit IPC. I also tried to confirm a visible prompt; `osascript` cannot list the app's windows
(privilege violation) and `SecurityAgent` is a persistent agent, so whether a dialog is on screen is
**not locally determinable**. What is provable is that the read never returns.

Not fixed. Caching the key would break `criterion8_rotation_kills_old_key_instantly` unless
`set_master_key`/`clear_master_key` invalidate it — a deliberate trade-off, not a silent one. Detail and
options in `REFERENCE.md` → "Keychain: ACL".

## Fixed: a stalled keychain no longer takes the gateway down with it

The wedge diagnosed above is now survivable rather than fatal. `MasterKeyCache` (`gateway.rs`) wraps the
injected key lookup and is what `check_gateway_key` — and `gateway_status`, whose raw read froze the
Gateway screen — now use. Cached (one read, not one per request), bounded (`MASTER_KEY_WAIT` = 1500 ms),
and single-flight (a stuck keychain parks one thread, not one per request).

The part that had to be got right: the per-request read was *documented* as the rotation guarantee
(`gateway.rs:899` — "the old key dies instantly because every request re-reads the keychain"), so a naive
cache would have silently broken `criterion8_rotation_kills_old_key_instantly`. Each value is therefore
stamped with a generation that `invalidate()` bumps, and `generate_master_key`/`revoke_master_key` are
now **private**, with `GatewayCore::rotate_master_key`/`revoke_master_key` doing write-then-invalidate as
one operation — a caller that forgot to invalidate would leave the old key working silently.

`Unavailable` is also now distinct from `Absent`: the first is "the keychain did not answer" (503), the
second "no key configured" (401). Both were `None` before, and the request path reported both as 401 —
blaming the client's credential for a local fault.

**Falsified first.** Reverting `get()` to a bare `resolve(&(self.inner)())` failed four specs with the
expected signatures — including *"the gateway must answer while the keychain is stalled — it hung
instead: Elapsed(())"* — and the suite went from 0.79s to **30.08s**: the hang, made visible.

**Verified end-to-end in the shipped build.** With the probe bypassing the sandbox proxy, three
sequential requests against a stuck keychain returned `HTTP 503 in 1.502s`, `1.502s`, `1.511s` — the
bound, reproducibly — while `sample` showed 3 threads still parked in `SecKeychainFindGenericPassword`.
Rust suite 172 → 176.

**A trap I fell into, worth remembering.** The first verification run reported `502 upstream connect
failed` for all three cases, which reads exactly like a gateway defect. It was the sandbox proxy: `env
-u` had been applied to the *app launch* but not to the probe. **The tell was the ledger — no row was
written, because the request never reached the gateway.** Check for the ledger row before believing a
5xx came from the app.

**Still open:** the three client-facing status codes (400 / 404 / 200) remain unverified end-to-end. The
4th reinstall re-invalidated the ACL and the wedge returned, so no request authenticates and none reaches
the router. That needs the keychain prompt approved — not more code.

## The edge was throwing away the status the worker had already decided

**Found while verifying the keychain fix, not while looking for it.** The webview's `gatewayStatus()`
applies a deliberate whitelist — pass through client-attributable upstream codes (400/404/413/422/429),
map a missing route to 404, everything else to 502 — and the Rust edge then **re-decided with a second,
narrower list and discarded most of it**. The OpenAI chat path knew only 404/429/401/503, so a 400 became
502; the Anthropic, Responses, `/v1/models` and Gemini paths discarded the status entirely and answered
502 for everything.

Net effect: Tushu's original bug — a schema error reported as 502 — **was still not fixed end-to-end**,
because the fix had landed only in the webview. The client was told its request had hit a broken gateway
when the request itself could never succeed, which invites retries that can never work.

This is the **third instance of one class** this month: re-deriving a structured value from a weaker
source while the real one was in hand. (The others: the ledger's `errorClass` written as a literal, and
`providerId` read from `last.candidate`.)

**Fixed.** Added `worker_status()` in `gateway.rs`: trust the worker's decision, reject only a value that
cannot be a real HTTP error status. All five consumer sites now call it. Three streaming arms also
hardcoded a failure they had not been told — Anthropic always `overloaded_error`, Gemini always
`code: 502 / INTERNAL` — and now derive it from the status (`anthropic_error_kind`, `gemini_error_body`),
which is the only channel left once SSE has committed a 200. Gemini's 429 branch used to answer
`code: 503, status: "INTERNAL"` while claiming "at capacity"; it now answers 429 `RESOURCE_EXHAUSTED`.

**Falsified first, twice.** (1) Neutering both helpers failed all four end-to-end specs plus the two unit
specs — `left: 502, right: 400` on each, which *is* the bug reproduced — and the negative-direction spec
correctly still passed. (2) Reverting the three streaming arms failed the three streaming specs, with
Gemini's old payload visible in the failure output: `data: {"error":{"code":502,...,"status":"INTERNAL"}}`.
Both probes removed; probes verified absent (0 hits across all four files).

## A fourth instance, one layer up: the shared auth gate

Chasing a failing spec I had just written led to `check_gateway_key` — the gate every handler calls before
doing anything. It returned a finished **`Response`**, in OpenAI shape, for all six of its refusals:
gateway-disabled (503), no-key (401), keychain-unavailable (503), auth-backoff (429), invalid-key (401),
spend-cap (402). So Anthropic clients received no top-level `type: "error"` (they branch on `error.type`),
and Gemini clients received `error.code: null` with no `error.status` at all — a strict SDK cannot classify
its own auth failure.

Same principle as `worker_status`, applied to *shape*: **the layer holding the evidence decides the outcome;
the dialect decides the envelope.** The gate now returns
`GateRefusal { status, message, retry_after, openai_type, openai_code }`, and each handler calls
`GateRefusal::{openai, anthropic, gemini}`. `Retry-After` is preserved on every path that had it.

Falsified by reverting both dialect framers to the single OpenAI envelope: the Anthropic spec failed
`left: Null, right: "error"` (no top-level `type`), the Gemini spec `left: Null, right: 503`
(`error.code` is null). The OpenAI guard spec correctly still passed — the refactor is about shape, and
`criterion8_wrong_key_401` still holds the OpenAI envelope in place.

**One more, smaller:** the Anthropic `try_slot` failure arm hardcoded `overloaded_error` / "gateway
unavailable or at capacity" for every refusal — so a *stopped* gateway asserted a capacity problem and told

(`429 → rate_limit_error`, `503 → overloaded_error`). Reachable in tests by `s.core.permits.close()` — the

## "The router stops after a tool call" — the two halves of the pair were built separately

Tushu reported that routing/execution dies once a tool call completes, and suspected Tauri. It was not
Tauri: it was a message-assembly bug in our own TS, and the previous `replayHistory()` fix had *masked*
it rather than fixed it.

**The contract.** A tool-calling continuation must send a matched pair — the assistant turn declaring
`tool_calls[].id`, then a `tool` message whose `tool_call_id` equals one of them. Providers answer HTTP
400 when they do not match, and the conversation cannot continue. That is the reported symptom exactly.

**Defect A — divergent fallbacks.** `manifest-interpreter.ts:117` emits `id: undefined` when a provider
carries no id. Each loop then applied its OWN fallback and they disagreed:

| site | assistant declared | result carried |
|---|---|---|
| `gateway-bridge.ts` | `id: c.id ?? ""` → `""` | `tool_call_id: call.id ?? name` → `"write_file"` |
| `agentLoop.ts` | `tool_calls: collected` → absent | `tool_call_id: call.id ?? name` → `"write_file"` |

Nothing required them to agree because **nothing built them together** — two separate statements. With an
id present both used it and it worked; without one, the pairing broke.

**Defect B — flat shape.** Both sites sent `{id, name, arguments}`. OpenAI requires
`{id, type:"function", function:{name, arguments}}`. `manifest-interpreter.ts:216` passes `{{messages}}`
through verbatim, so the malformed entry reached the provider unmodified. `ToolCall.raw` already held the
provider's correct object; neither site used it.

**Why the specs passed.** Both used a well-behaved provider supplying `id: "c1"`, so the fallbacks never
fired and the shape was never asserted. **Test fixtures that supply ids cannot catch an id-handling bug.**

**Fixed with one function.** New `apps/desktop/src/lib/tools/wire.ts` — `toWireToolCalls(calls)` returns
the wire entries *and* the ids it chose, so the assistant turn and the results come from one decision and
cannot drift. Synthesizes `call_<n>` when the provider supplies none. `toolCallName()` reads either shape,
because the context graph walks transcripts written before and after this change.

Changed: `gateway-bridge.ts` (`sandboxTurn`, `executeLocally(calls, ids)`), `agentLoop.ts` (same),
`Playground.tsx` (tolerant name reader).

**Falsified first, both paths.** Gateway: `expected '' not to be ''` — declared `""` vs result
`"write_file"`, the bug in one line. Agent loop: `expected 'undefined' to be 'string'`. Both probes
removed, absence confirmed. Suites: desktop **130 → 132**, router-core **216**, `tsc` clean.

**Side effect worth noting:** `runAgentLoop` now returns wire-shaped `tool_calls`, so `replayHistory()`
hands the provider a valid pair on the next plain message — the `BAD_REQUEST_SCHEMA` failure that was
previously worked around is now closed at the source.

## Correction: audit C1 was rated CRITICAL on a premise I never tested

While hardening C1 I checked the assumption the rating rested on, and it does not hold. **Downgraded
CRITICAL → MEDIUM**, and the recommended fix was wrong too.

**The premise I asserted:** "a compromised extension, **malicious model output**, or XSS vector can invoke
`tool_run` with any root." Tested it — there is **no XSS sink anywhere in `apps/desktop/src`**: zero hits
for `dangerouslySetInnerHTML`, `innerHTML`, `eval(`, `new Function`. Model output renders as text (React
escapes), so it cannot reach JS. That vector does not exist.

**Second thing I missed:** the root is *legitimately* caller-supplied by design. It is a free-text,
user-facing input — `Playground.tsx:551` placeholder "/absolute/path the tools are confined to", passed to
`createTauriToolHost(root.trim())` at :375. `tool_run` taking a root is the intended contract, not a leak.
My "remove `tool_run` from `handlers()`" fix would have broken agent mode.

**What survived:** Tauri capability files really do not ACL app-defined commands — verified, `default.json`
grants only `core:default`/`opener:default` and `gateway.json` only `core:event:allow-*`, neither naming any
app command. And `resolve_within` confines *to* the root correctly; only the root itself was unjudged, so
typing `/` gave no confinement. That is a footgun, so the fix is host-side validation, not removal.

**Implemented:** `validate_root()` in `tools.rs` — canonicalizes, then refuses non-existent/non-dir, `/`,
`$HOME`, and `/System /usr /bin /sbin /etc /private`. Refuses rather than clamps (silently rewriting `/`
would hand the user a workspace they never chose). Wired into `tool_run`, with 7 specs.

**The lesson, and it is the same one as the status-code work:** a severity rating is a claim about the
world, and mine named a specific attack path I had not checked. Before writing "an attacker can X", check

## H3 closed — lock-poison handling would be dead code (no code change)

The last open HIGH finding said: 206 `.unwrap()` sites, `panic = "abort"` turns every poisoned lock
into a hard crash, so replace lock unwraps with a 503 return (8h, mechanical). **Both halves are
wrong, and I proved the first one instead of arguing it.**

1. **Poisoning is unreachable in release.** Poisoning is set in `MutexGuard::drop`, which runs only
   while *unwinding*; `panic = "abort"` (`src-tauri/Cargo.toml:55`) means there is no unwinding.
   Built the same program both ways: unwind → `second lock POISONED`, exit 0; abort → SIGABRT at the
   first panic, exit 134, the second lock never runs. There is no "next request". `panic = "abort"`
   does not make poison dangerous — it makes poison impossible.
2. **206 was a raw grep including `#[cfg(test)]`.** Split properly: production `.unwrap()` = **76,
   every one a lock call, zero non-lock**; test-only = 410. Production `.expect()` = 3, all
   construction-time (`egress.rs:396/411` reqwest clients in `Egress::new()`, `lib.rs:256` Tauri
   builder). Production `panic!`/`todo!`/`unimplemented!`/`assert!`/`unreachable!` = **0**.

temporary guards — `gateway.rs:925/1297`, `gateway_cmds.rs:242/247/277`); no `catch_unwind` anywhere.

**Measurement caveat that bit me twice:** splitting prod/test by "cut at the first `#[cfg(test)]` at
column 0" silently truncated `gateway.rs` (its `#[cfg(test)] mod tests;` *declaration* sits near the

**What remains true:** with abort, any panic on any thread kills the app. That is the profile, not

## M1 re-scoped — `RwLock<Connection>` does not compile

The audit's fix for "SQLite `Mutex<Connection>` serializes everything" is **impossible as
written**. `std::sync::RwLock<T>: Sync` needs `T: Send + Sync`; rusqlite's `Connection` is `!Sync`
(it holds `RefCell<InnerConnection>` and `RefCell<LruCache<…>>`). Proved with a compile probe
(`fn need_sync<T: Sync>()` applied to both types): `RwLock<Connection>` errors twice,
`Mutex<Connection>` compiles — the mutex only needs `T: Send`, which is exactly why it is there.
Swapping it in would break the `Arc<Store>` every command shares. The finding's own aside —
"`Connection` is `!Sync` by design" — was the constraint, read as a footnote.

What is actually true, measured: 30 production fns in persist.rs take the store lock, **none**
calls another locking fn, none takes it twice → no self-deadlock path. Pragmas already correct
(`store.rs:500-503`): WAL, `synchronous=NORMAL`, FK on, `busy_timeout(5s)`. So the only real cost
is readers queueing behind writers — modest for a single-user desktop app. Real fix is a pool or
the owner-thread/actor pattern; deferred with a "measure lock wait first" trigger.

## A real bug in the code I had just written: `search_files` capped matches, not bytes

Found while re-reading my own new tools, not while hunting. `MAX_OUTPUT_BYTES` (64 KB) is applied
**only to `run_command`** (`tools.rs:655`) and to the allowlist struct. `search_files` capped the
*number of matches* at 200 — and **a "line" is whatever sits between two newlines**, so a 2 MB
minified file is ONE line. 200 such matches is ~400 MB.

**Measured, not argued:** falsifying the fix produced **804,004 bytes** from one search — ~12× the
cap, from a workspace of four files. Before the fix that string went straight into the model's
context, and then into `context_nodes.label` on disk.

**Fix, two bounds:**
- `clip_line()` — char-wise clip of each displayed line to `MAX_SEARCH_LINE_CHARS = 300`, with a
  `… (N chars)` marker. Char-wise, not the byte-wise `truncate()`: a hit is built from `str`, and
  byte truncation splits a multi-byte character (a test asserts no U+FFFD).
- total output capped at `MAX_OUTPUT_BYTES`, the same bound `run_command` already lives under.
- The cap message now **names which bound fired** ("capped at 200 matches" vs "capped at 65536
  bytes"). "Narrow the pattern" and "narrow the path" are different advice, and a model given the
  wrong one retries the same search.

5 specs. **Falsified** by no-op'ing `clip_line` and the byte check: 2 fail with
`output exceeded the byte cap: 804004 bytes`; the 3 that still pass are the ones the caps do not
govern (short line intact, no char split, match-cap case) — correct, not a gap.

**My first fixture was wrong and the test caught it:** 40 files × 4 000-char lines produced only
~14 KB after clipping, so the byte cap never fired and I had asserted a cap that was not being
exercised. Raised to 250 files so the byte cap is the bound that stops it, and paired it with a
250-file *short*-line case where the match cap is the bound — together they prove the message
names the right cap.

Rust **251** (was 246, +5). No TS touched. Rebuilt + installed.

**Lesson, and it is the one I keep relearning:** a cap on the *count* of results is not a cap on
their *size* whenever the unit being counted is unbounded. Same shape as "a cap on requests is not
a cap on bytes".

## L2 — the audit's claim was impossible, and the real defect pointed the other way

Audit said: "`is_local()` trusts any port on localhost." **Both halves are wrong, and I measured
rather than argued.**

**The port cannot be an input.** All three call sites (`check_url`, `image_host_allowed`, the
image-client redirect policy) pass `Url::host_str()`, which excludes the port. `is_local` was a

`127.0.0`, `127.0.0.1.5` and `127.evil.example` wrong.

(`127.0.0.2 is loopback`; `check_url("http://127.0.0.2:11434/v1").is_ok()`), while the other 17
egress tests — including every secret-pairing test — still pass, so the invariant-3 boundary was
untouched. Probe reverted, absence verified.

Rust **254** (was 251, +3). Rebuilt + installed.

**Why this is the fourth one:** C1, H1, M4 and now L2 all had the audit naming a mechanism that

## `custom-local:agnes-2.5-flash` 503 — it was FIRST_MSG_TIMEOUT, not a suspended window

Tushu pasted a WorkBuddy error: `Custom model custom-local:agnes-2.5-flash error` /
`{"code":-32603,...,"details":"the router worker did not respond — the gateway window may be
suspended"}`, timestamp 19:03:52 UTC+8.

**My first answer was wrong.** I said the message came from WorkBuddy's own router and blamed a
`custom-local:` naming mismatch. Both claims are false — the string is ours, at
`apps/desktop/src-tauri/src/gateway.rs:853`, emitted as `BridgeMsg::Error { status: 503 }` by
`Slot::recv()` when `FIRST_MSG_TIMEOUT` (30s) expires. And `custom-local:` resolution is fine:
`stripClientNamespace` strips it and dozens of `ok` ledger rows for `agnes-2.5-flash` prove it.

**Do not trust the message's own diagnosis.** It asserts a cause ("window may be suspended") that is
a guess baked into the string. The measurements contradict it — the window was alive and serving the
whole time.

**What the evidence actually shows** (live DB, ledger rows around the failure):

| observation | value |
|---|---|
| failed row | `error / CANCELLED`, `latency_ms = 33152`, `tokens_in = 0` |
| start (end − latency) | 1789902202 |
| WorkBuddy's error ts | 1789902232 = start **+ 30.0s exactly** |
| surrounding `ok` rows | 8.6s–27.3s latency, **119k–161k `tokens_in`** |

The 30.0s is `FIRST_MSG_TIMEOUT`, to the second. The worker never emitted a first message because in
gateway-tool mode the bridge emits nothing until a turn finishes, on a ~150k-token prompt.

**Why nothing was emitted for a whole turn:** `gateway-bridge.ts` only probes liveness
`if (gatewayTools && iter > 1)`. Iteration 1 has no probe, so Rust's 30s bound sees silence for the
entire first turn. Turn 1 on a 160k-token prompt exceeded it.

**FIXED.** `apps/desktop/src/gateway-bridge.ts` — the probe now runs on every iteration
(`if (gatewayTools)`), no longer `iter > 1`. And `gateway.rs` — the 503 now reports what was
observed (`"produced no response within {bound}ms — the request was abandoned; retry"`) instead of
asserting suspension.

Safe by construction: the probe is sent *by* the worker, so a suspended worker still sends nothing
(30s bound still fires), while a running-but-slow worker proves it is alive and survives.

**A side effect worth knowing, measured not assumed:** the probe now fires *before* turn 1, so a
client that has already disconnected is caught without ever calling the model or the sandbox. The old
test asserted `gateway_tool_run == 1` (turn 1 ran, then we noticed); it now asserts 0. Strictly
better — no tokens spent on a dead request.

**Trade-off I did NOT resolve, deliberately.** Chat egress passes `timeout_ms: null`
(`ipc-client.ts:39`), and `egress.rs` only applies a timeout when it is `Some(ms)` — so there is
**no upstream timeout at all**. Lifting the 30s bound on turn 1 therefore means a genuinely *hung*
upstream now hangs indefinitely instead of failing at 30s. Client disconnect is not detected either:
in gateway mode nothing is emitted mid-turn, so a failed `gateway_chunk` never happens. This is not

## Closed the hang my own fix opened: upstream idle bound

Lifting the 30s first-message bound meant a genuinely *hung* upstream would hang forever, so the
backstop had to be replaced with a real one. Added `UPSTREAM_IDLE_TIMEOUT` (120s) in

- `b.send()` in `stream()` — a handshake that completes and then never answers.
- each `stream.next()` — a stream that opens and then stalls.

A stream that keeps producing data is never cut off, however long it runs. This was the actual hole:
`connect_timeout` is set (10s) but covers only the TCP handshake, and chat passes `timeout_ms: null`,

is >4x the worst observed. Re-verified after install: 1721 tokens → 200 in 0.7s; 179,722 tokens → 200

`Channel<StreamEvent>`, which a unit test cannot construct, and 120s is too slow to wait out anyway.

was sized against **Agnes only**; other providers (Cline et al.) were never measured, so a provider

1. **The gateway is write-only against the context graph.** Verified by grepping every `gateway*.rs`
   for `context`: the only non-test hits are `record_gateway_tool_call` and its three tests. There is
   no read path — no `context::graph`, no `sessions()`, no `timeline()` — anywhere on the request
   path. `GatewayState.store` exists purely so the audit path has somewhere to write (its own doc
   comment says so). So the gateway does not "get" anything from the helper; it only contributes.
2. **`source: "engine"` has no production writer.** The column CHECK allows
   `('ui','gateway','engine')` and `context.rs:29` documents `engine` as "derived by the helper, not
   observed directly", but the only place it is ever set is a fixture in
   `web-test/history.spec.ts:54`. Production writers: `ui` (`recorder.ts:48`, `Skills.tsx:63`) and
   `gateway` (`gateway_cmds.rs:672`). Live DB confirms it — 340 `ui`, 3 `gateway`, 0 `engine`.
   Treat `engine` as reserved, not in use.
3. **`source` is not surfaced anywhere in the UI.** `buildConversationGraph` (`engine.ts:73-81`)
   maps only id/kind/label/ts/meta and drops `source`, so a gateway node renders identically to an
   Assistant tool node in the Context screen. `Context.tsx` never reads it either. If provenance
   matters on screen, that mapping is where it has to be added.

**Do not confuse `context_nodes.source` with `LedgerSource`.** The usage ledger has its own
`source` (`"ui" | "gateway"`, set in `gateway-bridge.ts:301,382`); different table, same two words.

## Designed the gateway-level memory/context layer

Wrote `GATEWAY_MEMORY_LAYER.md` (485 lines, repo root) — architecture, schemas, contract, and a
7-phase plan for giving every downstream model shared persistent memory so external agent IDEs
(Cursor, Claude Code, Continue, Aider) get it regardless of vendor.

Tushu also asked "what about this plan of implementation", so the doc leads with the verdict rather
than burying it. Five findings that changed the design:
1. It reverses the recorded "skills are frontend-only / gateway is blind" decision, for the same
   reason that decision existed (bills tokens on every call from every client, invisible layer, no
   review step). Mitigation = host-side toggle + budget cap + audit row, same as the tool path.
2. Recall is host-side BM25 and belongs on the request path; capture needs a model and does not.
   Queue it.
3. **Header-only metadata would get zero adoption** — Cursor/Continue can set a base URL and a key,
   not arbitrary headers. The body-level `metadata.aip` fallback is required, not optional.
4. L0 is verbatim, so cross-session injection ships one vendor's conversation to another. Default
   L1/L2/L3, L0 opt-in per scope.
5. It is a billing change — injected tokens burn the R4 spend cap faster per call.

Request-path facts that fixed the shape are in REFERENCE.md under "Gateway memory layer".

## Validated the design against ChatGPT + Claude + chat.z.ai (AI Hub relay)

Tushu asked for it; it was worth it. Same adversarial brief to all three. Doc grew 485 → 679 lines;
changes are marked **revised after review**, and §11 records what I adopted, what I rejected, and why.

**Unanimous: nullable-means-global is a contamination engine.** Self-defeating in a way I missed —
`metadata.aip` exists precisely because IDEs can't set headers, so the *common case* degrades to
`project = NULL` → global. Now: null project = capture-only, global is an explicit column.

**Two things I genuinely missed:**
1. **Prompt-cache destruction (z.ai).** Coding agents are built around provider prompt caching; a
   per-request re-ranked block at system position 0 invalidates the whole cached prefix every call.
   Fix = deterministic tie-break + freeze the block per scope for a TTL. Probably the highest-value
   item: it halves token spend via cache hits.
2. **Capture is a credential-laundering pipeline and an instruction channel (ChatGPT + z.ai).** Tool
   output is full of secrets; the distiller copies them into atoms; injection broadcasts them
   cross-vendor — recreating at the memory layer the leak the per-vendor keychain exists to prevent.
   And memory derived from conversations lets a model indirectly write future system context.
   Fix = never distil tool output, scrub at enqueue (the SQLite row is the liability), typed atoms.

Also adopted: strip `metadata.aip` before dispatch (day-one bug), exclude the internal principal or
distillation self-captures, build the retrieval query from extracted identifiers instead of the raw
prompt, pinned = retention not truth precedence, floor applies to unpinned only, 10–20ms hard
deadline on the memory path, drop L2 from v1.

**Rejected:** replacing BM25 with a keyword heuristic (the other two said keep + augment); ranking
layer before recency (the existing order is already recency-first, the reviewer read it backwards);
read-time decay as a bottleneck (candidates are bounded at limit×4, integer math).

**Tooling gotcha:** `mcp.json` points ai-hub at 8787 = our gateway's default port, so `mcp__ai-hub__*`
never resolves while this app runs. AI Hub was on 8788; called its JSON-RPC directly. Recipe in
REFERENCE.md. Also: `chat` timed out on chatgpt + zai but `read_latest` recovered both — don't resend.

**Design correction found while implementing:** the doc claimed "all four dialects converge on a
canonical body so there is ONE shape to inject into." True for injection, false for *parsing*: the
translation functions rebuild the body and drop unknown fields, so `metadata.aip` never reaches the
canonical body on the Anthropic/Responses/Gemini paths. Reading the contract from the canonical body
would have silently ignored the body fallback for exactly the header-less clients it exists for.
Hence `inject_context(core, headers, source: Option<&Value>, body: &mut Value)`.
