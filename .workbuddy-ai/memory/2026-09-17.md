## mercury-2.5 raw tool-call leak in Playground (bug fix)

**Symptom:** Playground chat rendered `<|tool_call_start|> <function=Bash> <parameter=command> mkdir -p /Users/tushershikder/.zcode/skills/...` verbatim when asked to "create a skill" on the mercury-2.5 provider.

**Root cause (3 layers, all app-side — Mercury 2.5 DOES support native tool calling):**
1. `Playground.tsx` `Chat()` sends `{model, messages}` with **no `tools` array and no system prompt**.
2. Router has no tool-calling concept: manifest grammar v1.1 caps at `capabilities: {text, image}`; `tools?: unknown` exists in `TextRequest`/`execution-engine` as opaque passthrough only (commit 06fdfef + uncommitted gateway diff).
3. `Playground.tsx` render dumped `streamed` into a `whitespace-pre-wrap` div — zero parsing, so any pseudo-token a model emits is painted.
The `.zcode/skills/...` path was a **model hallucination** (agent-dir convention from training data), not injected by anything in this repo.

**Fix applied:**
- NEW `apps/desktop/src/lib/assistant-stream.ts` — parses assistant output into `text` / `tool` segments. Streaming-safe (unterminated block → `complete: false`, hidden until the end marker arrives); holds back half-typed markers; lossless (keeps `raw`).
- Gotcha found while testing: mercury emits `<parameter=name>value` with **no `</parameter>`** — value runs to the next `<parameter=` or end of block. Parser must not require a closing tag.
- `Playground.tsx` — added `AssistantContent` + `ToolCallChip`; tool blocks render as an inert labelled card ("tool call (not executed)"), prose renders clean.
- `vitest.config.ts` — include widened to `src/**/*.test.ts` (was `e2e/**` only).
- NEW `apps/desktop/src/lib/assistant-stream.test.ts` — 8 tests, all pass; `tsc --noEmit` clean.

**Not done (open decision):** real tool execution. Would need a tool-capability flag in the manifest grammar (`{text, image, tools}`), a tool registry, and an execution loop. Also optional: a Playground system prompt telling the model no tools exist (prevents the hallucination at source, but changes request semantics for a diagnostic console — left out pending user call).

## Follow-up: full audit + tool-calling plumbing (same day)

User asked for a full audit then "fix all issues". Audit found 3 deeper breaks behind the symptom:

1. **`ModelRouter.generateText` silently DROPPED `tools` / `toolChoice` / `responseFormat`** — they existed on `TextRequest` but were never passed to `engine.executeText`. Fixed.
2. **`builtin-templates` never declared `tools`/`tool_choice`/`response_format`** in `requestTemplate`, so `renderTemplate` omitted them regardless. Added as `{{x?}}` (omit, not null). **Also had to add them to `REQUEST_FIELD_WHITELIST`** in `packages/adapter-spec/src/manifest.ts` — the lint (invariant 4) rejected the built-in template until I did; 2 router-core tests failed until then.

Added optional `toolCalls` selector to `chunkMap` + `responseMap` (grammar v1.1 amendment) and an `onToolCall` side channel on `TextRequest`. Streaming `arguments` arrive in fragments keyed by `index` → reassembled in a `Map`, flushed in a `finally` so every early-return path reports.

Other fixes: Playground no longer replays empty assistant turns left by Stop/failure (providers 400 on `{role:"assistant",content:""}`); Playground now sends a no-tools system turn (checkbox, default on) to stop the hallucination at source. Removed dead exports `hasToolCallSyntax` from assistant-stream.

**Deferred:** anthropic-compat can't report *streamed* tool calls (`content_block_start` + `input_json_delta` isn't expressible in the v1.1 chunkMap grammar). Non-stream works on both dialects.
