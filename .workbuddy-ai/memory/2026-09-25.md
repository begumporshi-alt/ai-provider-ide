## Increment 25j — the builtin profiles, and D41's second facet

Took the recommendation: **close D41** — the missing `PROVIDER_PROFILES[slug]` branch in `core::activation`.
Chosen over Phase 6 because it is reachable by an ordinary UI action (`Providers.tsx:298` creates a builtin
provider), while Phase 6 is UI-heavy and would be built against a release pipeline still blocked on the Apple
Developer Program.

**The reference's loop, `store.ts:367-381.** Runs **over providers**; for each one tries
`PROVIDER_PROFILES[p.slug]` **first**, registering `withBaseUrl(profile(), p.baseUrl)` and `continue`ing, only
then falling back to that provider's active manifest row (from `manifests_active`). The old Rust iterated
*manifest rows*.

**Two facets — D41 recorded only the first.**

1. **A builtin provider with no manifest row went unregistered.** Reachable: `addProvider` writes the provider
   row (`store.ts:495`) **before** the manifest row (`:497-502`), and its `catch` rolls back in-memory state
   only (`adapters.unregister` + `refreshFromHost`). Nothing deletes the provider row — so a failure between the
   two writes leaves a row-less provider permanently.
2. **A builtin provider *with* a row was served the stale one.** The row is written once, at creation, with
   `version: 1`; nothing re-seeds it on upgrade (no migration, no boot path rewrites a `builtin-template` row).
   The reference ignores that row for a builtin slug and serves the *current* profile. **Facet 2 needs no
   failure — only a second release.** This is the facet the register did not state, and it is the broader one.

**`core/builtin_templates.rs` (new, 9 tests).** `openai_compat(base_url, extras)`, `anthropic_compat(base_url)`,
`provider_profile(slug, base_url)`, `PROFILE_SLUGS`. The base URL is a **parameter** — `withBaseUrl` composed
rather than applied. Consequences: (a) the profile path dials `providers.base_url`, the column `recompute_allow`
derives the allowlist from, so **a builtin provider cannot trip D46**; (b) the pinned default URLs are *not*
duplicated in Rust — nothing consumes them, and a copy would be a second answer to "where does OpenRouter live".

**Details that cost care.**
- **The slug is the key, not `type`.** `store.ts:368` is `PROVIDER_PROFILES[p.slug]`. Keying on `type` would have
  diverged in the other direction, invisibly, for the same reason this one was.
- **An omitted key is not a null one.** `opencode` passes `{ imageEndpoint: false }`, so
  `headers: extra?.textHeaders` is `undefined` and `JSON.stringify` drops it. Emitting `"headers": null` would
  produce a manifest the reference never generates. Same for `modalityRules`.
- `BUILTIN_TEMPLATES` was deliberately **not** ported — its two callers (`adapter-generator.ts`,
  `fingerprinter.ts`) are both TypeScript, so the id enum would have no Rust selector.
- `PROFILE_SLUGS` is exported **so a test can walk every profile**; a test using only `openrouter` would pass
  with the `b.ai` arm dropped.

**Activation now iterates providers.** `Skipped.version` → `Option<i64>` (`None` = no row involved, not a `0`
sentinel). Both log consumers updated (`aiproviderd.rs`, `tauri/gateway_cmds.rs`).

**One additive divergence:** a provider with neither a profile nor a row is **reported**, naming the slug and the
write order. The reference is silent there — and that silence is what hid D41; the symptom arrives later from
`adapter_runtime` as `no active manifest for provider …`.

**Four probes, one at a time.**
- Remove the profile branch → reddens the **5** profile tests **alone**.
- `provider_profile` ignores its `base_url` argument → reddens **8** across both modules.
- Remove the no-row report → reddens its own test **alone**.
- Invert precedence (row first) → reddens the 2 tests that are about precedence. **2 further failures there were
  artefacts of the probe's own simplified row path, not of precedence** — recorded as such rather than claimed.

**Measured:** lib **1181 → 1197** (9 new module + 7 activation), binary 5 → 5. fmt clean, clippy
`--all-targets -D warnings` clean, `--no-default-features --all-targets` clean, check-doc-links 51 files / 127
links, book **745.9 KB** / 204 ids, `data-page-node-id` 0. D41 → **Closed**.

## Increment 25k — one authority for "which manifest serves this provider" (D49)

**The stated rationale was false.** The recommendation was "seed builtin providers at boot, or the port will drift
again on the next template change". That drift was already closed: 25j made activation read the *profile*, not the
row, so serving no longer diverged. What *did* diverge was the second consumer: `workbuddy::tool_support` still read
the row, so a builtin provider was **served** by its current profile and **reported on** from its snapshot row — two
answers to one question, produced by one increment (**D49**).

**`activation::serving_manifest` is the one function.** Takes `(slug, base_url, Option<(body_json, version)>)` and
returns `Result<Option<Serving>, UnreadableRow>`. Both `register_provider` and `tool_support` read it. `Serving`
carries `body: Value` and `version: Option<i64>` — `None` for a profile (no row), `Some` for a row so a failure can
name which one. `UnreadableRow` carries `version` and `detail` so the parse error is reported with its version.

**`tool_support` now outer-joins `manifests`.** The join is load-bearing: a builtin provider may have no row and still
be served by its profile. An inner join would answer "unknown" → false for a provider that is serving and forwarding
tools right now.

**`manifest_forwards_tools` now takes `&Value`.** Re-serializing after `serving_manifest` returns a `Value` would be a
second parse for no reason.

**Four tests, four claims.** `a_builtin_provider_reports_tool_support_from_its_profile_not_its_row` (row has no
`tools`, so `true` can only come from the profile). `a_builtin_provider_with_no_manifest_row_still_reports_tool_support`
(outer join is load-bearing). `a_provider_without_a_profile_still_answers_from_its_row_in_both_directions` (fix is
not "builtins are always true"). `a_row_that_is_not_json_is_unknown_rather_than_either_answer` (corrupt row → None).

**Three probes, one at a time.** Remove profile branch from `serving_manifest` → reddens the 2 new builtin tests + 5
existing D41 tests **alone**. Change outer join to inner → reddens the no-row test **alone**. Make
`manifest_forwards_tools` always `true` → reddens the negative-direction test + the existing predicate test **alone**.

**Measured:** lib **1197 → 1201** (4 new in `workbuddy.rs`), binary 5 → 5. fmt clean, clippy
`--all-targets -D warnings` clean, `--no-default-features --all-targets` clean, check-doc-links 52 files / 127 links,
book **749.9 KB** / 204 ids, `data-page-node-id` 0. D41 register line updated with D49 note.

## Increment 26a — the launchd LaunchAgent (Phase 6 step 1)

Took the LaunchAgent over the other three Phase 6 steps; Tushu also deferred §10 decision 2 (pure HTTP vs
hybrid) until the service actually exists.

**What Phases 1–5 did not do, and the distinction that picked this step.** They made the gateway a Rust service
that needs no webview. None let it outlive the app *process* — `Cmd+Q` still takes the gateway with it, because
the only thing that ever started it was the app. `core/service.rs` is the other half.

**`core/service.rs` (new, 15 tests) + `tauri/service_cmds.rs` (3 commands) + `web-test/shim.ts` cases.** The
binary is copied out of the bundle to `{data_dir}/bin/aiproviderd`, which is the risk register's own preferred
remedy (a plist pointing inside the `.app` breaks on every versioned or atomic swap, and `KeepAlive`
*throttles* on repeated failed execs rather than healing).

**Two measurements that changed the shape of the work.**
- `tauri build` **does** put `aiproviderd` in `Contents/MacOS/` (measured 4,454,336 B in
  `target/release/bundle/macos`) — but the copy in `/Applications` has only the app binary, so the installed app
  would have nothing to install from. The bundled one is the **default-features** build: the Tauri-free release
  binary is 4,073,968 B, 380 KB smaller. Recorded, not closed.
- The status page's Tests row had stopped at **25d / 1182** while reality was **1201** — stale by 19. Logged as
  **D50**, and 25e–25i are folded rather than itemised because their deltas were never recorded and reconstructing
  them would be a guess.

**Deliberately inert.** With `RunAtLoad` set, the agent and the app both bind the same persisted port, so
installing it is a **bind conflict, not a handover**, until Phase 6 step 3 lands. Nothing calls `install` in
production. Said in the module header, the increment note and the commit — three places, because it is the kind
of caveat that gets read as a footnote.

**No `cfg(target_os)` gate**, against the obvious instinct: a gated module is a module no non-macOS build ever
compiles, which is D17's blind spot. Only `read_uid` and `run_launchctl` name the outside world, so all 15 tests
run on all three CI platforms.

**One `&impl Fn` seam.** An earlier draft used `type Runner = dyn Fn(...)`; in a type alias `dyn Trait` defaults
to `+ 'static`, so every test closure borrowing a local failed `E0373`. `&impl Fn` has no such bound.

**Three probes, one at a time, each reverted.** Drop `RunAtLoad` → reddens its own test alone. Swap `bootout`
after `bootstrap` → reddens the ordering test alone. Break `parse_pid` → reddens the pid test alone, leaving the
"loaded but not up" and "launchd does not have it" tests green, which is what separates the three status states.

**Measured:** lib **1201 → 1216**, binary 5 → 5, headless run **1122 → 1152**. fmt / clippy
`--all-targets -D warnings` / `--no-default-features --all-targets` / tsc / check-doc-links 52 files 127 links /

### 26a live run — the last mile is unreachable from a CLI (committed `4636bfc`)

A temporary `tests/launchd_live.rs` probe (deleted after the run) drove the **real** `service::install` against
the real `launchctl`. What it proved: the generated plist is accepted by `plutil -lint` (OK, 779 B); `fs::copy`
preserves the executable bit so no `chmod` is needed; the failure path names the domain and launchctl's own
message.

**What it did not prove: that the job ever runs.** `bootstrap` returned **error 5 (EIO)**. Diagnosis, all
measured: `launchctl list` → **0 lines** in this context, while `launchctl print gui/501` shows the domain alive
(`type = login`, `creator = loginwindow[171]`, 410 services). Modern `bootstrap gui/501`, legacy `load -w` and
`bootstrap user/501` **all** fail identically → the caller's **session**, not the plist, the domain or the verb.
Ruled out one at a time: the sandbox (fails with `dangerouslyDisableSandbox` too, and `log` proves unsandboxed
mode was genuinely in effect — it stopped saying "Cannot run while sandboxed"), a malformed plist, and the
`com.apple.provenance` xattr on both the plist and the binary.

**Conclusion:** evidence about the *environment*, not the module. A CLI is not a process that may mutate
`gui/<uid>`; the Tauri app is, by construction. So 26a's end-to-end claim stays **unverified** until something
with an Aqua session calls `install` — i.e. **26b's UI control**, now named as the debt in §12.

**Dead ends, so nobody re-walks them:** `open -a Terminal <script>` fails with `-10820`; even unsandboxed, the
`.command` variant produced no output; `osascript … tell application "Terminal"` hangs on an automation
permission prompt. Do not try to reach a GUI session that way.

Left clean: no plist, no copied binary, no job in `gui/501`; temp probe and `/tmp` scripts removed.

## Increment 26c — §10 decision 2 settled + CORS middleware (Phase 6 step 5)

**Decision settled: pure HTTP.** §10 decision 2 ("pure HTTP vs hybrid HTTP+IPC") is resolved as **pure HTTP**.
Recorded in three places: the decision entry in `10-headless-service.md` §10, an entry in `DECISIONS.md`,
and the "Next action" line rewritten. Six reasons, each grounded in the project's own documented hazards
(see the decision entry for the full list). The Tauri app shell retains only platform APIs (window, tray,
dialogs, keychain); all data access goes through `fetch()`.

**CORS middleware** (Phase 6 step 5, prerequisite for step 4). `cors_headers` in `core/gateway.rs`:
- `OPTIONS` preflight answered 204 with CORS headers before any route or auth check — preflight carries
  no credentials and must not be gated by `check_gateway_key`.
- Allowed origins: `tauri://localhost`, `http://localhost*`, `http://127.0.0.1*`. External clients

- `ACCESS_CONTROL_ALLOW_HEADERS` includes all gateway auth headers: `Authorization`, `Content-Type`,
  `x-api-key`, `x-goog-api-key`, `AIP-Agent`, `AIP-Memory`.
- Registered as the outermost layer (after `ensure_retry_after`), so CORS headers are on every response
  including 429s.

**6 tests** in `gateway_tests.rs`: tauri origin allowed, dev server origin allowed, 127.0.0.1 origin
allowed, non-local origin rejected, no-origin (external client) unaffected, auth headers included.

## Increment 26d — the §5.3 admin routes (Phase 6 step 4, Rust half)

**`core/gateway_admin.rs`, a `#[path]` submodule of `gateway.rs`** — declared as a *child*, like
`gateway_handlers`, so it reaches `check_gateway_key` / `peer_ip` / `err` / `openai_error` without
widening those four to `pub(crate)`. (First attempt declared it in `core/mod.rs`; the four
E0603s are what forced the choice, and the child shape is the better one anyway.) Registered in
`spawn`, so the in-app gateway and `aiproviderd` serve the identical surface.

**Six routes:** `GET/POST /admin/settings`, `GET/POST /admin/keys`, `DELETE /admin/keys/{id}`,
`GET /admin/spend`.

**Three deliberate departures from a literal port of the commands.**
1. **The settings write merges, server-side.** The IPC path merged in TypeScript
   (`patchGatewaySettings`) because `settings_set` is a whole-row UPSERT. Moving the merge here
   makes it atomic instead of a read-modify-write across the network.
2. **`POST /admin/keys` returns the secret once.** The IPC command copied it to the clipboard and
   returned metadata only. A headless process has no clipboard; returning it is one behaviour for
   both cases and keeps the clipboard a UI concern.
3. **No store → 503 naming the route**, not an empty list that reads as "nothing configured".

**9 tests.** Auth (401, one fresh server per route), the 503, settings read/merge/refuse-non-object,
empty keys list, missing-label 400, spend shape (camelCase asserted — `store.ts` reads `monthMicros`).

**Two things measured that were not assumed.**
- **Auth failures back off.** Six unauthenticated requests against one core do **not** produce six
  401s: the first failure locks the peer IP for 500 ms with exponential backoff, so the rest are
  429. Caught by a test written the wrong way; pinned as its own test.
- **The happy path of `POST /admin/keys` is not tested.** `vault::put` hits the real OS keychain,
  which CI has no access to. Only the validation path is pinned. Stated in the module header and
  §5.3 rather than left implied.

**clippy `result_large_err`** on the two guard helpers returning `Result<_, Response>` — an axum
`Response` is large. Fixed by boxing the `Err` variant, not by restructuring.

**Measured:** lib **1222 → 1231** (+9), binary 5 → 5, headless **1158 → 1167** (+9 — the admin
tests run in both configs, which is the point of putting the module in `core/`). fmt, clippy
(both feature configs), check-doc-links 52 / 127 — all clean.

## Increment 26e — scope corrected, the allowlist seam, provider CRUD (Phase 6 step 4)

**The scope correction, measured not guessed.** The production UI calls **107** distinct `invoke`
commands — task 3 had estimated ~15 route groups. Two facts make "port all 107" wrong: `skills_*`
is **documented frontend-only** (MEMORY.md: "skills are frontend-only, gateway blind to them"), and
~34 more are *about the app* rather than the gateway (crash reports, diagnostics bundle, onboarding,
history, config import/export, agent trails, drift, router model context). A headless service has no
UI crash reports to serve. **Decision (Tushu): HTTP serves the gateway + service-owned data (~75);
IPC stays for app-owned UI state (~34).** This is *not* the hybrid rejected in decision 2 — that
kept IPC for **performance** (two spellings of one fact); this keeps it for **ownership** (one
authority per fact). Recorded in §10 decision 2 and DECISIONS.md.

**The allowlist seam — the finding that shaped the work.** `GatewayCore` had **no** reference to
`EgressState`/`AllowList`, but `provider_upsert`/`provider_delete` must keep the allowlist in step
with `providers.base_url`. A provider written over HTTP without that gets a row the gateway refuses
to dial — **D46 created by the CRUD path**. `recompute_allow`/`sync_allow_for_provider` used only
`egress.allow`, so both were changed to take `&AllowList`, and `GatewayCore` gained
`allowlist: Option<Arc<AllowList>>` + `with_allowlist()` (mirroring `with_store`). The headless
binary attaches it at boot; before this it computed the list once and *had no CRUD path at all*
(`aiproviderd.rs:137` says so).

**Config writes are all `#[cfg(feature = "app")]` gated** — they take Tauri `State`, so they do not
exist in the headless build the routes must serve. Fixed by extracting store-only cores
(`provider_upsert_row`, `provider_delete_row`) and having the gated commands delegate — the same
shape `providers_rows`/`providers_list` already used. `provider_delete_row` **returns** the keychain
accounts rather than deleting them, so the HTTP route does §7 hygiene identically.

**3 routes:** `GET/POST /admin/providers`, `DELETE /admin/providers/{id}`. **3 tests**, and the
allowlist one was **falsified**: removing the sync reddens exactly the 2 allowlist tests, leaving
the empty-list test green.

**Measured:** lib **1231 → 1234** (+3), headless **1167 → 1170** (+3). fmt, clippy (both configs)
clean.

**Remaining for task 3** (same mechanical pattern — extract store-only core, then route):
api-keys, manifests (+ activate), models cache, aliases, ledger read.
