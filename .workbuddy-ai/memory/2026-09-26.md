## Increment 26aa — Start's handover gets an undo, and the EIO that is not a defect (14:55)

**Naming note:** this first went in as "26z", which was already taken by the earlier
`launchd_live` label-collision entry above. Increment labels live in **two** places — this log and
`docs/dev-book/` — and the check for a free one has to cover both.

**Found by the operator in the first minute of real use.** Clicking **Start** with the app gateway
running turned the gateway off and *then* failed:

```
launchctl bootstrap gui/501 /Users/…/dev.aiprovider.router.plist failed (5): Bootstrap failed: 5: Input/output error
```

leaving the app gateway **off and** no service — nothing serving, worse than either state Start was
pressed from.

**The real defect (D63).** 26y's handover is destructive-first by necessity — the service cannot bind
while the app holds the port — but it shipped with **no undo**. `serviceAction` now takes
`{ run, undo }` and runs the undo when the action throws *after* `run` succeeded. Start undoes with
`gateway_enable` (runtime-only, symmetric with `gateway_disable`) and **not** `toggle(true)`, which
would persist an `enabled: true` the handover never changed. A failed undo is reported *alongside*
the original error rather than replacing it.

**Why the suite missed it:** the spec asserted `["gateway_disable", "service_start"]` — an assertion
that **stops at the failure**, so it could not see what followed. The class is D55's one level out:
D55 was a fixture asserting a non-load-bearing invariant; here the *assertion itself* ended exactly
where the defect began. New test asserts the full three-call log, and was **falsified** by neutering
the undo (which reddens it).

**The EIO is not a defect — three measurements, in this order:**
1. A **trivial** plist (`/usr/bin/true`, `plutil -lint: OK`, sharing nothing with the app) bootstrapped
   into the same `gui/501` fails **identically** → rules out the app's plist, its binary and its code
   in one step.
2. The project's own `launchd_live` harness, run from this shell, prints
   `SKIP: no Aqua session in this process` with the identical EIO — and the same two tests **pass**
   from Terminal.app (the 12:50 run).
3. So the domain refuses *every* bootstrap from a process outside a real GUI session. The app under
   test had been started by me from an agent shell (`pnpm dev`), so it inherited exactly that.
   **Operator's fix: launch the app normally.** Nothing to repair in `service.rs`.

**Reusable diagnostic order:** reproduce with a control that shares nothing with the suspect, then
hand the question to an instrument that already distinguishes the two cases — rather than reasoning
about which cause is likelier.

**Also:** `pnpm dev` needs `PATH="$HOME/.cargo/bin:$PATH"`; without it `cargo metadata` fails with
"No such file or directory" and tauri exits immediately.

**Measured:** full browser suite **114 passed / 0 failed** (113 + the new rollback test). The earlier

## Increment 26ab — the handover revoked the UI's credential, and nothing minted it back (15:20)

**Live symptom:** after a successful Start, every admin call from the app answered
`401 {"code":"invalid_api_key","message":"invalid gateway key"}` — e.g. `POST /admin/api-keys`.

**Diagnosis, each step measured rather than inferred:**
1. `lsof` on the port → the listener was **`aiproviderd`** (the agent), not the app. So Start had
   actually **worked** — launched from the operator's own session, exactly as 26aa concluded it must
   be. The 401 was the app's *own* admin calls being rejected by the agent.
2. The secrets file held `masterkey` and two `key:` entries but **no `key:ak-ui`**.
3. `gateway_keys` held **only** `ak-fc85350a2fb1dc67` ("Work buddy") — no `ak-ui` row.
4. `gateway_disable` calls `ui_session::revoke` (`gateway_cmds.rs:296`), and the handover calls
   `gateway_disable`.

**Mechanism.** `uiSessionKey()` caches the credential in a module-level `let` and returns it for the
life of the webview. `clearUiSession()` — whose own comment reads *"Called on gateway stop so the
next start mints a fresh one"* — had **zero call sites** (Grep returns its definition and the test
fake, nothing else). So the credential was revoked host-side, correctly and by design (D51), while
the client went on presenting it. The revoke was never wrong; the re-mint was never wired.

**Why 26y is what exposed it.** `gateway_disable` was previously reachable only by the operator
deliberately switching the Gateway off — rare, and followed by a switch back on that also reads as a
fresh start. 26y made it the **first half of one button press**, so the ordinary act of bringing the
service up began silently invalidating the UI's own credential. D64, and it is **D63's mirror
image**: D63 was a compensating step with no compensation; D64 is a teardown step whose paired setup
was never wired.

**Fix.** `fetchAdmin` retries **once** on a 401 after dropping the cached credential, re-minting
against whichever process now holds the port — the point of `ak-ui` being an ordinary app key. Not a
loop: a second 401 is a real refusal, and re-minting against it would dress a refusal up as a retry.
A non-401 failure is not retried. The tests assert the retry's `Authorization` header **differs**
from the first attempt's — a retry that re-sent the same stale key would satisfy a call count while
fixing nothing — and were **falsified** by disabling the retry, which reddens exactly the two retry
tests.

**Instrument note (again).** `grep 'a\|b'` in bash returned a **false zero** while searching for
`clearUiSession`; BRE `\|` alternation matches nothing. The Grep tool found it at once. The working
memory already records this trap, and it still cost a step — the lesson is that the *first* search
for an absence claim must be the instrument that is known to report presence.

**Measured:** vitest **185** (181 + 4). Rust 1304, browser 114 unchanged.

## Increment 26ac — the 429 the retry didn't cover, and the boot screen's destructive advice (15:30)

**Live symptoms (three, in sequence).** After 26ab's 401 fix: `POST /admin/api-keys` → 401 (resolved
by 26ab). Then on next boot: `GET /admin/api-keys` → **429 too many failed auth attempts — backing
off**, and the boot screen displayed its unconditional *"restore from the newest dated backup"* line
for a transient rate limit.

**Diagnosis.** The 429 is a **consequence of the 401 storm**, not an independent fault. The
brute-force backoff is checked *after* the key match (`core/gateway.rs:1487`), so a valid credential
never reaches it — pinned by `r4_valid_key_not_throttled_by_another_callers_failures`. A 429
therefore means the credential was *still* bad. 26ab's retry covered 401 but **not** 429, so the
first poll after the re-mint presented the new key, the server matched it and cleared the window —
but only if the retry was triggered by the *first* 429. Without 429 in the retry condition, the app
locked itself out for the backoff duration (caps at 32 s).

**Fix.** Two parts:
1. `gateway-client.ts:116`: retry condition extended from `res.status === 401` to
   `(res.status === 401 || res.status === 429)`.
2. `boot-failure.ts` (new): `bootFailureHint(error)` chooses advice from the error string —
   429 → "reload, the backoff clears by itself"; 401 → "reload mints a fresh credential";
   5xx → "check the log"; no listener → "the gateway did not answer"; unknown → backup advice,
   now **hedged** rather than asserted. Wired into `App.tsx:77`.

**Tests.** Two new in `gateway-client.test.ts` (429 retry + second-429 no-retry), five in
`boot-failure.test.ts` (one per branch + hedged fallback). 429 branch **falsified**: disabling it
reddened both 429 tests, 401 and 500 tests stayed green.

## Increment 26ad — the launchd error now says what it means (16:00)

Pays the debt 26aa filed: *"the card surfaces `Bootstrap failed: 5: Input/output error` verbatim."*

**Two measurements changed the shape of the fix.**
1. **"Map status 5" is the wrong key.** launchctl *exits* 5, and launchd separately embeds **its own**
   status code inside the message (`Bootstrap failed: **5**: …`). The same number appears twice meaning
   two different things → key on the **pair** (exit status **and** message text), not the number.
2. **The verbatim problem was never confined to `bootstrap`.** Live `launchctl bootout gui/501/<label>`
   of a job launchd doesn't hold → exit **3** `No such process`, not 5. A mapping keyed on 5 alone would
   have left `stop`'s most common failure just as opaque.

**A fixture was pinning a shape launchctl cannot produce.** `a_stop_launchd_refuses_…` used
`(5, "Bootout failed: 5: Input/output error")` — copied from the `bootstrap` fixture above it. Green
against a shape the tool cannot emit; it could not have caught *any* real `bootout` failure. D61's
instrument class in a new place: not "an instrument that cannot report presence" but "a fixture
asserting a property of a fabricated input".

**Design.** One `describe_failure(what, out)` at all three sites (`service.rs:351/419/444`). Note is
**appended, never substituted** (a wrong cause is discountable; a dropped raw message is not) and
**hedged** — "Most common cause: this process has no GUI session (Aqua)" — because the cause was
established by *excluding* alternatives (trivial plist failed identically; `launchd_live` printed
`SKIP: no Aqua session`), not by observing a success under it.

**Falsification, both directions.** Disabling the note reddened the 3 positive assertions and left the
2 negative ones **green** — which is exactly why the negative tests needed their own probe: **an absence
assertion passes trivially when the thing is absent for the wrong reason.** Making the note unconditional
reddened both. **My first attempt at that probe was worthless**: it returned `"PROBE"`, which does not
contain the substrings the negative tests assert on, so it could not have failed them. Lesson:
**a probe must be built to fail the assertion it targets**, not merely to differ from the correct code.

## Increment 26ae — the app could not authenticate to its own service (17:50)

**Context.** Full write-up in `10-headless-service.md` and D67; committed and pushed this session.
The app's admin calls answered `401 invalid gateway key` against the service it had just started, and
the 401 storm behind that is what turned the next boot into the `429` that 26ac had only made
*legible*.

**Two per-process caches, one layer apart.**
1. `vault::load` was `static LOADED: Once` — *"Runs once per process."* 26y moved the listener into a
   second process, so the app minted `gwkey:ak-ui` into a file `aiproviderd` had already snapshotted;
   the service was asked to honour a credential it did not hold. It failed in the **worse** direction
   too: a *revoked* credential kept authenticating in any process that had loaded it, so
   `ui_session::revoke` did not do what its comment promises.
2. `AppKeyCache` keyed on the active **id set**, but `ak-ui` is re-minted *under the same id*
   (`ui_session` deletes the row, inserts a fresh one), so a rotation left the fingerprint identical
   and the memo served the pre-rotation secret for its full 60 s TTL.

**Fix.** `load` re-reads on the file's `(mtime, len)` stamp, replacing rather than merging (`save`
writes the whole map; a merge would resurrect an account another process deleted). The memo keys on

### Researched direction (2026-09-26) — what robust gateways do, and the revision it forced

Sources: tianpan.co *Tail-Tolerant Retry Policy Your LLM Gateway Doesn't Have* (2026-05-02);
`docs.llmgateway.io/features/routing`; the Google-SRE hedged-request literature.

**It revises my own 27b-era advice.** I had proposed "raise `FIRST_MSG_TIMEOUT` to 60 s + one
retry". The field does something better: **hedge at p95 rather than retry after failure** —
latency is `min(primary, hedge)`, not `primary + hedge`. On this gateway's own numbers (p95 11.0 s,
p99 19.0 s, max 113 s) a duplicate fired at ~11 s would have covered both the 30 s abandonment and
the 113 s tail. Published non-LLM figure: P99 64 ms → 17 ms at ~9 % extra load.

Patterns worth adopting, in order:
1. **TTFT must be the first *content* byte.** `Slot::recv` (`gateway.rs:1333`) sets `started = true`
   on *any* message and an empty liveness delta counts (`gateway_handlers.rs:107-110`), so a probe
   disarms the 30 s bound — that is the only reason row 1590 survived 113 s. Same class of bug the
   literature warns about (measuring on header receipt, not first body byte).
2. **Hedge at p95, rate-limited to 5–10 % of traffic** (token bucket), or a provider outage makes
   every primary slow and every hedge fire, doubling load on the degraded provider.
3. **Three deadlines**: end-to-end, streaming, non-streaming. This gateway has **no end-to-end
   deadline** — the idle timeout bounds silence, not duration.
4. **Classify before retrying; timeouts get their own budget.** For LLMs a timeout is the *modal*
   failure, not an exception. `NETWORK`/`CANCELLED` do not separate it.
5. **Parallel cross-provider failover**, not sequential. LLMGateway: 60-min time-decayed window
   (1 min ×10, 5 min ×3, rest ×1), reroute below 90 % uptime, hard switch below 85 %, ≤2 retries,
   1 % epsilon-greedy exploration.
6. **Sticky sessions** for upstream prompt-cache warmth — and sticky requests deliberately *skip*
   the retry loop. Material here: prompts run 63–73 k tokens.
7. **Measure latency twice** — user-visible with retries vs model latency without; the gap is the
   cost of the retry policy.

**Caveats to carry:** a lost hedge is still billed for input tokens; hedging needs idempotency for
side-effecting calls; and with **one provider** a hedge only helps if the failures are independent
— measure that before assuming it. Do not copy LLMGateway's 1.5 M ms end-to-end default; it is a
ceiling for long jobs, not a UX target.

### Correction (appended 2026-09-27) — the disarm mechanism was mis-cited

Lines 875-877 and 908-910 above attribute the disarmed 30 s bound to
`gateway_handlers.rs:107-110`. **That file cannot disarm it.** Re-read of both files:

- `gateway_handlers.rs` holds its **own** local `started` (line 103) whose only job is the SSE

### Increment 28 (2026-09-26 23:10-23:23) — the retry was unreachable, not missing

**Root cause of row 1600 is bound misalignment between two layers, not a missing retry.**
`egress.rs` bounded **both** the wait for response headers and each wait for a chunk by the same
`state.idle_timeout` (= `UPSTREAM_IDLE_TIMEOUT`, 120s). But the gateway's `FIRST_MSG_TIMEOUT`

`bridge.cancel`. So a pre-headers stall was aborted by the *gateway* 90s before the egress layer
would have noticed, and `UPSTREAM_STALL_RETRIES` (27b) — written for exactly that stall — **could
never fire in production**.

**The proof is an absence, and it is decisive:** row 1600 ran on the rebuilt 27b binary and left
**no `connection stalled` line in any log**, because the pre-headers bound was never reached. The
stall instrumentation existed; nothing could reach it.

**Fix (increment 28):**
- `const UPSTREAM_HEADER_TIMEOUT = 10s` — the pre-headers budget, split from the 120s streaming
  budget. `stream` now uses `state.header_timeout` at the `b.send()` site and leaves
  `state.idle_timeout` on the chunk read. Worst case `2 x 10s = 20s < 30s`, leaving 10s headroom.
- New field `EgressState::header_timeout` (a field for the same reason `idle_timeout` is one — the
  test needs to shrink it; the test seam sets both to `TEST_IDLE`).
- The pre-headers warn/message now report `header_secs`, not `idle_secs` — it previously named a
  number **12x** the one that had actually expired.
- `Slot` gained `started_at: Option<Instant>`, stamped on the **first poll** (not at construction,
  since `try_slot` may wait for a routing permit), and `Slot::recv` logs `first_msg_ms` when the
  first message arrives. **This is the only record of time-to-first-message the system has** — the
  ledger stores total duration only, which is why the bound could never be calibrated.

**New regression test:** `the_stall_budget_fits_inside_the_gateway_bound` asserts
`(UPSTREAM_STALL_RETRIES + 1) * UPSTREAM_HEADER_TIMEOUT < FIRST_MSG_TIMEOUT`. **Falsified before

## Correction 3 — the `PARSE_ERROR` rows are *not* misrecorded successes (falsified 2026-09-27)

The claim above — "the ledger records *successful* requests as `PARSE_ERROR`" — is **falsified**. It
rested on row 1601 carrying `tokens_out=8` while the client saw a 200 + `[DONE]`. Both observations
are true; the inference is not. **A 200 carrying no content is not a success.**

Reproduced directly against the upstream with a live key:

```
max_tokens: 16  -> reasoning_tokens: 16, text_tokens: 0,  finish_reason: "length"
max_tokens: 200 -> reasoning_tokens: 61, text_tokens: 11, finish_reason: "stop"
```

`agnes-2.5-flash` is a **reasoning model**: it streams `delta.reasoning_content` first, and the
router ignores those frames. At `max_tokens: 16` the budget is spent entirely on reasoning, so
`text_tokens: 0` and no `delta.content` ever arrives. `emitted == 0` was therefore **accurate** and
`PARSE_ERROR` was the **correct** class. The probe was self-defeating — it manufactured the very
condition it was meant to detect. Real traffic runs 63–73 k tokens and clears the reasoning phase.
(Probe trap: the opener frame carries `"content":""`, so `grep -c '"content"'` returns 1 on a stream
that produced no text at all.)

**The generalisation is unsupported, not merely unproven.** The 140 `PARSE_ERROR` rows are not
homogeneous: `tokens_out` ranges 1–325 (75 rows ≤ 32, but rows 877/844/1461 carry 325/172/152).
Reasoning starvation explains the small-output rows; it does **not** account for the rest. The
ledger has no reasoning-vs-text split, so the class **cannot be partitioned** from it.

**What replaces it — a structural attribution gap.** All 140 rows carry `provider_id IS NULL`,
`key_id IS NULL` **and** `fallback_chain_json = '[]'`. This is by construction, not accident:
`write_text_ledger`'s drained-nothing arm (`Ok(success)`, `router.rs:900`) builds a bare
`ledger_row(...)` and passes `served = None`, and the common tail sets `provider_id = served.map(...)`
(`:945`). The source's own comment defends it — "a null provider on an error row is itself the
signal that nothing served at all" — but that folds two different states into one: *no candidate was
reached* and *a candidate was reached and answered with nothing*. `advance_cursor` also runs on the
success path only, so a key that reliably yields empty content is **neither rotated away nor named**.

**Consequence:** a request failing this way leaves no record of which provider or key produced it.
Provider health cannot be computed for this class, so circuit breaking stays deferred — for a
sharper reason than the original: not "the rows are false positives" but "the rows are
unattributable and heterogeneous".

### The dominant class is a *rate* limit, not a quota wall

`RATE_LIMITED` = 189 rows, **176 on 09-22 alone**, clustered at 05:00–07:00 and 15:00. Proof it is
rate-based and transient rather than exhaustion:

```
hour   ok   rate_limited
05     60   120      <- 60 requests SUCCEEDED inside the failing hour
06      9    32
07     19    16
10-14   0     0      <- clean
15     29     8
16     71     0
```

Capacity existed in the same hour. The router failed those requests anyway because it **never
waits**: 169 of 189 rate-limited rows completed in **<0.5 s**, and `retry_after_ms` is **absent from
every one** — agnes sends no `Retry-After` on 429, so the router has no number to wait on and cools
the key by `COOLDOWN_FLOOR_MS` instead, failing the request immediately.

### A second key does not fix it

8 rows tried more than one key; **8 of 8 had every attempt rate-limited**. Two different keys, same
429, same moment — the limit is **account-scoped**. The other 181 tried only one key because the
other was already in cooldown. **`Key-02` buys no rate headroom on the same agnes account.**

### Implications for the roadmap

1. **Bounded backoff-and-retry on 429 is the highest-leverage fix** — it targets the largest class by
   a wide margin, and the interleaving proves the retry would usually have succeeded. **The wait
   budget must fit inside `FIRST_MSG_TIMEOUT` (30 s)** — the same cross-layer bound-ordering invariant
   as increment 28, and the new test must pin it the same way.
2. **A second *provider* is the only fix for availability**; a second key is not. It would also turn
   RATE_LIMITED into a routable-away condition.
3. **Instrumentation is the prerequisite for everything after that** — fill `provider_id`/`key_id` on
   the drained-nothing arm (`TextSuccess.candidate` **is** populated even when `emitted == 0`, so the
   data is already in hand; `router.rs:900` discards it), and write `last_used_at` so key health is
   observable at all.
4. **Boot-snapshot staleness** — small, removes an operator trap.
5. **Still deferred:** circuit breaking (needs attribution first), hedging (needs TTFT), sticky
   sessions (irrelevant).

**Also unmeasured: the host.** The gateway is a single launchd process on a laptop. If the machine
sleeps, no amount of provider redundancy helps. Size that before buying redundancy.

## Correction 5 — the "account-scoped 429" claim is withdrawn (2026-09-27)

I wrote above that a second key adds no 429 headroom because the limit is account-scoped, citing
"8/8 multi-key attempts all rate-limited". **Withdrawn, on two grounds.**

1. **The evidence is one 26-second window.** Rows 1397–1403 are 15:02:15–15:02:28 and 1407 is
   15:04:39 on 09-22, using key labels `key-01`/`Key-02` that belonged to keys **no longer in
   `api_keys`** (both current keys were added 09-26). I generalised from a dead key pair to the
   current one.
2. **The observation cannot distinguish the hypotheses.** A burst fast enough to trip one account
   trips both, whether the limit is account- or key-scoped — both hypotheses predict "both keys 429
   at the same instant". 8/8 was therefore **non-discriminating**, not confirming. The instrument was
   never calibrated to separate the two.

The user has since confirmed `Key-02` is a **separate agnes account**, so rotation across accounts
*does* add headroom. What the same data does support is the mechanism below.

## The real mechanism — a 1-second cooldown converted into a hard outage

`COOLDOWN_FLOOR_MS = 1000` (`engine.rs:70`), and agnes sends **no `Retry-After`**, so
`retry_after_ms` is `None` and `record_result` sets `cooldown_until_ms = now + 1000`. Then
`is_key_usable` returns `false` for that key (`engine.rs:1184`), `order_keys` retains it away
(`planner.rs:314`), `plan.is_empty()` is true, and the text path calls `record_no_route` and returns
`Err(NoRoute)` **without attempting anything** (`router.rs:759-764`).

Measured consequence, 09-22 hour 05:

```
hour   ok   rate_limited   no_route
05     60   120            28
```

All **36** `NO_ROUTE` rows carry an empty chain and 0–3 ms latency — nothing was tried. **31 of the
36 fall on 09-22**, the same day as 176 of the 189 `RATE_LIMITED` rows. A burst trips both keys →
both cooled for 1 s → every request arriving inside that second gets an instant hard failure.

**A 1-second cooldown that produces an instant hard failure is strictly worse than waiting the
second out.** The gateway bound is 30 s; the entire cooldown is 1 s.

**Revised priority:** (1) when the plan is empty *because of cooldown*, wait out the earliest expiry
and retry, bounded — instead of `NO_ROUTE`; (2) bounded retry on 429 within `FIRST_MSG_TIMEOUT`,
pinned by the same bound-ordering test. Both are small, and (1) targets rows that currently fail in
**under 3 ms**.
