## Increment 25j — the builtin profiles, and D41's second facet

Took the recommendation: **close D41** — the missing `PROVIDER_PROFILES[slug]` branch in `core::activation`.
Chosen over Phase 6 because it is reachable by an ordinary UI action (`Providers.tsx:298` creates a builtin
provider), while Phase 6 is UI-heavy and would be built against a release pipeline still blocked on the Apple
Developer Program.

**The reference's loop, `store.ts:367-381.** Runs **over providers**; for each one tries
`PROVIDER_PROFILES[p.slug]` **first**, registering `withBaseUrl(profile(), p.baseUrl)` and `continue`ing, only
then falling back to that provider's active manifest row (from `manifests_active`). The old Rust iterated
*manifest rows*.

**Two facets — D41 recorded only the first.**

1. **A builtin provider with no manifest row went unregistered.** Reachable: `addProvider` writes the provider
   row (`store.ts:495`) **before** the manifest row (`:497-502`), and its `catch` rolls back in-memory state
   only (`adapters.unregister` + `refreshFromHost`). Nothing deletes the provider row — so a failure between the
   two writes leaves a row-less provider permanently.
2. **A builtin provider *with* a row was served the stale one.** The row is written once, at creation, with
   `version: 1`; nothing re-seeds it on upgrade (no migration, no boot path rewrites a `builtin-template` row).
   The reference ignores that row for a builtin slug and serves the *current* profile. **Facet 2 needs no
   failure — only a second release.** This is the facet the register did not state, and it is the broader one.

**`core/builtin_templates.rs` (new, 9 tests).** `openai_compat(base_url, extras)`, `anthropic_compat(base_url)`,
`provider_profile(slug, base_url)`, `PROFILE_SLUGS`. The base URL is a **parameter** — `withBaseUrl` composed
rather than applied. Consequences: (a) the profile path dials `providers.base_url`, the column `recompute_allow`
derives the allowlist from, so **a builtin provider cannot trip D46**; (b) the pinned default URLs are *not*
duplicated in Rust — nothing consumes them, and a copy would be a second answer to "where does OpenRouter live".

**Details that cost care.**
- **The slug is the key, not `type`.** `store.ts:368` is `PROVIDER_PROFILES[p.slug]`. Keying on `type` would have
  diverged in the other direction, invisibly, for the same reason this one was.
- **An omitted key is not a null one.** `opencode` passes `{ imageEndpoint: false }`, so
  `headers: extra?.textHeaders` is `undefined` and `JSON.stringify` drops it. Emitting `"headers": null` would
  produce a manifest the reference never generates. Same for `modalityRules`.
- `BUILTIN_TEMPLATES` was deliberately **not** ported — its two callers (`adapter-generator.ts`,
  `fingerprinter.ts`) are both TypeScript, so the id enum would have no Rust selector.
- `PROFILE_SLUGS` is exported **so a test can walk every profile**; a test using only `openrouter` would pass
  with the `b.ai` arm dropped.

**Activation now iterates providers.** `Skipped.version` → `Option<i64>` (`None` = no row involved, not a `0`
sentinel). Both log consumers updated (`aiproviderd.rs`, `tauri/gateway_cmds.rs`).

**One additive divergence:** a provider with neither a profile nor a row is **reported**, naming the slug and the
write order. The reference is silent there — and that silence is what hid D41; the symptom arrives later from
`adapter_runtime` as `no active manifest for provider …`.

**Four probes, one at a time.**
- Remove the profile branch → reddens the **5** profile tests **alone**.
- `provider_profile` ignores its `base_url` argument → reddens **8** across both modules.
- Remove the no-row report → reddens its own test **alone**.
- Invert precedence (row first) → reddens the 2 tests that are about precedence. **2 further failures there were
  artefacts of the probe's own simplified row path, not of precedence** — recorded as such rather than claimed.

**Measured:** lib **1181 → 1197** (9 new module + 7 activation), binary 5 → 5. fmt clean, clippy
`--all-targets -D warnings` clean, `--no-default-features --all-targets` clean, check-doc-links 51 files / 127
links, book **745.9 KB** / 204 ids, `data-page-node-id` 0. D41 → **Closed**.

## Increment 25k — one authority for "which manifest serves this provider" (D49)

**The stated rationale was false.** The recommendation was "seed builtin providers at boot, or the port will drift
again on the next template change". That drift was already closed: 25j made activation read the *profile*, not the
row, so serving no longer diverged. What *did* diverge was the second consumer: `workbuddy::tool_support` still read
the row, so a builtin provider was **served** by its current profile and **reported on** from its snapshot row — two
answers to one question, produced by one increment (**D49**).

**`activation::serving_manifest` is the one function.** Takes `(slug, base_url, Option<(body_json, version)>)` and
returns `Result<Option<Serving>, UnreadableRow>`. Both `register_provider` and `tool_support` read it. `Serving`
carries `body: Value` and `version: Option<i64>` — `None` for a profile (no row), `Some` for a row so a failure can
name which one. `UnreadableRow` carries `version` and `detail` so the parse error is reported with its version.

**`tool_support` now outer-joins `manifests`.** The join is load-bearing: a builtin provider may have no row and still
be served by its profile. An inner join would answer "unknown" → false for a provider that is serving and forwarding
tools right now.

**`manifest_forwards_tools` now takes `&Value`.** Re-serializing after `serving_manifest` returns a `Value` would be a
second parse for no reason.

**Four tests, four claims.** `a_builtin_provider_reports_tool_support_from_its_profile_not_its_row` (row has no
`tools`, so `true` can only come from the profile). `a_builtin_provider_with_no_manifest_row_still_reports_tool_support`
(outer join is load-bearing). `a_provider_without_a_profile_still_answers_from_its_row_in_both_directions` (fix is
not "builtins are always true"). `a_row_that_is_not_json_is_unknown_rather_than_either_answer` (corrupt row → None).

**Three probes, one at a time.** Remove profile branch from `serving_manifest` → reddens the 2 new builtin tests + 5
existing D41 tests **alone**. Change outer join to inner → reddens the no-row test **alone**. Make
`manifest_forwards_tools` always `true` → reddens the negative-direction test + the existing predicate test **alone**.

**Measured:** lib **1197 → 1201** (4 new in `workbuddy.rs`), binary 5 → 5. fmt clean, clippy
`--all-targets -D warnings` clean, `--no-default-features --all-targets` clean, check-doc-links 52 files / 127 links,
book **749.9 KB** / 204 ids, `data-page-node-id` 0. D41 register line updated with D49 note.
