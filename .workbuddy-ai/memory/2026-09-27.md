## Increment 29 — the cooldown wait: a 1-second cooldown no longer fails a request

**Deployed and verified.** Built on the diagnosis recorded at the end of `2026-09-26.md` (see
Correction 5 there): `COOLDOWN_FLOOR_MS` is 1000 ms, `agnes` sends **no `Retry-After`**, so a 429
cools its key for exactly one second — and the empty plan that followed was turned into an instant
hard `NO_ROUTE`. 36 such rows, all with an **empty chain and 0–3 ms latency**, 31 of them on
2026-09-22, the same day as 176 of the 189 `RATE_LIMITED` rows.

### What changed

| File | Change |
|---|---|
| `core/engine.rs` | `key_block(key, now) -> Option<KeyBlock>` is now the **one** spelling of "why is this key unusable". `is_key_usable` = `key_block(..).is_none()`; new `key_retry_at` = `Some(until)` **only** for `KeyBlock::Cooling`. |
| `core/planner.rs` | Extracted `servable_carriers` so `build_plan` and the new `earliest_key_retry_at` cannot disagree about who carries the model. New `earliest_key_retry_at` returns the **minimum** cooldown expiry across servable carriers. |
| `core/router.rs` | New `plan_waiting_out_cooldown`, used by **both** the text and image call sites. `COOLDOWN_WAIT_BUDGET_MS = 5_000`. New `tracing::info!` when the wait fires. |

**`None` is the load-bearing answer in both new readers, and it means "do not wait".** It covers
the three cases waiting cannot fix: no carrier at all; a usable key exists; every blocked key is
blocked by a **denied status or an open breaker**, neither of which clears on a clock. A caller that
slept on those would sleep until its own bound killed the request.

**The loop cannot spin**: `key_retry_at` returns a time *strictly greater* than `now`, so every
iteration sleeps ≥ 1 ms. The `wait_ms <= 0` guard is defensive against a backwards wall-clock step,
which would otherwise make the `as u64` cast sleep for years.

## Increment 30 — the auth breaker gets a half-open state

**Deployed and verified, on both request paths.** The last genuinely-open item from increment 29's
note: an open auth breaker had no half-open state. `breaker_open` was cleared *only* by an
`ErrorClass::Ok`, and an open breaker meant the key was **never tried again** — so no `Ok` could ever
arrive to clear it. The exclusion was a latch, not a circuit: a credential rotated back into service,
or an upstream that had a bad five minutes, stayed dead to the router for the life of the process.
Unreachable so far (`AUTH_FAILED` = 3 ledger rows against a threshold of 3), so this is preventive.

### The measurement the fix rests on

`is_retryable_with_next_key` lists `AuthFailed` (`engine.rs:216-223`, pinned at `:1396`), so a failed
attempt **advances to the next key rather than failing the request**. Admitting a dead key therefore
costs one wasted attempt, not a failed request — which is what makes a re-probe safe rather than
reckless. This was checked *before* writing any code, and it is the whole justification.

### What changed

| File | Change |
|---|---|
| `core/engine.rs` | `KeyHealth.breaker_open: bool` → `breaker_open_at: Option<i64>`. New `BREAKER_HALF_OPEN_MS = 60_000`. `key_block` returns `Breaker` only *inside* the window. `record_result` stamps on **every** failure past the threshold, not only the transition. |
| `packages/router-core/src/health-tracker.ts` | The same change: `breakerOpen` → `breakerOpenAt`, new exported `BREAKER_HALF_OPEN_MS`, new private `breakerBlocks`. |
| `packages/router-core/test/health-tracker.test.ts` | **New file** — the TS tracker had **no test file at all**. 5 cases. |
| `core/planner.rs` | Doc correction + `a_half_open_breaker_contributes_no_wait_at_any_instant`. |

**`Option<i64>` rather than a second field, deliberately.** A `bool` plus a separate `opened_at` is two
fields that must agree, and the pair has a state the flag cannot describe alone: open, with no idea
when. Storing the moment makes that unrepresentable, and it is the moment — not a flag — that
`key_block` reads, so the window cannot be defeated by a missing stamp.

**`key_retry_at` still answers `None` for `Breaker`, and that is the load-bearing decision.** A breaker
now clears on a clock, which makes it *look* like a cooldown — but the clock is minutes and a request's
budget is seconds, so a caller that slept on it would sleep past `FIRST_MSG_TIMEOUT` and fail anyway.
Increment 29's contract survives untouched.

## Increment 31 — `addKey` no longer strands a secret when its row does not land

### The defect

`store.ts:632` `addKey` is a two-store write: `registry.addKey` puts the secret in the vault under
`key:<uuid>`, then `fetchAdmin("POST", "/admin/api-keys", …)` records the row. `sendAdmin` throws on
any non-2xx (`gateway-client.ts:120`) and **nothing undid the vault write**. The secret was then
unreachable: the keys list reads `api_keys`, so it could be neither seen, nor selected, nor revoked
from anywhere in the app.

**The invariant was already written down twice and enforced in three of four places.** Rust
`key_create_h` rolls back and says why (`gateway_admin.rs:359`, *"a secret with no row is an
unrevokable ghost"*); the Rust IPC `key_create_h` does the same (`tauri/gateway_cmds.rs:340`); and
`addProvider` — eleven lines above `addKey` — rolls its own state back with the comment *"so the
registry never holds a ghost provider"*. Only `addKey` did not. **The fourth site was the one holding
a credential.**

### Why it is reachable, not theoretical

`api_keys.provider_id` is a real FK and `PRAGMA foreign_keys = ON` (`store.rs:517`), so a 500 is
available whenever the provider row is absent. `registry.addProvider` is **in-memory only**
(`provider-registry.ts:22`) — it never persists — so "provider in the registry, not in the host" is a
state the app passes through by design. The spec's failing case reproduces it directly.

### The live instance, and its removal

`key:323d5158-950e-4272-81ed-b1c4e5f1c67e` sat in the vault with no `api_keys` row. Shape: 39 chars,
prefix `sk-aip` — `generate_random_key()`'s exact output (`sk-aip-` + 32 hex), i.e. a **gateway**
credential in the provider-key namespace, not a third-party key (the two real provider keys are
`sk-tyh…`/`sk-HS1…` at 51 chars). Proven unused *before* removal: **0 hits across every column of all
30 tables**, 0 repo hits, **0 ledger rows**.

Removed by rewriting `.secrets.json` the way `vault::save` does (tmp → chmod 600 → rename). Verified:
5 → 4 entries, the other four **byte-identical by sha256** to a pre-change backup, mode 600 intact,

### 2. A test binary can write the vault into the user's home

Chasing a 16-byte stray `~/Library/Application Support/ai-provider-router/.secrets.json` holding
`{"k1": "v1"}` — the `SERVICE` default dir, which nothing in the repo reads.

**The mechanism is the finding:** `vault::set_data_dir` is a `OnceLock` (`DATA_DIR.get_or_init`), so
**the first caller wins and every later call is silently ignored.** In a test process the vault's
location therefore depends on whichever test touches it first — and `vault.rs`'s own
`get_returns_none_for_missing_account` does exactly that, calling the real `get()` with a real
account name, pinning every other test in that binary to the user's directory. `vault.rs:234`
already admits the hazard in a comment and works around it *locally*, but nothing stops the next test.

**Fix:** under `#[cfg(test)]`, `default_data_dir()` returns a temp dir — making the class impossible
rather than fixing one call site.

**Verified two-sided:** after a full `cargo test --lib`, the default dir did **not** reappear *and*
`/var/folders/.../T/aip-vault-default-7778` **was** created. The new branch is taken, not merely the
old one absent — the "prove the instrument reports presence" rule.

**Honest limit:** the **writer was not identified.** No code in the repo calls
`vault::put("k1","v1")`; every call site is production or an injected closure. So this is a backstop
for the class, not a reproduction-driven fix, and the original leak was not reproduced. Stray file and
dir removed (backed up to `/tmp`).

8787 is `gateway::DEFAULT_PORT` (`core/gateway.rs:38`) — the *other* gateway's constant. It is neither
`aiproviderd`'s default nor the persisted setting.

### Three more defects, each hidden by the one before

1. **`repro-restore.sh`'s kill matched nothing.** `pkill -f "AI-Provider Router"`, but the process is
   `aiproviderd`. Calibrated: `pgrep -f "AI-Provider Router"` → **exit 1**; `pgrep -f aiproviderd` →
   **820**. So it killed nothing, waited on a port that never went down, and printed `up=yes after 1s`
   on every attempt — a no-op reported as a working mechanism. Worse than a crash, because it is green.
2. **The soak's TSV was unparseable.** `${RES// /$'\t'}` — zsh does **not** expand `$'\t'` inside a
   parameter-expansion *replacement*; it inserts the five literal characters. `od -c` on a data row
   showed `2 0 0 $ ' \ t ' 0 . 0 2 6 3 3 6`, and `awk -F'\t' '{print NF}'` gave **4** for the header and
   **3** for every data row. The script's own comment already warned about this bug class for
   `print -r`; the fix had been applied to the format string but not to the substituted value.
3. **The supervisor was misidentified.** `launchctl list | grep` was read as "no launchd job". But
   `launchctl list` prints **0 lines** from a non-interactive shell here — and a control label whose
   plist *is* present (`com.tdai.gateway`) returned nothing too, so the absence was not evidence.
   `launchctl print gui/501/dev.aiprovider.router` → `state = running`, `pid = 820`, `RunAtLoad` +
   `KeepAlive`. My "no launchd job" line in the previous increment was **false**.

### Notes for next time

- **An instrument can be *empty*, not merely mispatterned.** The recorded bash-`grep` trap is a
  *false zero*; `launchctl list` here is a *true zero* — it emits nothing at all, so no pattern can
  find anything. Same conclusion either way: **calibrate against a known-present control** before
  reading an absence off it. `launchctl print gui/<uid>/<label>` is the probe that works.
- **zsh does not expand `$'\t'` inside `${x// /…}`.** Never build a delimiter by substitution; split
  the fields and let `printf` own the tabs. This is the second time this file's tab handling has cost
  a pass.
- **A hardcoded default is a claim about configuration, and configuration may differ from the
  constant.** An executable has to *reach* a listener; a document may state a default. That is why the
  drift register's D7 "not drift" verdict was true and still did not protect these scripts.
- **Defects stack, and the loud one hides the quiet ones.** The port bug was genuinely loud — and it
  meant the loop never reached the TSV write, so a second defect sat behind it for an unknown time.
  "It fails loudly" is a reason to look *next*, not a reason to look away.
- **A `Edit` whose anchor includes a heading will delete that heading if the replacement omits it.**
  I did exactly this to `### Housekeeping` in this file while correcting the parenthetical above, and
  caught it only by grepping for the heading. The recorded rule ("an inserting `Edit` must not shrink
  its anchor block") is not about intent — reproduce **every** line of the anchor.

## Incident 2026-09-27 09:13 — `CANCELLED` at 30 s, and it was the upstream, not the router

Reported: *"Custom model custom-local:agnes-2.5-flash error"*, `2026/09/27 11:13:37 UTC+8`, server
detail *"the router produced no response within 30000ms — the request was abandoned; retry"*.

### What the evidence says

| Step | Measurement |
|---|---|
| Report timestamp → ledger | `11:13:37 UTC+8` = `09:13:37` local → row **1652**, `error_class=CANCELLED`, `latency_ms=30015`, `tokens_in=0`, `tokens_out=0` |
| Ledger row → `request_id` | dispatch `03:13:07.798Z` + 30 015 ms = `03:13:37.813Z` → **`request_id=22`**. Bound exactly |
| The log for that id | `egress: upstream sent no response headers — connection stalled attempt=1 max_attempts=2 header_secs=10` (03:13:17.815) and `attempt=2` (03:13:27.817), then `gateway: bridge produced nothing for 30000ms` (03:13:37.800) |
| The chain | `[{"cls":"NETWORK","key":"Key-02","provider":"agnes"},{"cls":"NETWORK","key":"key-01","provider":"agnes"}]` |

**Root cause: the upstream accepted the connection and sent no response headers.** Both attempts
stalled at the 10 s pre-headers budget (`UPSTREAM_HEADER_TIMEOUT`, `egress.rs:445`). The router
retried once (`UPSTREAM_STALL_RETRIES = 1`, `:466`), then failed the request at
`FIRST_MSG_TIMEOUT` (30 s, `gateway.rs:1311`) instead of hanging — which is what it is designed to do.

### What I ruled out, and how

- **Not the prompt size.** The reflex is "~100 k tokens is just slow". Falsified: in the same window,
  **116 550**-token prompts completed in **7.7 s** and **116 146** in **5.4 s** (rows 1654, 1653).
  `tokens_in` did not push these past 10 s.
- **Not a local proxy.** The service's environment has **no** proxy vars (`ps eww -p 14115`); my
  *shell* has `HTTP_PROXY=http://127.0.0.1:56268`, so probes must unset all six or they measure the
  sandbox, not the upstream.
- **Not a live outage.** Direct probe minutes later: `http=200 dns=0.0028s connect=0.056s
  ttfb=0.46s`. The design's assumption — headers "well under a second" — held.
- **Not chronic.** All 10 `connection stalled` warnings in the entire log fall between 09-26 17:38 and
  today 03:15, **9 inside a 16-minute window**, 6 in the last two minutes. Hourly today: `08` = 10 ok
  / 0 errors, `09` = 17 ok / 3 `CANCELLED`. A burst, already over.
- **Not model-specific.** `agnes-3.0-flash` (`request_id=26`) stalled the same way as
  `agnes-2.5-flash`.

### The structural finding

`providers` holds **one** row — `Agnes`, `https://apihub.agnes-ai.com/v1` — with 2 active keys. Both
entries in `fallback_chain_json` carry `"provider":"agnes"`, so **the "failover" is a second
credential against the same host**. When the host stalls, there is nowhere to go. More keys cannot fix
this; **only a second provider on a different host changes the outcome.** `egress.rs:457-460` records
the same lesson from 2026-09-26.

### Left open, deliberately

The two logged stalls account for 20 s of the 30 s. The last ~10 s has **no log line at all** in
`request_id=22`'s lifecycle. For `request_id=25` a third `attempt=1` appears **18 ms *after*** its
bound fired, which hints at a further attempt racing the gateway bound — a lead, not a measurement.
Not recorded as a cause.

### Skill updated

`gateway-incident-triage` §5a (the `connection stalled` discriminator — its *presence* is what
separates this from the 2026-09-26 `request_id=12` case, where the line's *absence* was the proof) and
§5b (count providers, not keys; the budget invariant; the open question above).

### Follow-up 09:23 — it recurred, and my "burst is over" call was wrong

A second report arrived 8 minutes later (`11:21:15 UTC+8`, model `agnes-3.0-flash`). **Same
signature**: ledger row **1658** at `09:21:15`, `CANCELLED`, `30 010 ms`, 0/0 tokens,
`request_id=27` — dispatch `03:20:45.005839Z` + 30 010 ms = `03:21:15.015`, bound exactly. Two
`connection stalled` warnings again (`03:20:55.018`, `03:21:05.020`), then the gateway bound.

**I had written "a burst that has already passed" on the strength of three fast probes and a quiet
six-minute log window. That was wrong, and the correction matters more than the original finding:** an
intermittent condition on a scale of minutes cannot be bounded by one fast probe. Row 1659 succeeded
29 s later, so the interleaving is request-level, not a hard outage.

**Body size is not the driver — measured, because it is the tempting answer.** TTFB against
increasing bodies to `apihub.agnes-ai.com`:

| prompt | body | ttfb |
|---|---|---|
| ~1 k tok | 2 KB | **7.36 s** ← slowest, and the *smallest* |
| ~10 k tok | 24 KB | 0.88 s |
| ~50 k tok | 117 KB | 1.29 s |
| ~100 k tok | 235 KB | 1.85 s |

**The smallest prompt was the slowest.** TTFB rises only mildly with body size and the dominant
variable is *when* you ask. This also retires the earlier "116 k-token prompts are just slow" reading
from the first triage — they completed in 5–8 s.

**The upstream's tail, 12 identical tiny requests:** `0.563 0.561 0.920 1.092 0.658 2.379 0.221 0.202
0.183 0.190 0.200 0.182` s. Mostly 0.18–2.4 s, with one separate probe at **7.36 s**.

**Severity since the last restart:** 27 requests, 23 first messages, **11 stalled attempts, 4
failures ≈ 15% of requests**. Attempt-level stall rate ≈ 11/38 ≈ **29%** — *assuming stalls are
independent, which a burst pattern may falsify, so treat any "more retries would fix it" projection as
a hypothesis.*

**The custom-header theory, settled.** The user asked whether their WorkBuddy custom header was the
cause. It is not: neither stored manifest (both `provenance.origin = "user-edited"`) has a `headers`
key on any endpoint, and `core/` has no `extra_headers`/`custom_headers` field at all. The
client→router leg is a different boundary from the router→upstream leg, and only the second dials
agnes.

**The router is healthy while the upstream is not.** Live request at `09:25:03`: `http=200`, router
TTFB **0.010 s**, ledger row **1660** `status=ok latency_ms=881 tokens_out=18`. A 10 ms answer from
the router during an upstream stall is the cleanest possible statement of where the fault is.

### The recommendation, unchanged and now better supported

Still **one provider** (`Agnes`) with 2 keys, so both chain entries name the same host. **A second
provider on a different host is the only change that alters the outcome** — more keys cannot. A third
attempt (`9 s × 3 = 27 s < 30 s`) is the plausible tuning, but the independence assumption above has
to hold first, and it costs a longer wait before failing.
