## Closed: the zero-cost bug (it was three defects, not one)

Yesterday's note ended with tokens still recording 0 "STILL UNEXPLAINED". Resolved. Three
independent defects sat on the same path, which is why each fix looked like it hadn't worked:

1. Nothing asked the provider for usage on a stream (`stream_options` never sent). Fixed in
   `29ba465` via `stream.requestUsage` + a dialect default for manifests stored before the flag.
2. `execution-engine` swallowed the caller's `onUsage`, so the gateway bridge never learned the
   counts even when the engine had them.
3. **The real cause:** the interpreter `return`ed as soon as it saw `finish_reason`, but
   OpenRouter delivers usage on a *later* chunk. Measured order:
   `content -> finish_reason=stop, usage=null -> usage={...}, choices=[] -> [DONE]`.
   Fixed by `continue`-ing past finish_reason when usage was requested.

`1c149e0` covers 2 and 3. Runtime proof: `tokens_in 311 / tokens_out 3` where every row had
been 0/0.

## Bare `openai/gpt-4o-mini` did not route — real bug, now fixed

Tushu added a WorkBuddy custom model with `{"id":"openai/gpt-4o-mini"}`. It 404'd:
`no route for model "openai/gpt-4o-mini" (no enabled provider carries it)` — even though the
model WAS in the cached catalog. `openrouter/openai/gpt-4o-mini` worked fine.

Cause: `resolveWanted` read everything before the first `/` as a provider slug. No provider named
`openai`, so it pushed no candidate — and the bare-native-id branch was gated on
`!model.includes("/")`, so it never ran either. OpenRouter's native ids contain a slash, which
makes a bare native id indistinguishable from a qualified one on the wire.

Fix (`ef98827`): track whether the id actually qualified. Read the slash as a qualifier only when
it names a real provider; otherwise fall through to the bare-id lookup. A genuinely qualified id
still short-circuits, so nothing can be silently rerouted to another provider. 3 tests, incl. a
guard that a qualified id is not rerouted even when a model literally named
`openrouter/openai/gpt-4o-mini` exists in the catalog.

Verified on the rebuilt app: `openai/gpt-4o-mini`, `custom-local:openai/gpt-4o-mini` and
`openrouter/openai/gpt-4o-mini` all return 200 with usage.

## A null-usage scare that was NOT a usage bug

deepseek came back with `usage: null` and 0 tokens on one request. Looked like the same class of
bug again. It was not:

- Direct upstream check (non-stream AND stream): deepseek reports usage exactly like gpt-4o-mini
  does — finish_reason on chunk N, usage on chunk N+1. Identical shape.
- The failing ledger row was `status=error, error_class=NO_ROUTE` — **no request was ever sent**,
  so of course there was no usage. Rapid-fire requests had tripped OpenRouter's rate limit, the
  key went to cooldown, and the planner had no candidate.
- Re-ran: deepseek 892/2 and gpt-4o-mini 316/2, both with usage, both with correct cost.

Lesson: `error_class` in the ledger is what distinguishes "usage was dropped" from "nothing ran".
Check it before assuming the capture path broke again. Also: `usage: null` on a *successful*
response and `usage: null` on an error response look identical from curl — read the ledger row.

## Runaway tool-call XML in WorkBuddy chat — root cause: manifest provers drop `tools`

Tushu pasted a WorkBuddy chat where the assistant emitted a recursive, unterminated
`<invoke name="Bash"><parameter name="command">…` blob and had to be cancelled at 44s.

Ledger first (`ledger` table, `datetime(ts/1000,'unixepoch','+6 hours')`) — this is the single
most useful debugging move, it names the model that actually served:

| local | model | latency | tok in/out |
|---|---|---|---|
| 02:34:10 | agnes-3.0-flash | 1782 | 0/0 |
| 02:35:18 | agnes-2.5-flash | 2950 | 0/0 |
| 02:37:44 | agnes-2.5-flash | **40359** | 0/0 |

So it was Agnes, not gpt-4o-mini. Chain:

1. **The active Agnes manifest drops tools.** `requestTemplate` is only
   `{model, messages, stream, max_tokens?, temperature?}` — no `tools`, no `tool_choice`, no
   `response_format`. Verified by reading the row:
   `SELECT body_json FROM manifests WHERE provider_id='8234f8af-…' AND is_active=1`.
2. **The engine could carry them.** `manifest-interpreter.ts` already passes
   `tools/toolChoice/responseFormat` into `renderTemplate`, and honours `responseMap.toolCalls`,
   `stream.chunkMap.toolCalls`, `stream.toolCallStream`, `responseMap.usage`. The gap is only that
   `adapter-generator.ts:81` tells the generator the placeholder set is limited to five names, so
   no AI-generated manifest ever declares them.
3. **`workbuddy.rs:281` hardcodes `"supportsToolCall": true`** for every published model, so
   WorkBuddy is told Agnes can call tools. (The reasoning flag is deliberately `unwrap_or(false)`;
   tool call is not.)
4. Result: model sees WorkBuddy's tool-heavy system prompt with zero tool schemas, role-plays tool
   calls as inline XML, never terminates, degenerates. `parseAssistantStream` only knows
   `<|tool_call_start|>`-family markers, so `<invoke>` XML passes through unfiltered.
5. **Agnes upstream DOES support tools.** Direct call to
   `https://apihub.agnes-ai.com/v1/chat/completions` with `tool_choice:{"function":"Bash"}`
   returned a well-formed `tool_calls` (with `type:"function"`, `index`, `usage`). Key from
   keychain: `security find-generic-password -s ai-provider-router -a key:<keyId> -w`. So the
   manifest is the ONLY thing blocking it.

Two further defects found while reproducing:

- **Pass-through tool_calls are not OpenAI-shaped.** Live capture from the gateway:
  `{"delta":{"tool_calls":[{"arguments":"{…}","id":"call_…","name":"Bash"}]}}` — missing per-call
  `index`, missing `type:"function"`, missing the `function:{name,arguments}` wrapper. Emitted in
  both the SSE branch and the non-stream branch of `gateway_handlers.rs`.
- **Agnes ledger rows are 0/0 forever** because the manifest has no `responseMap.usage` — spend
  accounting and the R4 cap are blind for this provider.
- `~/.workbuddy-ai/models.json` has 5 entries all named "ai-provider router"
  (openai/gpt-4o-mini + 4 agnes variants), so the picker cannot distinguish them.

Fixes, in value order: (1) add tools/tool_choice + toolCalls + usage to the Agnes manifest;
(2) allow them in the generator prompt; (3) derive `supportsToolCall` from real capability data;
(4) emit OpenAI-shaped tool_calls; (5) unique names per published model.

## The 503s: fixed on the request path; the deeper cause is App Nap

Followed up on the intermittent `503 AI-Provider Router core unavailable`.

**Mechanism.** The worker window is created `visible(true)`, warmed, then hidden
(`hide_worker_after_warmup`), and `set_hidden(true)` switches the stale bound to 30s. macOS
suspends the JS of hidden webviews, so the 2s `setInterval` heartbeat stops. `spawn_watchdog`
polls every 5s and *would* recover it, but is rate-limited to once per 60s — so any request
arriving inside that cooldown was refused outright. 22 watchdog events in today's log.

**Fix.** `try_slot` is now async and, when the beat is stale, calls `await_core`, which asks the
host to re-warm (`request_warm`, rate-limited to once per 2s so a burst during one lapse does
not flicker the window) and polls `beat_is_fresh()` every 150ms up to a 5s grace. Stopped is
still terminal — `is_running()` now separates "operator stopped it" from "beat lapsed", so a
stopped gateway answers immediately instead of waiting 5s to say the same thing.
`GatewayCore` gained a `warm: Mutex<Option<WarmFn>>` hook attached in `build_core` via
`warm_bridge_window`. `set_warm` exists alongside the consuming `with_warm` builder because the
real hook must refer back to its own core — the builder cannot express that, and the unit test
hit exactly that wall.

115 Rust tests; 3 new ones in `core_recovery_tests` (recovery succeeds and fires the hook once,
a hookless core is simply not warmed, stopped is terminal).

**Verified:** 14/14 then 8/8 consecutive requests OK, zero 503s (it was 2-of-3 failing before).
Caveat worth stating plainly: the log shows no watchdog event during either run, so the recovery
path was not exercised live — the unit tests carry that claim, the runs prove no regression.

**The deeper cause is still open.** One request in the first run got no response at all for 60s
while the listener stayed bound and nothing was logged. That is not a lapsed heartbeat — it is
the whole app process being suspended (App Nap) when it is in the background. A lapsed beat
produces a 503; App Nap produces a hang. Fixing it properly means suppressing App Nap
(`NSProcessInfo beginActivityWithOptions`, or a plist/activation-policy change), which needs
objc and is a separate piece of work. Practical mitigation today: keep the app's window open
while chatting through it.

## 10:10 — App Nap suppression shipped (commit `31b0b58`)

**This was the root cause behind the whole day's symptoms.** The router core lives in a hidden
webview and proves liveness by heartbeat; macOS suspends JS in hidden/backgrounded processes.
Heartbeat stops → watchdog notices after the fact and re-warms → requests meanwhile refused, and
one observed turn waited past 60s on a worker that would never answer. The two earlier fixes
(wait out a lapsed beat; bound the first message) treated the consequence, not the cause.

**Implementation** — new `apps/desktop/src-tauri/src/app_nap.rs`, called from `lib.rs::run()`
*after* `tracing_subscriber` init (first attempt put it before, so the confirmation line was
silently dropped — no subscriber installed yet). Uses
`NSProcessInfo::beginActivityWithOptions_reason` with
`NSActivityOptions::UserInitiatedAllowingIdleSystemSleep`, chosen over plain `UserInitiated` so
the machine can still idle-sleep — a local gateway should stay responsive without keeping a
laptop awake overnight. The returned token is leaked with `std::mem::forget`; dropping it would
end the assertion and it must outlive every request.

**objc2 was already in the tree via Tauri** (objc2 0.6.4, objc2-foundation 0.3.2), so adding them

## Closed the L2/L3 producer gap I left open

Last turn shipped a four-layer memory system with producers for **L0** (raw turns) and **L1**
(derived atoms) only. L2 (scenarios) and L3 (core) were schema-valid and displayable but had no
writers, which meant the "abstract-first" recall pass — the whole point of layering — was
returning empty in practice. Saying it does layered recall without the layers actually producing
was a lie, even if a small one.

Fixed:
- **L2 scenarios** — auto-producer. `SCENARIO_EVERY = 6`: after six new L1 atoms pile up for one
  session, the next pass reads the unseen window and asks the model to group them into up to
  three L2 blocks (`subject` + `text`). Cursor per session; on failure it rolls back so the
  next pass retries the same atoms. Fired from `distilTurn` with `void`, so a slow second call
  never delays what the user is reading. New `memory_session_atoms` host command returns
  oldest-first because `listMemories` is newest-first and the window needs to be chronological.
- **L3 core** — user-authored. A Core profile section in the Memory screen with add/edit/forget.
  Pinned by default — that is the point of L3. New `memory_update` host command rewrites text in
  place. L3 is excluded from the main derived list and from the filter chips so it has one
  source of truth. Filter chips renamed "all" → "derived" to be honest about scope.

Why user-authored L3 and not auto-distilled: the stable things about a person are the things
the person knows. Auto-distilling a persona from chat without review is exactly the kind of
thing that goes quietly wrong — "the model thinks I prefer X" because it misread a casual
remark. L3 earns its always-injected status by being something the user said.

Cost: scenario passes add one model call every ~6 L1 atoms per session (≈ every ~18 turns).
Worth it because layered recall now actually does what its name promises. Atom batches and
scenario batches are both heavily debounced so a slow chat costs nothing on either path.

**2. `agent-graph.spec.ts` — writing an invariant spec found two real bugs in `Playground.tsx`.**
The existing `agent-turn.spec.ts` sends one turn and asserts with `find`, which is indifferent to a
duplicate. Asking instead "does each turn appear once?" failed immediately.

- **`recordAgentTurn` was handed the loop's whole transcript.** `runAgentLoop` seeds its working
  copy from the replayed history and returns *all* of it, so every turn re-recorded the entire
  prior conversation as brand-new nodes — the graph grew quadratically in turns. It also minted its
  own user node while the recall path had already created one for the same prompt, so one turn put
  the user's message in twice. Fix: the caller creates the user node once (it needs it up front as

  themselves to the next turn's batch. Moved the flush into `finally`, matching plain chat.

**3. Same root cause, third instance — and this one killed the host's edge accumulator.**

generated one *per call*, even though the memory's own stable id was already in the node's meta.
So the same memory appeared as N nodes, and `context::record`'s

dedupe path.** The host is built to upsert on id and accumulate edge weight, and the buffer is
deliberately naive. So any new recording path that mints an id instead of reusing a stable one
turns the host's dedupe into dead code — silently, with no test failure unless a spec asserts
uniqueness. Worth checking every time a new node kind gets a producer.

## Time in the memory system: recency now ranks, and rows show when a fact was first seen

Followed the timestamp question to its two real consequences. Commit `8b98dbc`.

**Recall ignored time.** `ORDER BY score, CASE layer …` — a six-month-old atom and yesterday's
ranked identically on an equal match. Added `rerank`: relevance band → recency → layer.

Design decisions worth keeping:
- **Band measured from the best hit, not from the spread of the candidate set.** My first version
  normalised by the spread, which degenerates exactly when the set is small: with two candidates
  the two extremes *are* the whole spread, so they always land in different bands and recency never
  fires. Two or three candidates is the common case for a real recall query. The Rust test
  `at_comparable_relevance_the_more_recent_memory_wins` caught this immediately.
- **A band, not a weighted blend.** Blending would stop the displayed bm25 scores being monotonic,
  so a correctly-ranked list would look like a broken one. The number on each row is the match and
  must stay readable as such.
- **L3 is exempt from decay** — a core fact is core because the user wrote it down, not because it
  is recent. Decaying it would bury the most stable thing we know.
- `recall` now fetches `limit * 4` candidates before re-ranking; recency can only reorder what it
  is shown.
- `RELEVANCE_BAND` (0.15) is a **tuned default, not a measured optimum** — there is no ground truth
  for "the right memory" to measure against. Named so it can move once there is. Said so in the
  code comment and the commit rather than implying it was validated.

**Sort-direction bug caught by the tests, not by reading.** `band(b).cmp(&band(a))` sorts bands
*descending*, but band 0 is the best match. `a_clearly_better_match_is_not_displaced_by_a_recent_weak_one`
failed on it. Worth remembering: a three-key comparator is easy to get backwards in exactly one key.

**One of my own tests was passing for the wrong reason.** `recall_still_returns_the_relevant_memory_when_the_others_are_newer`
used a distractor ("Agnes publishes wrong modality…") sharing no token with the query — so it was
never a candidate, and `hits[0]` was the wanted memory trivially. Rewritten to share a token and to
assert `hits.len() == 2`, so the test cannot pass vacuously. **Assert the candidate set, not just
the winner.**

**The Memory screen showed `updated_at` only.** `created_at` was stored and never displayed, so a
deduped atom reported when we last *saw* a fact as if it were when we learned it. Rows now show a
relative age; "first <age>" appears only when the two would **read** differently — comparing the
rendered strings, not the raw delta. That is what stops a re-record seconds after the first from
printing "just now · first just now" while still showing "1h ago · first 3d ago". Absolute
timestamps moved to the `title` attribute.

Note for next time: `vitest` here is `environment: "node"` with `include: ["e2e/**/*.test.ts",
"src/**/*.test.ts"]` — **no jsdom, no testing-library, and `.tsx` is not in the include list**, so
component logic is only testable through the browser harness. Keep helpers that need unit tests out
