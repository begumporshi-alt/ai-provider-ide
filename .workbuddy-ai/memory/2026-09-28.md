## The three Hcnsec errors were one misconfiguration (2026-09-28, later)

Tushu reported three different messages from one provider (`Hcnsec`, `https://api.hcnsec.cn`):

1. Fetch from provider → `Could not list this provider's models — JSON Parse error: Unrecognized
   token '<'.`
2. Test on `glm-5.3-flash` → `answered with an empty response — the request succeeded but no
   content came back`
3. Key test → `key-01: could not verify — JSON Parse error: Unrecognized token '<'.`

**One cause, and it was not three bugs.** "New API"/One-API gateways serve an HTML SPA from `/`
**and from every unknown path, at status 200**, while the real API lives under `/v1`. Measured, three
hosts, same shape:

| URL | status | content-type |
|---|---|---|
| `agentrouter.org/` | 200 | `text/html` |
| `agentrouter.org/v1/models` | 401 | `application/json` |
| `vyceai.com/` | 200 | `text/html` |
| `vyceai.com/v1/models` | 401 | `application/json` |
| `apihub.agnes-ai.com/v1/models` | 401 | `application/json` |

`api.hcnsec.cn` measured the same on the first pass; a later re-probe returned **522** on all three
paths (Cloudflare, origin unreachable) — so that host is now also down, which is a *second*, current
condition, not a contradiction of the first. Do not read a later probe as a refutation without
checking *when* each was taken.

- **The three symptoms differ because three different parsers met the same HTML.** `listModels` and
  the key test both `JSON.parse` it → `Unrecognized token '<'`. The streaming path instead read it as
  an SSE body, saw no `data:` line, ended cleanly, and so reported "empty response" — the *same*
  fault wearing the opposite mask (a clean-looking stream). **A "successful but empty" and a "parse
  error" can be one fault**; the loud one does not exhaust the quiet ones.
- Live DB confirms the stored shape: `Hcnsec` → `https://api.hcnsec.cn`, `Vice` → `https://vyceai.com`,
  `agent router` → `https://agentrouter.org`, all `enabled`, **none with `/v1`**; only `Agnes` →
  `https://apihub.agnes-ai.com/v1` carries it — and it is the one that answers. **A row can be
  `enabled` while every request to it is misrouted** — status is a bookkeeping state, not a probe.
- **`buildManualManifest` takes the field verbatim** (`manual-manifest.ts:73`,
  `provider.baseUrl = input.url`) while the template supplies the paths (`/models`,
  `/chat/completions`, `/messages`); `joinUrl` only strips a trailing slash and adds one leading.
  So the operator must type the **API root**, not the host. Onboarding's placeholder has always read
  `https://api.example.com/v1` (`Onboarding.tsx:643`) — **the wizard was the copy that drifted**, and
  a placeholder that models the wrong shape is a claim about configuration.

**The fix, in two halves.** (a) Message: `jsonBody(raw, url)` + `htmlNotJson(url, head)` exported from
`manifest-interpreter.ts`, guarding all four parse sites — names the URL it asked, quotes 80 chars of
what came back, and on a leading `<` says the base URL is probably missing its API path and suggests
`/v1`. The SSE loop checks the first non-blank line for `<` so an HTML body is named instead of
reported as a clean stream. (b) Field: placeholder → `/v1` plus a one-line hint.

- Falsified first: with the guards disabled, 2 of the 4 new tests fail and the 2 that assert working
  JSON/SSE still pass — i.e. the new tests exercise the guard, not the happy path.
- Gates: router-core **291** (+4), desktop 245, Rust 1358, typecheck 3/3, clippy `-D warnings` clean,
  rustfmt clean, key-leak-grep OK, doc-links 58 files/144 links, version-sync 1.2.0.
- **The remedy is Edit → Base URL → `https://api.hcnsec.cn/v1`**, and it needs **no restart**: the

## `?seed=systemai` could not boot the app — `nullable` is not `maybe` (fixed)

Found while trying to verify the nav change: the smoke spec failed, and the failure screenshot
showed the app's **"App data could not be opened"** card, not a broken screen —
`HostShapeError: GET /admin/models-cache: the host sent a shape this build does not understand`.

The chain, each link read rather than assumed:

1. `seeds.ts` model rows carried five fields (`providerId, nativeId, modality, contextWindow,
   fetchedAt`); the seed's own `SeedInput.models` type declared exactly those five.
2. `shim.ts:464` `applySeed` does `models.push({ ...m })` — **no normalization**, so the rows reach
   `models_cache_list` as declared.
3. `store.ts:458` guards the response with `arrayOf(isHostModelRow)`.
4. `host-guards.ts:74-75` guards `pricingJson` and `capabilitiesJson` with **`nullable`**.
5. `host-boundary.ts:52-55` — `nullable(g) = v === null || g(v)`; `maybe(g) = v === undefined || v ===
   null || g(v)`. **`nullable` rejects an absent key.** So both columns are required-present, and the
   type agrees: `HostModelRow` (`store.ts:83`) declares them non-optional while `origin?` is optional.

So a fixture that omits a nullable column is not "null" — it is a guard failure, and `arrayOf` takes
the whole array down with it, which fails the **boot**. The failure then surfaces in whichever spec
happens to run first, as a 120 s timeout on its first `getByRole`, naming nothing about the real
cause. **A fixture that is not host-shaped is worse than a missing fixture**: it fails far from where
it is wrong.

Fixed by making `SeedInput.models` host-shaped with both columns **required** — the compiler then
named all seven offending rows (`seeds.ts:104,105,108,165-168`) — and supplying
`pricingJson: null, capabilitiesJson: null`. Measured: "AI Providers" render check 2 m 11 s timeout →
**1.1 s**; `smoke.spec.ts` never-finishing → **14 passed in 22.5 s**.

**This is why the A/B mattered.** Before touching anything I ran the *untouched* "AI Providers"
screen and it failed identically — which ruled out my change in one step instead of after an
