### Two structural decisions, both forced by Rust rather than chosen

- **The context is a `trait PlanContext`, not a struct of `&'a dyn Fn` fields.** A struct holding
  `&'a dyn Fn(..)` forces every test to keep its closures alive longer than the context built from them;
  `&|pid| ...` is a borrow of a temporary and does not compile. A trait lets the fixture *be* the context,
  which is also what the TypeScript is (an object literal with methods).
- **`Candidate` moved out of `core::engine` into `core::planner`.** Its increment-7 doc-comment parked it in
  the engine only "because the planner itself is not ported yet"; the planner now owns its output type. The
  engine imports it, so no call site changed. `ProviderRow`/`ApiKeyRow`/`ModelRow` gained `Clone`, because the
  TypeScript's `Candidate` holds *references* and the port clones. **After removing the struct, `ModelRow`
  became unused in non-test engine code** — it is imported inside `mod tests` so a plain `cargo build` warns
  about nothing.

### Three provably-equivalent divergences (each pinned by a test)

1. **`rem_euclid` replaces JavaScript's `%` *plus* its negative `slice` indices.** `-1 % 3` is `-1`, and
   `slice(-1)`/`slice(0, -1)` count from the end — so `start = -1` on three keys means "begin at index 2",
   which is exactly `rem_euclid(3)`. Total and panic-free where a literal `%` would produce a `usize` panic.
2. **The TypeScript's `if (!ctx.pricingFor)` guard is unobservable** once an absent price is `None`: every
   rank is `None`, every comparison is `Equal`, and a stable sort is the identity. So `pricing_for` is a
   **required** trait method with no default body — this crate's rule — and "no pricing" is one of its
   answers rather than a missing one. (Note the tension with the crate's "no default body" rule and why the
   rule still wins: the optionality *is* the value.)
3. **Dedup key is a `(provider_id, native_id)` tuple**, not `` `${providerId} ${nativeId}` `` — the string
   collapses `("a b","c")` with `("a","b c")`.

### Two source behaviours kept, both now pinned

- **`orderCarriers` decides by `wanted.some(...)`, so ONE carrier asking for `cost_spread` reorders every
  other carrier on the list**, including providers whose own strategy is something else.
- **A *disabled* provider still claims its own qualifier.** `stripClientNamespace` and the qualified-id lookup
  read `ctx.providers` regardless of status, while `buildPlan` requires `enabled`. So `a/m1` resolves as
  qualified against a disabled `a`, `qualified` suppresses the bare-id fallback, and the plan comes back
  **empty** even though another enabled provider carries a model literally named `a/m1`. That is the source's
  "never silently reroute" rule reaching further than its comment describes.

### The three safety properties, and the one that is checked exhaustively

Tier 1 is hard truncation of the oldest *complete turns*. Truncation is safe only because of three
things, each pinned: the `system` prefix survives; the newest turn survives even when it alone exceeds
the budget; and **a turn boundary only ever falls on a `user` message**, so an assistant `tool_calls`
turn and the `tool` results answering it always move together.

The third is checked at **every** budget from 0 to just past the whole conversation. That is not
thoroughness for its own sake — mutation M3 (turn boundary moved onto `tool`) reddens *only* that test.
The two hand-picked-value tests around it stay green, because the loop's `turns.len() - 1` bound happens
to stop it in the same place.

### Two estimators stay apart; one fact is shared

`gateway::context_scope` already estimates tokens for the memory-injection budget. The tidy-up is to
merge them. They are not the same estimate:

| | memory injection | compressor |
|---|---|---|
| chars per token | `MEMORY_CHARS_PER_TOKEN` 3.5 | `CHARS_PER_TOKEN` 4.0 |
| reserve fraction | `MEMORY_RESERVE_FRACTION` 0.20 | `RESERVE_FRACTION` 0.25 |
| content shape | string content only | multimodal parts, serialised when not a string |

The memory estimator **over-estimates on purpose** — fewer chars per token means more tokens means it
under-injects, which is the safe direction. The compressor is not under that pressure. And
`MEMORY_FRACTION` is *also* 0.25 while meaning "share of the remaining window memory may take" — a
value collision with a different meaning, which is the D21 pattern. So both ratios and both reserves
stay separate, with a test asserting they differ, and **the one genuinely shared fact — the per-message
overhead of 4 — was extracted to `context_scope::MESSAGE_OVERHEAD_TOKENS`** and is referenced by both.

### `String::length` is UTF-16, and here that matters

`encode_utf16().count()`, not bytes and not scalar values. Byte length over-estimates every non-ASCII
conversation — Bengali is 3 bytes per character — and drops history that fits; scalar values
under-count astral characters by half. The test pins all three readings with inputs that differ 4×,
including four Bengali characters.

### `new Set` is object identity; Rust has none

`dropped_against` spends one unit of allowance per kept copy instead of testing membership. With
`[A, A, B]` reduced to `[A, B]`, exactly one `A` went — which is what identity says and what neither
plausible wrong reading (`contains`, or "is any copy kept?") gives.

**The falsification run proved the doc-comment's claim the hard way.** M14 replaced the allowance with
`contains_key` and expected two tests to redden; only the unit test did. The budget-driven duplicate
test cannot distinguish the readings **because in it no copy of the dropped message survives** — the
doc-comment says exactly that ("only a partially-kept duplicate can tell them apart"). The harness
expectation was wrong; the code was right.

### `DEFAULT_CONTEXT_WINDOW` is an alias, and its test is a tautology

`DEFAULT_CONTEXT_WINDOW = DEFAULT_WINDOW_TOKENS`, because both answer one question — what window do we
assume when nobody told us — and the TypeScript says so in as many words. `the_fallback_window_is_the_hosts_own_constant`
**cannot fail while the alias holds**, and that is recorded in the test rather than hidden: it guards
the *shape*, catching the day someone writes `8192` back in.

### Tier 2: the degrade path is the contract

A summarizer that fails and one that returns only whitespace are the **same** outcome — Tier 1's answer.
An added feature must not turn a working request into a failed one. The summary lands in the system
prefix so the re-fit cannot trim it away; the re-fit may drop further turns and those go **without a
second summary**, since recursing would put an unbounded number of model calls on the request path. The
dropped set is reported against the **original** conversation, not the intermediate one, so "what was
removed" does not change meaning depending on whether a summary happened to be produced.

### The Tier 2 re-entrancy blocker — measured, in both directions

`Assistant.tsx`'s live summarizer closes over the `router` singleton and calls `router.generateText`
from inside `router.generateText`. In Rust, `generate_text(&mut self, …)` cannot take a callback that
re-enters the same `&mut self`.

Measured, not guessed (`/tmp/reentrancy.rs`, `/tmp/reentrancy-ok.rs`):

- The nested shape is rejected with **`E0501`** — `cannot borrow *self as mutable more than once at a
  time`. **Not `E0499`**, which was the first guess and which the compiler refused.
- The sequenced counterpart (summarize, *then* route) **compiles and runs** — printed `text text`,
  `calls: 4`. So the constraint is the re-entrancy and nothing else.

**Conclusion: the guard `skipCompression` exists to provide is not needed in this shape at all.** What
Tier 2's wiring needs is a **seam** — the summarizer handed to the router as a boundary the router calls
and does not own, the shape `AdapterFactory` and the usage callbacks already use — rather than a closure
over the router. This supersedes Phase 4's original note ("introduce the compression and the guard
together") and §12's open question.

## The adapter-runtime spike — is `rquickjs` a port or a reimplementation? (answered: a port)

The recommended next move, approved as such. A standalone crate, **723 lines, 13 probes**, at
`.workbuddy-ai/spikes/js-engine/` (`cargo run --release`; `SPIKE_CRASH=1` for the two that are
expected to kill the process). 11 pass by default; 2 are opt-in crashers.

**Verdict: a port.** `GOOD_GUEST` copied *verbatim* out of `code-adapter.test.ts:21-37` runs through
`rquickjs` and reaches the same three values that file asserts —
`listModels=[text-1,img-2]`, `generateText=[Al,pha]`, `generateImage={ok,200,QUJD}` — against a Rust
host reproducing `makeHttp`'s deferred-promise bridge and `callOp`'s job pump. Every host primitive
maps. `AdapterInstance: Send + Sync` is satisfiable via rquickjs's `parallel` feature.

### Three traps, each measured

1. **`EvalOptions::default()` is `global: true` — script mode.** So the obvious `ctx.eval(src)` rejects
   the guest's `export default {` on its first character. Clearing `global` does select
   `JS_EVAL_TYPE_MODULE`, but `eval_with_options` then returns the module's *evaluation promise*,
   which resolves to **`undefined`** — the namespace is unreachable from that door at all.
   `Module::declare(...)?.eval()?` + `get("default")` is the only one that works, and it also compiles
   without running (which is what `compile()` is for). The struct is `#[non_exhaustive]`, so
   `EvalOptions` can only be defaulted and mutated, never built with a literal.

2. **`Context::with` holds the runtime's global lock for the whole closure** (`context/base.rs:109`).
   Under `parallel`, `Runtime::is_job_pending` / `execute_pending_job` each take that same
   non-reentrant lock (`runtime/base.rs:162,170`) → **deadlock inside a context scope.** Only
   `Ctx::execute_pending_job` (`ctx.rs:375`, no lock) works. **The feature the seam's bounds require
   is exactly what makes the obvious pump illegal.** Cost: the `Ctx` variant returns `bool` and folds
   "a job ran" together with "a job threw", so job exceptions must be read off the promise.

3. **The 32 MB memory limit is not containment.** The headline. Measured, each variant its own run:
   - no limit, ~60 MB allocation → resolves normally (so the limit, not the allocation, is the cause)
   - 8 MB limit → **SIGSEGV**, 3/3, inside `m.call`
   - **the TS's own 32 MB limit → SIGSEGV too**
   - same allocation *after an `await`* (so it lands in a job) → rejects cleanly, no crash
   - a plain `throw new Error("boom")` at entry → rejects cleanly
   - runaway recursion vs the 512 KB stack limit → rejects cleanly

   So the trap is specific: an OOM raised while the guest runs **directly inside the call**, before its
   first `await`, kills the process; the same trap in a job is contained; neither the stack limit nor
   an ordinary throw is fatal. **The TS suite has no test for the memory limit at all**, so nothing
   there could have caught it. A containment limit that aborts the host is not a containment limit.

   What survives in-process: the wall-clock deadline (measured — a spinning guest aborted at 300.7 ms
   and 301.2 ms against a 300 ms budget), the http/emit budgets, path containment, stack depth. What
   does not: a heap ceiling. Either the adapter runtime runs under a supervisor or that one limit does.

## Increment 16 — the interpreter's I/O half, and two findings that came from falsifying rather than writing

**Landed:** `core/http_port.rs` (184 lines, 2 tests), `core/manifest_view.rs` (551, 6),
`core/interpreter.rs` (2,258, 44), plus `parse_retry_after` / `retry_after_from` in `core/manifest.rs`
(6 tests). 58 tests, Rust **812 → 870**. Gate: `cargo fmt --check` exit 0 with **zero bytes** of output,
`clippy --all-targets -- -D warnings` clean, `cargo test` **870/0**, `--no-default-features
--all-targets` clean. `manifest_view.rs` and `http_port.rs` were fmt-clean on the first pass; only
`interpreter.rs` needed it.

**The `finally` was the whole design problem.** `generateText` ends in a `finally` (`:421-437`) that
fires on every exit, reporting the reassembled tool calls and then the usage. Rust has no `finally`,
and `Drop` cannot stand in — the callbacks are `&'a mut dyn FnMut`, so a consumer that drops the
stream leaves `Drop` nothing callable and the borrow would not outlive the value anyway. The port has
an idempotent `TextStream::flush()` called at every exit the loop can reach and **before** a mid-stream
error is handed over.

**`HttpPort` is its own module for the one-way-edge reason `adapter.rs` is** — `egress.rs` will
implement it, `interpreter.rs` consumes it, so putting the trait on either side would make the other
depend on the whole of it. **`HttpResponse` is deliberately not the TypeScript's one object:** it fills
`body` for a unary request *and for a streaming request that failed*, and `lines` only for a stream that
succeeded, because a `>= 400` on the stream path (`manifest-interpreter.ts:304`) is the single case
where the request's choice and the caller's need differ.

**The read model is not the grammar, and the two want opposite strictness.** `adapter-spec/src/manifest.ts`
is 193 lines of zod that validates, applies defaults and enforces `superRefine` rules — it is the gate an
AI-generated manifest passes. The interpreter reads a manifest that has *already* passed it, so
`manifest_view.rs` must **ignore unknown fields** — the exact opposite of this repo's
`deny_unknown_fields` rule for boundary payloads. A stored manifest is a superset; a payload is a
contract.

**Increment 15's own scope note was wrong, and it was corrected rather than quietly patched.**
`parse_retry_after` / `retry_after_from` (`manifest-interpreter.ts:191-204`) are pure functions the class
calls and were never ported, although that note said every pure function the class calls was present.
The note was rewritten to *enumerate* what the module holds rather than summarise it. **The date branch
of `Retry-After` is a recorded absence:** the source's second branch is `Date.parse(v)`, a superset of
RFC 9110 this crate has no parser for, so an unreadable value returns `None` and the caller falls back
to `engine.rs:1168`'s cooldown floor — asking for nothing rather than setting a cooldown nobody chose.

I wrote `regex = { default-features = false, features = ["std"] }` and recorded that `perf` and

compiling *at runtime*. `Cargo.toml` now declares a plain `regex = "1"` with the reasoning in a
comment. **Stating the requirement is what keeps a future dependency change from moving it.**

### And the assumption underneath was wrong in a way only a test could show

The design was `unicode` off, so `\d`/`\w`/`\s` are ASCII and match JavaScript. A test asserting that

the `Regex` type refuses a pattern that can match invalid UTF-8 —
`RegexBuilder::new("^dall-e-.*$").unicode(false).build()` → *pattern can match invalid UTF-8*.

The trade is refused deliberately: **a class divergence on input that cannot occur beats a hard
failure on input that does.** What remains is measured and pinned in both directions — for ASCII input
every construct agrees with JavaScript (`.` is the one reachable exception, matching `\r` where
JavaScript's does not); for non-ASCII input `\d` and `\w` part company, `\b` following. Recorded
rather than papered over with a pattern rewriter, which would trade a known difference for an unknown
defect.

### Five coercion surfaces measured with node before any Rust was written

`String(x)`, `Number(x)`, `Boolean(x)`, `.length`, and the auth-header regex. Three divergences a
natural port would have introduced came out of it:

- **`\b` is ASCII in JavaScript and Unicode in Rust**, so the naive port makes the lint *weaker* than
  its reference: `/\bWebAssembly\b/.test("éWebAssembly")` is `true` in JS, while Rust finds no boundary
  and lets the source through. Fix: scoped `(?-u:\b)`. `unicode(false)` globally is **not** available
  for it — it makes `.` byte-oriented and `Regex` then refuses any pattern containing one, the same
  refusal `core::modality` recorded.
- **`.length` counts UTF-16 units.** `chars().count()` keeps an id the reference drops; `s.len()` drops
  one the reference keeps. Three candidate metrics, three different catalogues.
- **`Number(status)` can be `NaN`, `-1`, `1.5` or `1e21`**, none of which a `u16` holds, so the
  narrowing rule is stated rather than inherited. `NaN` → `0` is not a silent coercion: it is the same

### The finding — D30

§2.1.3 said `AdapterInstance: Send + Sync` was satisfiable "under `parallel` only". The first half
reproduces: `Runtime` and `Context` do get both bounds. **The second half is missing.** A probe
asserting the bounds failed with `error[E0277]`, for two independent reasons:

- `Persistent<T>` carries `rt: *mut JSRuntime` (`persistent.rs:37`) — the *wrapper* is `!Send`/
  `!Sync` whatever `T` is.
- `T` reaches `NonNull<JSContext>` (`context/ctx.rs:74`, via `Value`'s `Ctx`) and `*mut c_void`
  inside `JSValue`'s `JSValueUnion`.

So `Ctx`, `Value`, `Object`, `Function` and `Persistent<T>` are all `!Send` **and** `!Sync` in both
directions. The adapter therefore cannot hold its runtime, its compiled guest or its parked
resolvers as fields — and that shape fails at the `Arc<dyn AdapterInstance>` coercion, not at the
definition, so it is found late. The `Send + Sync` handle must be a **channel to a thread that owns
them**: an actor. Recorded as D30 (Half, Open) and written into §2.1.3 with the plan change.

That also answers half of §2.1.3's "largest remaining unknown". `Context::with` is synchronous and
holds the global lock, so the pump and the egress `await` cannot share one scope: an operation is a
sequence of short synchronous scopes separated by awaits on the actor thread, and anything surviving
a scope boundary crosses as a `Persistent` or a dumped `serde_json::Value`. Note `rquickjs-core` has
**no `serde_json` dependency at all**, so that dump is code to write, not a built-in bridge.

## Increment 19b — `core/js_host.rs`, the actor

`JsSandbox` (spawn/call/dispose), `JsHost` (compile/drive), the deferred-promise bridge over `HttpPort`,
`dump` as a recursive walk, 14 tests. Rust **943 → 957**. Gate green: fmt, clippy, 957/0, `--no-default-features`.
Book: **204 ids / 506.0 KB**, 127 links, key-leak OK.

### Six findings, three from probes, two from tests, one from clippy

1. **`resolve_answered` must run before `pump`.** Reversing it (probe A) makes the verbatim guest timeout:
   the resolve queues the guest's continuation as a job, a pre-resolve pump leaves it undrained, and the
   driver then finds `parked` empty → `Timeout` for a guest one job away from finishing.

2. **`Promise::result` on rejection returns `Err(Error::Exception)` and the reason must be caught with
   `Ctx::catch()`.** Treating the `Err` as the reason reports every rejection as "exception". This is the
   `value/promise.rs:107-113` behaviour.

3. **`is_function` must precede `is_object`.** The latter is a raw `JS_TAG_OBJECT` check that functions
   also satisfy, so `f: () => 1` dumps as `{}` without the guard. Caught by `the_dump_walks_rather_than_stringifies`.

4. **`armed` is a second spelling of one state — removed.** A probe showed the whole suite passes with the
   `AtomicBool` guard deleted: `deadline_ms == u64::MAX` already makes the comparison false for every clock
   reading. The flag, its two `store` calls, and the `AtomicBool` import were all removed. This is exactly
   the "`NULL` ≠ `0`" defect class: two spellings of one state.

5. **`Runtime` has no `memory_limit()` or `max_stack_size()` getters in 0.9.0.** The only observable
   consequence of the memory limit is the `SIGSEGV` of §2.1.3 trap 3, which cannot be tested in-process.
   The stack limit *is* observable, and `runaway_recursion_is_contained_on_the_actor_thread` asserts it.

6. **`std::thread`'s default stack is not a contract.** `RUST_MIN_STACK` overrides it. Probe B1: `ACTOR_STACK_BYTES`
   reduced to `STACK_LIMIT / 2` (256 KB) → `SIGABRT` on thread `js-sandbox`. Probe B2: explicit size removed +
   `RUST_MIN_STACK=262144` → same `SIGABRT`. Control: explicit size restored + same env → PASS. So the
   explicit `.stack_size` is load-bearing, not decorative.

### S6g — containment off the main thread

Added to the spike. S6f ran on the main thread (8 MB C stack). The actor runs on a `std::thread` (2 MB
default). Measured: 256 KB → `SIGABRT`, 512 KB → contained, 768 KB → contained, 1 MB → contained,
2 MB → contained. `ACTOR_STACK_BYTES = STACK_LIMIT * 4` keeps the 4× margin.

## Increment 20a — `core/code_adapter.rs`, the manifest half of the sandbox

`CodeAdapterInstance` implements all seven `AdapterInstance` members over one `JsSandbox`; 13 tests;
Rust **957 → 971**. Gate green: `cargo fmt --check` exit 0/0 bytes, `clippy --all-targets -D warnings`
0 findings, 971 pass, `--no-default-features --all-targets` compiles.

### Four findings

1. **`dispose` must take `&self`, and the seam is why.** `AdapterInstance::dispose(&self)` cannot call
   a `&mut self` join. Wrapping the sandbox in a lock does not work either: `call` is async, so a
   `std::sync::MutexGuard` across an await is a `Send` error, and a `tokio::sync::Mutex` cannot be
   locked from a synchronous `dispose`. So `JsSandbox.thread` became `Mutex<Option<JoinHandle<()>>>`
   and `dispose(&self)` locks only for the join; `take` keeps it idempotent.

2. **A queue created on a thread nothing else can name is dead code.** The `log` buffer was first
   built inside `JsHost::compile`; `JsHost` never leaves the actor thread, so the field had no reader
   and clippy would have failed it. The `Arc` is now created in `spawn`, cloned into the actor, and
   kept on `JsSandbox`; `drain_log_lines` is copy-and-clear because `log` is a global the guest may
   call between operations.

3. **The two adapters disagree about "rate limited", and both are the reference.** The interpreter's
   `ping_key` tests `status == 429`; the code adapter's tests `/429/.test(msg)` — a **substring** of
   the rejection message (`code-adapter.ts:610`). A guest throwing `"upstream said 429"` is reported
   `429`/`rate_limited` with no HTTP status anywhere. Probe: hard-wiring `rate_limited = false`
   reddens `ping_key_reads_429_out_of_the_message` (`left: 0, right: 429`).

4. **`manifest::AuthHeader` and `sandbox::AuthHeader` are the same struct twice** — identical fields,
   each rendering the same `{{secret}}` rule into a different container (`BTreeMap` for the
   interpreter, order-preserving `Vec` for the sandbox), and disagreeing on a duplicate name. The
   four-line conversion lives in one function; the duplication is recorded, not collapsed.

### Two gaps stated, not closed

- **`generate_text` is buffered, not streamed** (20b). It runs the operation to completion and then
  yields the collected lines: same text, delivered late. True streaming needs the actor to forward
  chunks mid-operation — a chunk channel on `Command::Call`.
- **A code provider reports no usage and no tool calls.** `code-adapter.ts` never calls
  `args.onUsage`/`args.onToolCall`, so both `TextArgs` callbacks are dropped and the spend cap
  cannot bite for such a provider.
