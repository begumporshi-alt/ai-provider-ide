### Per-app budgets: the documented gap understates the work

`09-status.md` said "Per-app keys exist; per-app limits do not". Measured against the live DB, that is only
half the story — **there is no per-app attribution either**, so a budget would have nothing to sum.

The trap is a name collision. Two different things are called `key_id`:

| | What it is | Join |
|---|---|---|
| `ledger.key_id` | the **provider credential** (`api_keys.id`), e.g. `2f4b37eb-…` | **713** of 792 gateway rows |
| `gateway_keys.id` | the **gateway app key** the client presented, e.g. `ak-fc85350a2fb1dc67` | **0** rows |

The ledger's 16 columns contain no app-key column at all. The first join I tried — `ledger.key_id IN (SELECT id
FROM gateway_keys)` — returned **0**, which reads as "no attribution" but was really "wrong table". The second
join against `api_keys` returned 713/792 and settled it.

So the work is three parts, and the first is a prerequisite nobody documented: (1) migration 0016 adds
`app_key_id` to the ledger **and the TS router must start passing it** — a column alone proves nothing, which

## Tier 2 — summarization — also landed

compressWithSummary replaces dropped turns with a compact summary. Key design decisions:

- **One implementation, not two.** Both gateway and assistant converge on `router.generateText`, so the trim
  lives there once. The assistant gets Tier 2 via `opts.summarize`; the gateway stays on Tier 1 (stateless,
  latency-sensitive).
- **`skipCompression: true` on the inner call.** Without it, compressing would trigger a summary, which would
  compress — an unbounded chain. This is the only thing breaking it.
- **The summary lands in the system prefix,** so it survives any later trim. Tested directly.
- **Failure degrades.** A throwing or empty summarizer falls back to Tier 1 truncation. Tested by flipping
  the code: without the catch block, 1 test fails; with it, all pass.

The assistant wires `createSummarizer` into every agent turn via `generate: (req, opts) =>
router.generateText(req, { ...opts, summarize: createSummarizer(chosen) })`. The summarizer calls the same
model with a dedicated prompt, capped at 300 tokens out and 12K chars in.

router-core 265 → **273** tests. Gate green. Committed `2f8e0dd` + `934a6bb` + `8795cd5`.

## Per-app budgets — parts 2 and 3, landed

Migration **0017**, the enforcement, the UI, and six browser specs. 15 files, +~700.

**The design decision worth recording: the two caps are independent, not narrowed.** The obvious
implementation is to compute `min(global_remaining, app_remaining)` and enforce one number. That is wrong, and
wrong in a way that only shows at scale: with a **$10 global** cap and a **$100 per-app** cap, an app that
spends $50 has breached the global limit while sitting at half of its own. A single narrowed number cannot
express "this app is fine, the install is not". So `SpendLimits` carries **two pairs** — `(total_micros,
total_cap_micros)` and `(app_micros, app_cap_micros)` — and `spend_gate` checks them **sequentially**, global
first.

**And the two refusals stay distinguishable** (`spend_cap_exceeded` vs `app_budget_exceeded`) even though both
are `402 insufficient_quota`, because the remedies are opposite: one says "raise the global cap", the other says
"raise *this app's* budget". A caller that cannot tell them apart cannot act.

**`NULL` is the only representation of "no cap".** `gateway_key_cap_set` normalizes `<= 0` to `NULL` rather
than storing a zero. The alternative — `NOT NULL DEFAULT 0` — collapses "not reported" and "explicitly zero"
into one value, and two spellings of one state is the defect the project already recorded for 0015. A test
(`clearing_a_per_app_cap_stores_null_not_zero`) exists for exactly this, and it is the *only* test that can see
it: the behavioural test passes either way.

**The index ships in 0017, not 0016, and 0016 says why.** 0016 declined to ship a column with an index for a
query nobody had written. 0017 is that query. `idx_ledger_app_key_ts` on `ledger(app_key_id, ts)`.

### The finding that shaped everything: `codesign --verify` proves nothing

Measured against an ad-hoc bundle:

    codesign --verify --deep --strict --verbose=2 /tmp/adhoc-test.app
      /tmp/adhoc-test.app: valid on disk
      /tmp/adhoc-test.app: satisfies its Designated Requirement
      exit 0

An ad-hoc signature **is** a valid signature. A verifier that stops there is decoration. What actually
separates the two states: `spctl` (exit 3 vs 0 — `rejected` vs `accepted` + `source=Notarized Developer ID`),
`stapler validate` (exit 65 vs 0), the `CodeDirectory` flags word (`0x2(adhoc)` vs `0x12a00(…,runtime)`), the
`Authority=Developer ID Application:` chain, and `TeamIdentifier` (`not set` vs a real team).

Two measurement errors corrected along the way, both of which would have produced a wrong rule:
- The flags word sits **on the `CodeDirectory` line**, not on a `flags=` line of its own — a grep for `^flags`
  matched nothing, which I nearly read as "Chrome has no hardened runtime".
- **`$?` after a pipeline is the last command's status, and `PIPESTATUS` is empty in zsh.** Both printed
  `exit=0` for a command that had in fact exited 3 and 65. Re-measured with `out=$(cmd 2>&1) || rc=$?`.

## Pushed — and the badge lied until the commit was checked

`8795cd5..5757c52` → `origin/main`. CI run **#81** for `5757c52` finished `status=completed, conclusion=success`.

**The badge was not evidence about this push.** `.../ci.yml/badge.svg?branch=main` said `<title>CI - passing</title>`
while run #81 was still `in_progress`, because the badge reports the latest **completed** run — #80, on the
*previous* commit. A green badge immediately after a push is therefore consistent with your run still running
and with your run being red. It only becomes evidence once the run for **your** head SHA is completed.

So the check is keyed on the SHA, not on the branch status. One unauthenticated call:

    api.github.com/repos/<owner>/<repo>/actions/runs?per_page=6
    -> #81 5757c52 in_progress null      <- ours, still running

to a correct one, so the same query was run with `?status=failure`, and it returned three real runs — **#72

is what makes it a working control rather than a plausible-looking one. Then the run was polled by id
(`.../actions/runs/35835859285`) until it completed.

turned out to be hard to key reliably: the run number and the status token are far apart in the row, so "the

## `core/` no longer compiles Tauri at all — the `app` feature (commit `031ae4f`)

Phase 1 made `core/` Tauri-free in **source** only. Deviation 2 of `10-headless-service.md` §2.1.1 said so and
deferred the fix to Phase 2. Done now, because the CI payoff was immediate.

**The change.** `Cargo.toml` gained `[features] default = ["app"]` with
`app = ["dep:tauri", "dep:tauri-plugin-opener"]`, both deps became `optional`, and the app `[[bin]]` got
`required-features = ["app"]` (without it, a feature-less build still compiles `src/main.rs`, which calls the
gated `run()`). `build.rs` reads `CARGO_FEATURE_APP` and skips `tauri_build::build()` without it. Every `tauri`
mention in `core/` sits behind `#[cfg(feature = "app")]`.

**The trap that cost the first compile — 29 × E0277, one root cause.** `From<rusqlite::Error> for CommandError`
lived in `tauri/commands.rs`, but ungated `core/persist.rs` accessors use `?` on rusqlite results. A trait impl
is visible crate-wide regardless of which module it is written in, so **it worked by accident while the feature
was on** and vanished the moment the glue was gated out. Fix: move the impl *and* its redaction helper
`ui_db_error` to `core/error.rs` — neither names a glue-side type (`StoreError` and `rusqlite::Error` are both
core deps), so the module's own stated rule ("conversions that mention glue-side types stay in
`tauri::commands`") puts them there. The 4 glue-side tests now call `crate::core::error::ui_db_error`.

**The dead-code cascade was shallow, and gating it is correct rather than cosmetic.** Gating the 28 command
attributes plus `egress::stream()` left **15** warnings: 14 app-only helpers in `persist.rs` (or the constants
they clamp with) and `egress::UPSTREAM_IDLE_TIMEOUT`. Gating those left **1** (`serde_json::{json, Value}`
unused), then **0**. The warnings were the app-only half of `core/persist.rs` showing through — exactly the
coupling the split exists to expose.

**Evidence (the claim needs all of it).**
- `cargo tree --no-default-features --edges all | grep -ci 'webkit|wry|gtk'` → **0**; runtime `tauri` absent.
- `cargo build --bin aiproviderd --release --no-default-features` → `aiproviderd 1.0.0`, **4,073,968 B** vs
  **4,454,336 B** with default features. The 380 KB is Tauri not linked — independent corroboration.
- `cargo test` → **489 passed / 0 failed** (unchanged); clippy `--all-targets -- -D warnings` and `fmt --check`
  clean; `cargo check --no-default-features` warning-free.
- `tauri build --bundles app` → exit 0, 2m37s; bundle still holds both binaries.

**`cargo tree --bin X` does not show build-dependencies.** The first check used it and reported 0 tauri lines
while `cargo build` was compiling `tauri-build`. Use `--edges all` (or `-e build`) before claiming a crate is
absent. `tauri-build` **cannot** be gated: Cargo has no optional build-dependencies.

**The CI job proved nothing, and `default = ["app"]` would have let it keep proving nothing (D15).**
`headless-service` ran `cargo build --bin aiproviderd --release` with default features — which, before the
feature existed, built exactly what every other job built. Now it passes `--no-default-features` and the
GTK/WebKit apt packages are gone from it. Deliberately **not** `-D warnings` yet: `--no-default-features` is
warning-free on macOS, but macOS-only code cfg'd out on Linux can surface dead-code lints macOS never sees, so
tightening waits for a Linux run to show its own lint set.

**Three more unvalidated counts corrected** (fourth time this class has bitten): "32 `#[tauri::command]`
handlers" is **28** (four were doc-comment mentions), "9 references" in `gateway_tests.rs` is **8** (one was a

## The release verifier read the bundle, not what was inside it (commit `f60e9da`)

Followed the obligation recorded earlier the same day: `aiproviderd` is copied into `Contents/MacOS/` by
`tauri build` with nothing declaring it, and a Developer ID release must sign **every** Mach-O.

**The gap.** `verify-release-signature.sh` asserted five properties of the `.app` — not ad-hoc, Developer ID

`GatewayCore` owns `Arc<dyn Bridge>` and the reply path is `GatewayCore::reply`, so a bridge must reach
the core that owns it. `SynthBridge` did that with `Mutex<Option<Arc<GatewayCore>>>` filled by a

trait never mentioned. Forgetting it compiled and failed silently: `dispatch` panicked inside a detached
`std::thread` that nothing joins, so the request waited out `FIRST_MSG_TIMEOUT` and answered a generic
503.

**The fix is a parameter, not a stored handle.** `ReplyHandle` (`Clone`) holds only
`Arc<Mutex<HashMap<u64, UnboundedSender<BridgeMsg>>>>`; `Bridge::dispatch(&self, req, replies)` takes
one; `GatewayCore::dispatch(req)` supplies it; `GatewayCore::reply` delegates to the same map. A stored
handle is the same defect in another shape — still a step, still forgettable. **The cycle is not merely
absent, it is unrepresentable:** `dispatch(&self)` has no `Arc<Self>` to put into the handle, and
`new_with_key_wait` builds the handle *before* the `Arc` exists. The construction order forbids it, so no
later edit reintroduces it by accident.

the bridge a *fresh* handle instead of the core's — the two-maps defect — fails the end-to-end test after

## Phase 2 increment 5 — the per-provider limiter (audit R3)

**New file `core/limiter.rs`, not another section of `engine.rs`.** 22 tests. `cargo test` 519 → **541 / 0**.

**This one adds a behaviour rather than relocating one, and that is the finding.** A Grep over
`apps/desktop/src-tauri` for `per_provider_concurrency` returned **nothing**: R3 is implemented in
TypeScript only, so the Rust gateway has the one global semaphore (`permits`, 8+32) and none of the
per-provider isolation it exists to provide — which is exactly the starvation `concurrency.ts`'s own
header describes. The plan's "no behaviour change" constraint does not apply in the usual direction
here, because there was nothing to preserve.

**Why a separate file.** `engine.rs` is the port's *pure* half — a taxonomy and two arithmetic folds,
no state. `ProviderLimiter` is the only one of the six dependency modules that is **shared mutable state
across threads**, and its hazard (the check-then-act race) is a different hazard from anything in
`engine.rs`. Group by *kind*, not by which TypeScript file a piece came from.

**Three deliberate differences from the original.**

1. **RAII release.** TS returns `(() => void) | null`; a caller that ignores it holds the slot for the
   process's life and nothing reports it. `Permit` releases on `Drop`. `release()` stays callable and
   idempotent so the double-release case remains representable, and `Drop` calls that same method.
2. **One lock for check *and* increment.** `concurrency.ts:75-76` is a check-then-act, atomic only
   because JS is single-threaded. `has_capacity` is now documented **advisory** — rewriting `acquire`
   as `if !self.has_capacity(p) { return None }` is exactly how the race returns.
3. **The cap is `usize`.** TS `-1` satisfies `maxPerProvider <= 0` and so behaves as *unlimited* while
   displaying as a bound. The type removes it; `clamp_concurrency` still rejects a stored negative
   because the stored value is untrusted.

**My own four tests failed on the first run, and that was the port announcing itself.** I wrote
`assert!(lim.acquire("p1").is_some())`, which binds the `Option` and drops the `Permit` at the end of
the statement — so the slot came straight back. An ignored acquire *holds* in TypeScript and *releases*
in Rust. The failure mode is **fail-open, not fail-closed**, and `Option` being `#[must_use]` makes the
careless call site a compiler warning anyway.

**The finiteness check is load-bearing, not defensive.** `"Infinity"` parses to `f64::INFINITY` and
`"NaN"` to `f64::NAN`, and **`f64::min` ignores a `NaN` operand** — so without the check both clamp to
`MAX_PER_PROVIDER` (64) instead of the default (4), turning a corrupted string into the largest cap the
program allows. Deleting it fires the named test. The general rule: before calling a check defensive,
delete it and watch — if the named test fires, it was the guard.

**D18 — a test named for a property that does not test it.** `release is idempotent — a double release
cannot leak capacity` (`concurrency.test.ts:134-142`) **passes with the `released` flag deleted** from
`concurrency.ts:77-80` — measured, `vitest run -t "release is idempotent"` → 1 passed / 272 skipped.
With a cap of 1 the count is already 0 and the entry already deleted after the first release, so the
extra calls take the "delete at zero" branch and change nothing. The property only bites with **two**
permits held, where a double release drops the count 2 → 0 while the other is still in flight. The code
is correct; the test's claim is broader than its check. Ported for fidelity, marked weak in place, and
carried by `an_explicit_release_followed_by_drop_counts_once` (cap 2) — whose falsification fires.

**Six falsifications, all fired, restores byte-identical.** Splitting check from increment into two
locks fails the concurrency test **5 of 5 runs** — the test is exact rather than statistical, because
no permit is released until all 64 threads have decided, so the simultaneous-holder count is precisely
the cap for a correct implementation and can only exceed it for a racy one. Also fired: removing the
`released` guard, clamping a negative to zero, flooring zero to one, removing `impl Drop`, removing the
finiteness check.

**One documented divergence.** `Number("0x10")` is 16 in JS; `str::parse::<f64>()` rejects it, so hex
and octal strings fall back to the default. Tested rather than left implicit — a port that differs
silently is worse than one that differs loudly.

**Preserved for the loop port:** a skipped candidate is reported `RATE_LIMITED`/`429`
(`execution-engine.ts:85`, `:169`) even though the provider was never contacted. The reported chain
therefore cannot distinguish "we never tried" from "the provider said 429" — a fidelity gap, not a bug,
and Phase 3 inherits it.

**Still parked:** the attempt loop (needs `route_planner`'s `Candidate`, Phase 3) — which is also this
limiter's only consumer, so nothing in the shipping gateway consults it yet — and the streaming half.

## Verifying an external three-part risk assessment against the code

Tushu pasted a three-part engineering risk assessment (rquickjs/Boa sandbox, recursive context
compression, launchd KeepAlive) and asked whether it was true. I verified each claim against the repo
rather than answering from general principles. **Two of the three areas are generically plausible but
aimed at the wrong problem for this codebase; one is correct and was already recorded in the plan.**

### 1. Sandbox — the reasoning is inverted here

The sandbox today is QuickJS-**WASM** via `quickjs-emscripten` (`code-adapter.ts:41-49`), in TypeScript.
`rquickjs`/`boa` are *candidate Rust replacements* — an open decision the plan already records
(`10-headless-service.md:895`, `:948-951`, `:995`). The assessment's headline risk ("lacks web API
coverage — `fetch`, `TextEncoder`, `URL`") is a non-issue: the sandbox **deliberately has none of
them**. `code-adapter.ts:20-24`: "No filesystem / DOM / Node / import / eval exist in QuickJS at all";
the guest gets exactly two host functions, `http(req)` and `log(string)`, and the lint bans
`import(`/`require`/`Function(` as a tripwire. The `execute_pending_jobs()` concern is already solved by
design, and documented as a *rejection* of the alternative (`:26-29`): "Why the SYNC QuickJS variant + a
job-pump (not ASYNCIFY)".

**The real risk it misses:** the sandbox's *limits* are the contract — 64 KB source, 45 s wall clock,
32 MB heap, 512 KB stack, 20 http calls, 400 emitted lines, 8 MB body, plus the quickjs-emscripten
handle-ownership rules. Reproducing those in a new engine is a bigger surface than ES2020 completeness,
and `code-adapter.test.ts:3` says those tests "pin the security" properties.

### 2. Recursive compression — two of its checkable specifics are false in this repo

`skipCompression` is real (`model-router.ts:108`, `:134`, `Assistant.tsx:100`). But the plan's own note
cited `gateway-bridge.ts:102`, and that file contains **no** `skipCompression`/`compress`/`summar` at
all — the citation points into a doc comment about `GATEWAY_WINDOW`. And the same sentence claimed "the
same flag exists in the Rust port", while `src-tauri` has **no compression path whatsoever** (Grep for
`compress`/`summari[sz]` → one unrelated comment; `trim`/`compact`/`drop_turn`/`reduce_context` → only
string `.trim()`). Both fixed; recorded as **D20**. The substantive point stands: the failure mode is a
lock held across the recursive call, and an inner request context that resets the guard — the same "a
field on one side is not wiring" family already in the register.

### 3. launchd — correct on mechanism, already recorded, but its remedies beat the plan's

launchd is unbuilt (`:84` "Process manager | None"). The planned plist points `ProgramArguments` at an
absolute path **inside** the bundle, so the path-tracking concern is accurate, and `KeepAlive` is
`SuccessfulExit=false` so a failed exec can loop. The plan already had the risk (`:897`) and the open
unknown (`:1000`) — but its mitigation ("check the path and rewrite the plist") is the **weakest** of
the available options. Adopted the assessment's stronger remedies into the risk row: a fixed path
**outside** the bundle or a stable symlink; or `launchctl bootout`/`bootstrap` around the swap. Added
the `KeepAlive` **throttle** detail the plan omitted — repeated failed execs can leave the job disabled,
so a briefly-missing path is not self-healing.

### The lesson

**A generic risk assessment is a list of questions, not a list of findings.** Each item had to be
resolved against this repo, and two of the three resolved *differently* from how they were presented —
one inverted (the missing web APIs are a design *property*), one already recorded (with a weaker
mitigation that was still worth improving). **Answering "is this true?" from plausibility would have
confirmed three plausible things and caught neither falsehood.**

### The option the plan never considered

§4.3 ("Why not a Tauri sidecar") rejects the **Tauri sidecar** — correctly, since a sidecar is launched
and killed by the app, and the service must outlive the UI. But the plan nowhere considers **running the
existing TypeScript engine in a standalone Node process under launchd** — same lifecycle as
`aiproviderd`, no port at all. That would satisfy the actual goal (webview independence) in days rather
than months, at the cost of shipping a Node runtime (~50 MB) and keeping two languages.

### The adapter layer is the real fork

Rust already has hand-written dialect adapters (`gateway_anthropic.rs`, `gateway_gemini.rs`,
`gateway_responses.rs`) at the HTTP edge, while TS is manifest-driven (one interpreter + per-provider
manifests). Porting the interpreter into the same binary risks **two mechanisms for provider
adaptation**. The plan's own fallback (`:895`) — keep Tier-2 code adapters in a subprocess — sidesteps
both that risk and the rquickjs-immaturity risk. The seam worth taking: **declarative in-process,
executable out-of-process.**

## Will compression work? Measured, and the plan's guard is the wrong shape

`context-compress.ts` splits cleanly, and the split is better news than the plan implies.

**Tier 1 is pure and ports like increments 1–6.** `estimateMessageTokens`, `estimateTokens`,
`promptBudget`, `compressMessages`, plus `DEFAULT_CONTEXT_WINDOW = 8192`, `CHARS_PER_TOKEN = 4`,
`RESERVE_FRACTION = 0.25`. Arithmetic and list slicing — no async, no locks, no recursion. Four tests
already exist to port against ("hands the summarizer exactly the messages that were dropped", "does not
call the summarizer when nothing was dropped", "falls back to plain truncation when the summarizer
throws", "falls back when the summarizer returns nothing usable").

**Tier 2 is ONE function, and its failure mode degrades rather than fails.** `compressWithSummary` is the
only async export, and `:217` states the contract: "**Failure degrades, never propagates.** A summarizer
that throws, or returns nothing, yields [plain truncation]." So a bug in the summarizer costs summary
quality, not availability — a much smaller blast radius than "infinite recursion until stack
exhaustion".

**Two changes to the plan's approach:**

1. **Make the recursion guard structural, not a flag.** The TS sets `skipCompression: true` on the inner
   request; a flag is a runtime check that can be forgotten, and D20 is evidence that even its
   *documentation* was wrong. The summarizer should call an entry point that has no compression step at
   all, so "forgot the flag" is not expressible — the same move as increment 3's `ReplyHandle`.
2. **The deadlock hazard is real here, and precisely.** `store.rs:504` is `pub conn:
   Mutex<Connection>`, and the existing habit is lock → synchronous SQL → drop (`capture.rs`,
   `egress.rs` — **no lock is held across an await anywhere**). A port that writes
   `let conn = store.conn.lock(); … await summarizer() …` re-enters a non-reentrant mutex and blocks
   forever. **The precision the assessment lacks:** `std::sync::MutexGuard` is `!Send`, so on a
   multi-threaded runtime with a `Send` future the *compiler* rejects it — you get a compile error, not
   a hang. It is only a live deadlock on a current-thread runtime. So do not rely on the compiler; keep
   the lock scope synchronous.

**Can the whole thing be deferred? Yes, and it should be said plainly.** The product does not depend on
it today: the app ships, the gateway serves, and `hide_on_close` defaults to **true** (D10), so closing
the window already leaves the gateway running. What deferring costs is availability when the app is
genuinely quit or crashes — robustness, not function. **The headless service is a robustness
improvement, not a blocker.** The two things not to defer are the doc corrections (done) and the
adapter decision (a cheap-now, expensive-later fork).

## The book contamination, and the guard that was written down and skipped

**What happened.** Commit `b448404` captured `docs/dev-book/book.html` carrying **6,540** `data-page-node-id`
occurrences. The generator never emits the attribute (`grep -c data-page-node-id scripts/build-dev-book.mjs` → 0);
whatever renders the file injects it. `REFERENCE.md` already documented this phenomenon *and* the exact guard for
the exact window ("the rewrite can land between `git add` and `git commit`") — and the guard was not run. Third
occurrence, second time in two sessions.

**Fixed two ways.** The artefact: `c07d0f2` regenerates it (196 ids, 363.8 KB, 0 occurrences). The process:
`scripts/git-hooks/pre-commit` now refuses a staged `book.html` carrying the attribute, installed with
`git config core.hooksPath scripts/git-hooks` and documented in `CONTRIBUTING.md`. Falsified both ways — a
contaminated staged change is refused with HEAD unmoved, and the repair then reports "nothing to commit", which is
also the proof that the generator reproduces HEAD byte-for-byte.

**Why a hook and not a gate step.** `pnpm ci:local` runs `docs:book`, which *regenerates* the file, so a gate-time
check would pass while the staged copy stayed contaminated. The only reliable moment is between staging and the
commit object.

**The test that lied, and what it taught.** The first version of the hook was tested by staging HEAD's own
contaminated bytes. `git diff --cached` compares the index against HEAD, so identical bytes produce no diff, the
file is not listed, the guard returns early, and the mutation did not fire — the guard looked broken when the
*test* was. Two durable facts: (a) `git diff --cached --name-only` is a predicate for *changes*, not for
*participation*, so a guard that must see an unchanged file cannot be built on it; (b) the hook's real boundary is
now written in its own comments — it prevents new contamination and cannot repair an already-contaminated HEAD,
which is a separate one-time command.

## Increment 9 — the text half of the adapter seam (2026-09-23, later)

**What landed.** `core/adapter.rs` gained `ToolCall`, `TextArgs<'a>` and `AdapterInstance::generate_text`, so the
seam is whole for both members the engine calls. `cargo test` **575 → 583/0** — eight tests, not the seven the
increment was scoped for.

**The decision was pull vs push, and the crate had a precedent for the wrong one.** The engine's other text path is
`ReplyHandle` + `mpsc` (push). `generate_text` returns
`BoxFuture<Result<BoxStream<'a, Result<String, AttemptError>>, AttemptError>>` — pull, matching the TypeScript's
`AsyncGenerator`. The reason is cancellation: a pull stream is driven by the engine, so the engine owns the stop
rather than every adapter remembering a flag. The two-phase return is the design, not an implementation detail:
awaiting the future is the response phase (a refusal is `Err`), polling the stream is the mid-stream phase (a break
is `Err` as an *item*, because the consumer already holds text and a clean `Err` would invite the retry that
duplicates it).

**The compiler produced the increment's best evidence, unasked.** Adding the trait member broke exactly one
implementor outside the new code — the image double at `engine.rs:1539` — with `E0046`. That is the method-shaped
twin of increment 8's exhaustive struct literal, and it is the reason neither method has a default body: a default
would make the next such addition silent. The forced decision (what an image-only adapter does when asked for text)
is now written down instead of surfacing as a runtime surprise in whichever test reached it first.

**A `Result` whose Ok arm is a `BoxStream` cannot use `unwrap_err`.** `E0277: doesn't implement Debug`, on the type
you are *not* testing. `match` explicitly — which is also the stronger assertion, because it names the phase. Every
consumer inherits this, `execute_text` first.

**The double was wrong first, and no test could have caught it.** The first draft fired both callbacks while the
*future* resolved — the source's **non-stream** branch (`manifest-interpreter.ts:312-329`) — behind a `TextArgs`
whose `stream` field said `true`. The stream branch fires them in the loop's `finally` (`:424`, `:430`), after the
last chunk. Nothing failed, because the tests asserted the values delivered and not the moment. The consequence was
live rather than theoretical: a consumer that read usage without draining would have gone green here and failed
against every real adapter, and that consumer is the very next increment. Fixed by taking the callbacks and firing
them at exhaustion, once, in the source's order (tool calls before usage), plus
`the_callbacks_fire_when_the_stream_ends_and_not_when_the_future_resolves`, which asserts the **moment** — empty
after the future resolves, populated after the drain. This is why the count is 8 and not 7.

**Falsification: 8 mutations, 8 as claimed, every restore byte-identical.** Six red tests (response-phase refusal
flattened to an empty stream; mid-stream break hoisted into the response phase; classifier reading only the status;
unreported cache block flattened to zero; tool call losing its `arguments`; callbacks firing during the future) and
two compiler rejections (an implementor missing the member; `on_usage` reverted to a two-field payload). Four
anchors had to be rebuilt once the double changed — which is the point of the harness aborting on a
non-unique/absent anchor rather than reporting DID-NOT-FIRE.

**Deliberately not modelled: the abort guard.** The source flushes neither callback when `signal.aborted` (`:424`,
`:430`). The engine stops on cancellation before it can read usage, so a double that stayed silent there would
assert a branch no engine path reaches. Stated in the double's doc comment rather than left as an omission.

**Still open, and now the only thing left in Phase 2.** `engine::execute_text` — the loop over the seam — and with
it how a streaming loop owns the mutable state it must keep alive across its yields, since `execute_image`'s
`&mut HealthTracker` borrow (`:559`) cannot outlive the call. Three shapes: lend the state to the returned stream
(`execute_text<'a>(health: &'a mut HealthTracker, ..) -> BoxStream<'a, ..>`, so the caller cannot touch health while
draining), own it behind interior mutability, or take a sink. The TypeScript answers none of them, because a
generator borrows its enclosing scope for free — the one affordance Rust does not have.
