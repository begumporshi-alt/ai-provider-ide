# 2026-09-29 — A gateway that gates on the *client*, not the key

## The report, and what it actually was

The operator could not add `agentrouter.org`, by either path:

- **Auto setup** could not identify it.
- **Manual** produced: `key-01: the provider rejected this key — HTTP 401: {"error":{"message":
  "unauthorized client detected, contact support for assistance at https://discord.gg/HgekCyHJqB"},
  "message":"UNAUTHENTICATED","success":false,"type":"unauthorized_client_error"}. It is out of
  rotation until you enable it.`

Both symptoms are one cause. The gateway refuses the **client** before it reads the key.

## Measured — the ablation, credential held constant, only `User-Agent` varied

| `User-Agent` | Response |
|---|---|
| *(none)*, `curl/8.7.1`, `Mozilla/5.0 (…) Chrome/131` | `401 unauthorized_client_error` |
| `totally-made-up-client/9.9`, `xyzzy/1.0`, `a` | `401 unauthorized_client_error` |
| `claude-cli/2.0.0 (external, cli)`, `claude-cli/9.9.9 (external, cli)` | `401 new_api_error` — `无效的令牌` |
| `zcode`, `Zcode/1.0`, `XzcodeX`, `my-zcode-fork/1.0`, `zcode-cli` | `401 new_api_error` |
| `codex_cli_rs/0.1.0`, `opencode/1.0`, `cline/1.0`, `roo-code/1.0` | `401 new_api_error` |
| `claude-code/0.1.0`, `claude-cli/2.0.0` (no parens), `z-code`, `cursor/1.0`, `gemini-cli/0.1.0`, `kilo/1.0` | `401 unauthorized_client_error` |

**It is an allowlist of client families, not a blocklist of bots.** `Mozilla/5.0`, `curl` and a
made-up UA are all refused, so "send a plausible browser UA" is not a fix. The decisive row is the
third: with the client accepted, the *same dummy key* is judged on its merits as `无效的令牌`. So
rows 1–2 are evidence about the client and **none at all about the key**.

Also confirmed: `GET /models` (no `/v1`) returns the HTML SPA at **200** regardless of UA — the same
"New API" shape as Hcnsec, so the base URL must be `https://agentrouter.org/v1`.

**This falsified the hypothesis I carried in from the previous session**, which was "only the
Claude CLI UA flips it, so it is a UA-vs-browser distinction". `zcode` passes and `claude-code` does
not; a browser UA does not. The earlier single-point measurement was true and its explanation was
wrong — the lesson is the one already in `MEMORY.md`: a reason is a claim too.

## Four defects, one per layer

1. **The app sent no `User-Agent` at all.** Not in `egress.rs`, not in `interpreter.rs`'s
   `json_headers`, not in the TS `ManifestInterpreter`, not in any manifest. RFC 9110 §10.1.5 says
   one *should* be sent; here its absence was the direct cause of the refusal.
2. **`LIST_MODELS_ENDPOINT` had no `headers` field.** `generateText` and `generateImage` had one.
   `listModels` is the call every probe, ping and catalog refresh makes — so a header that reached
   only `generateText` left such a provider unreachable while looking configured.
3. **`verdictFor` mapped every `401`/`403` to `invalid`**, and `invalid` is *conclusive*: `store.ts`
   writes it and `HealthTracker.isKeyUsable` then keeps the key out of rotation. A working credential
   was disabled by a request that never examined it.
4. **The probe discarded error bodies**, so `fingerprint` saw nine shapeless `401`s, returned
   `unknown`, and — worse — still emitted "chat/completions endpoint exists" and "messages endpoint
   exists", which are vacuous on a host that answers `401` to every path.

## The fix

- `egress.rs`: `DEFAULT_USER_AGENT = concat!("AI-Provider-Router/", env!("CARGO_PKG_VERSION"))` on the
  credentialed `reqwest::Client`. One choke point — `EgressState::new` is what the app *and*
  `aiproviderd` each construct, so both request paths are covered.
- Grammar + Rust read model + both interpreters: `listModels.headers`, merged by `list_headers`
  (deliberately **not** `json_headers`, which inserts `content-type` unconditionally — wrong for a
  bodyless GET and a change to the catalogue request as a side effect).
- `client-gate.ts` (new, router-core): `detectClientGate` / `clientGateNotice`. **One authority**,
  consumed by `verdict.ts` and `probe-runner.ts` — two copies of one rule is this repo's most
  reliable defect.
- `verdict.ts`: a gate `401` is `unverified` (leave the key alone) with a notice that says the client
  was refused and the key was never judged.
- `probe-runner.ts`: reads a refusal body far enough to ask one question, keeps only the matched
  marker; `runProbes` accepts `extraHeaders`.
- `fingerprinter.ts`: checks for a gate **first** and returns early, suppressing the endpoint
  evidence a uniform refusal invalidates.
- `manual-manifest.ts` / `ProviderSetup.tsx`: **Custom headers** field → every endpoint;
  `headersToLines` hydrates it on edit; a header named like the auth header is refused.
- `Onboarding.tsx`: on a gate, a panel naming the marker + a header field + **Retry with these
  headers**, which re-probes and keeps the headers on the provider. The generator is deliberately
  **not** run for a gate.

## Empirical notes on the transport (both new)

- **hyper lowercases header names on the wire.** `User-Agent:` arrives as `user-agent:`. A test
  asserting the capitalised name fails against correct code. Match the *name* case-insensitively and
  assert the *value* exactly.
- **reqwest honours a per-request `user-agent` over the client default.** Verified, not assumed —
  and it is load-bearing: if the default won, the whole custom-headers feature would be inert for
  the one header it was built for, and every other test would still pass.

## Still open — the engine's taxonomy

**`ErrorClass` still classifies a gate `401` as `AUTH_FAILED`.** Consequence: the execution engine
will rotate through every key (pointless — all fail identically), and `ledger.error_class` fills with
`AUTH_FAILED` rows against a provider whose only problem is client identity, which is a *drift*
signal (`DRIFT_CLASSES`). Not fixed here, and deliberately not half-fixed: adding a variant means
`engine.rs`'s enum, the **fixed-size** `ALL_CLASSES: [ErrorClass; 10]`, `as_str`, `is_drift`,
`is_retryable_with_next_key`, the TS union, and the dev-book's cross-language contract — and
`10-headless-service.md` says a new class is a deliberate act. The measured harm is real and this is
the honest remaining gap.

## The alias table, and the second writer that changed the fix (same session)

The user authorised the recommendation from the message above: *"persist `auto`, or have
`refreshStaleCatalogs` re-derive auto rows while preserving genuine manual ones."* Both clauses
assume the auto/manual distinction is **knowable**. Scoping it turned up the thing that decides the
design.

### The recommendation's premise was incomplete, and one measurement supplied the missing half

I had already established that the Rust planner applies the same alias-first rule (`planner.rs:315-331`)
and does **not** derive aliases, so the table has to keep the derived rows — ruling out "stop
persisting them". What I had not checked is **who else writes the table**:

- `persistAliases` (`store.ts:595`) — derived rows.
- **`config_import` (`persist.rs:2316-2319`) — `INSERT OR IGNORE INTO model_aliases`, the aliases out
  of an imported snapshot.** A second writer, and its rows are *authored*, not derived.

And `model_aliases` has **four columns** (`alias, provider_id, native_model_id, priority`, PK
`(alias, provider_id)`) — **no provenance**. So:

1. **"Boot prunes the table to the derived set" is wrong** — it would destroy imported aliases. That
   killed the simplest version of option (b), which is the version I was about to write.
2. **Option (a), persist `auto`, is not obviously right either** — a migration must pick **one**
   default for **two** populations at once. `DEFAULT 1` (derived) prunes every imported row already in
   a user's database; `DEFAULT 0` (manual) reproduces the incident on every existing install. **A row
   that predates the column stays ambiguous either way**, so the column buys a correct future and not
   a correct present.

That is the generalisable part: **a migration cannot disambiguate legacy data it has no basis to
disambiguate — it can only guess, and the guess is wrong for one population.** When the ambiguity is
resolvable from data you already have, resolve it there.

### The fix: classify a loaded row by whether the derivation could have *emitted* it

`ModelCatalog.hydrateAliases(rows)` — a derived row is one `deriveAutoAliases` **emits**, and it emits
only bare rows: `alias === nativeModelId`, on a provider whose catalog carries that native id. So
`derivationEmits(r)` splits the two populations **by definition, not by heuristic** — they are exactly
disjoint on it. Rows inside the set are re-derived; a row outside it cannot have come from a
derivation, so it is kept *and kept as `auto: false`*, which is what leaves its id alone.

Deliberately **not** touched: `deriveAutoAliases`'s `manual.has(native)` guard, and `setAliases`'s
meaning. The documented "manual entries win" rule is preserved exactly, so this is not a semantic bet
on a feature that does not exist. `hydrateAliases` also returns whether the rebuild moved the table,
so `store.ts` writes back only when it did.
