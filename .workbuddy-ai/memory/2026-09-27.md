## Increment 29 — the cooldown wait: a 1-second cooldown no longer fails a request

**Deployed and verified.** Built on the diagnosis recorded at the end of `2026-09-26.md` (see
Correction 5 there): `COOLDOWN_FLOOR_MS` is 1000 ms, `agnes` sends **no `Retry-After`**, so a 429
cools its key for exactly one second — and the empty plan that followed was turned into an instant
hard `NO_ROUTE`. 36 such rows, all with an **empty chain and 0–3 ms latency**, 31 of them on
2026-09-22, the same day as 176 of the 189 `RATE_LIMITED` rows.

### What changed

| File | Change |
|---|---|
| `core/engine.rs` | `key_block(key, now) -> Option<KeyBlock>` is now the **one** spelling of "why is this key unusable". `is_key_usable` = `key_block(..).is_none()`; new `key_retry_at` = `Some(until)` **only** for `KeyBlock::Cooling`. |
| `core/planner.rs` | Extracted `servable_carriers` so `build_plan` and the new `earliest_key_retry_at` cannot disagree about who carries the model. New `earliest_key_retry_at` returns the **minimum** cooldown expiry across servable carriers. |
| `core/router.rs` | New `plan_waiting_out_cooldown`, used by **both** the text and image call sites. `COOLDOWN_WAIT_BUDGET_MS = 5_000`. New `tracing::info!` when the wait fires. |

**`None` is the load-bearing answer in both new readers, and it means "do not wait".** It covers
the three cases waiting cannot fix: no carrier at all; a usable key exists; every blocked key is
blocked by a **denied status or an open breaker**, neither of which clears on a clock. A caller that
slept on those would sleep until its own bound killed the request.

**The loop cannot spin**: `key_retry_at` returns a time *strictly greater* than `now`, so every
iteration sleeps ≥ 1 ms. The `wait_ms <= 0` guard is defensive against a backwards wall-clock step,
which would otherwise make the `as u64` cast sleep for years.

## Increment 30 — the auth breaker gets a half-open state

**Deployed and verified, on both request paths.** The last genuinely-open item from increment 29's
note: an open auth breaker had no half-open state. `breaker_open` was cleared *only* by an
`ErrorClass::Ok`, and an open breaker meant the key was **never tried again** — so no `Ok` could ever
arrive to clear it. The exclusion was a latch, not a circuit: a credential rotated back into service,
or an upstream that had a bad five minutes, stayed dead to the router for the life of the process.
Unreachable so far (`AUTH_FAILED` = 3 ledger rows against a threshold of 3), so this is preventive.

### The measurement the fix rests on

`is_retryable_with_next_key` lists `AuthFailed` (`engine.rs:216-223`, pinned at `:1396`), so a failed
attempt **advances to the next key rather than failing the request**. Admitting a dead key therefore
costs one wasted attempt, not a failed request — which is what makes a re-probe safe rather than
reckless. This was checked *before* writing any code, and it is the whole justification.

### What changed

| File | Change |
|---|---|
| `core/engine.rs` | `KeyHealth.breaker_open: bool` → `breaker_open_at: Option<i64>`. New `BREAKER_HALF_OPEN_MS = 60_000`. `key_block` returns `Breaker` only *inside* the window. `record_result` stamps on **every** failure past the threshold, not only the transition. |
| `packages/router-core/src/health-tracker.ts` | The same change: `breakerOpen` → `breakerOpenAt`, new exported `BREAKER_HALF_OPEN_MS`, new private `breakerBlocks`. |
| `packages/router-core/test/health-tracker.test.ts` | **New file** — the TS tracker had **no test file at all**. 5 cases. |
| `core/planner.rs` | Doc correction + `a_half_open_breaker_contributes_no_wait_at_any_instant`. |

**`Option<i64>` rather than a second field, deliberately.** A `bool` plus a separate `opened_at` is two
fields that must agree, and the pair has a state the flag cannot describe alone: open, with no idea
when. Storing the moment makes that unrepresentable, and it is the moment — not a flag — that
`key_block` reads, so the window cannot be defeated by a missing stamp.

**`key_retry_at` still answers `None` for `Breaker`, and that is the load-bearing decision.** A breaker
now clears on a clock, which makes it *look* like a cooldown — but the clock is minutes and a request's
budget is seconds, so a caller that slept on it would sleep past `FIRST_MSG_TIMEOUT` and fail anyway.
Increment 29's contract survives untouched.

## Increment 31 — `addKey` no longer strands a secret when its row does not land

### The defect

`store.ts:632` `addKey` is a two-store write: `registry.addKey` puts the secret in the vault under
`key:<uuid>`, then `fetchAdmin("POST", "/admin/api-keys", …)` records the row. `sendAdmin` throws on
any non-2xx (`gateway-client.ts:120`) and **nothing undid the vault write**. The secret was then
unreachable: the keys list reads `api_keys`, so it could be neither seen, nor selected, nor revoked
from anywhere in the app.

**The invariant was already written down twice and enforced in three of four places.** Rust
`key_create_h` rolls back and says why (`gateway_admin.rs:359`, *"a secret with no row is an
unrevokable ghost"*); the Rust IPC `key_create_h` does the same (`tauri/gateway_cmds.rs:340`); and
`addProvider` — eleven lines above `addKey` — rolls its own state back with the comment *"so the
registry never holds a ghost provider"*. Only `addKey` did not. **The fourth site was the one holding
a credential.**

### Why it is reachable, not theoretical

`api_keys.provider_id` is a real FK and `PRAGMA foreign_keys = ON` (`store.rs:517`), so a 500 is
available whenever the provider row is absent. `registry.addProvider` is **in-memory only**
(`provider-registry.ts:22`) — it never persists — so "provider in the registry, not in the host" is a
state the app passes through by design. The spec's failing case reproduces it directly.

### The live instance, and its removal

`key:323d5158-950e-4272-81ed-b1c4e5f1c67e` sat in the vault with no `api_keys` row. Shape: 39 chars,
prefix `sk-aip` — `generate_random_key()`'s exact output (`sk-aip-` + 32 hex), i.e. a **gateway**
credential in the provider-key namespace, not a third-party key (the two real provider keys are
`sk-tyh…`/`sk-HS1…` at 51 chars). Proven unused *before* removal: **0 hits across every column of all
30 tables**, 0 repo hits, **0 ledger rows**.

Removed by rewriting `.secrets.json` the way `vault::save` does (tmp → chmod 600 → rename). Verified:
5 → 4 entries, the other four **byte-identical by sha256** to a pre-change backup, mode 600 intact,

### 2. A test binary can write the vault into the user's home

Chasing a 16-byte stray `~/Library/Application Support/ai-provider-router/.secrets.json` holding
`{"k1": "v1"}` — the `SERVICE` default dir, which nothing in the repo reads.

**The mechanism is the finding:** `vault::set_data_dir` is a `OnceLock` (`DATA_DIR.get_or_init`), so
**the first caller wins and every later call is silently ignored.** In a test process the vault's
location therefore depends on whichever test touches it first — and `vault.rs`'s own
`get_returns_none_for_missing_account` does exactly that, calling the real `get()` with a real
account name, pinning every other test in that binary to the user's directory. `vault.rs:234`
already admits the hazard in a comment and works around it *locally*, but nothing stops the next test.

**Fix:** under `#[cfg(test)]`, `default_data_dir()` returns a temp dir — making the class impossible
rather than fixing one call site.

**Verified two-sided:** after a full `cargo test --lib`, the default dir did **not** reappear *and*
`/var/folders/.../T/aip-vault-default-7778` **was** created. The new branch is taken, not merely the
old one absent — the "prove the instrument reports presence" rule.

**Honest limit:** the **writer was not identified.** No code in the repo calls
`vault::put("k1","v1")`; every call site is production or an injected closure. So this is a backstop
for the class, not a reproduction-driven fix, and the original leak was not reproduced. Stray file and
dir removed (backed up to `/tmp`).

## CORRECTION (same day, later) — the paragraph directly above is wrong on both counts

Two claims in *"The recommendation"* above do not survive measurement. Marked here rather than edited
in place, because the log is append-only and the wrong version is itself evidence of the trap.

**Wrong #1 — "a third attempt at 9 s is the plausible tuning."** 9 s is *shorter* than the current
10 s, and the measured in-path `first_msg_ms` distribution shows the 10 s bound is **too short, not
too long**. Real upstream requests only (the mock session writes `first_msg_ms=0` 924 times and must be
excluded), **n = 54**:

```
p50 2106 ms   p75 3622 ms   p90 7126 ms   p95 13396 ms   p99 18626 ms   max 18644 ms
```

**4/54 (7.4%)** exceed 10 s and still succeed on the retry; in the incident session alone it is
**3/24 (12.5%)**. So the 10 s bound is *manufacturing* stalls — aborting a healthy slow request, then
re-sending the identical prompt. Tightening it makes the failure rate worse. **And 0/54 ever needed
more than 20 s**, which is the number the budget should have been built around.

**Wrong #2 — "a second provider is the only change that alters the outcome."** Too strong. A single
attempt allowed ~20 s on chain entry 1 changes the outcome for the whole slow-but-alive class without
any new provider. A second host would help only the residual case where entry 1 is genuinely
blackholed.

**Why the earlier probes misled me — the calibration error.** The 12-probe set (`0.18–2.4 s`, one at
`7.36 s`) measured a **bare upstream call with a tiny body and no tool schema** — `TTFB_socket`. The
request path measures `first_msg_ms`, stamped from *dispatch* (`gateway.rs:1361`), so it also carries
prompt upload, memory prepend and tool schemas. **The two differ by an order of magnitude at the
median (0.27 s vs 2.5 s).** I calibrated the budget against the probe. *Calibrate the instrument, not
just the reading* — this is the same failure mode as the `launchctl list` false zero, one layer up.

### The arithmetic that was never checked: 4 attempts cannot fit in 30 s

| layer | source | worst case |
|---|---|---|
| one attempt | `UPSTREAM_HEADER_TIMEOUT = 10s` (`egress.rs:445`) | 10 s |
| one egress call | `1 + UPSTREAM_STALL_RETRIES` = 2 (`egress.rs:466`, loop `:502`) | 20 s |
| one **plan** | `execute_text` iterates `args.plan` (`engine.rs:964`) | **40 s** |
| the gateway bound | `FIRST_MSG_TIMEOUT = 30s` (`gateway.rs:1311`) | **30 s** |

`the_stall_budget_fits_inside_the_gateway_bound` (`egress.rs:1351`) pins the **second** row. Nothing
pins the third. **40 > 30, so the last candidate is always cut off mid-attempt.**

Proved by a log line that arrives *after* the deadline — request 25 (`03:14:07.496` dispatch):

```
03:14:17.505  WARN egress: connection stalled attempt=1 max_attempts=2   ← entry 1
03:14:27.506  WARN egress: connection stalled attempt=2 max_attempts=2   ← entry 1 exhausted
03:14:37.497  WARN gateway: bridge produced nothing for 30000ms          ← the bound fires
03:14:37.515  WARN egress: connection stalled attempt=1 max_attempts=2   ← entry 2, 18 ms too late
```

`attempt=1` after `attempt=2` = the counter reset = a **second** `egress::stream` call. Ledger row 1652
confirms the chain: `[{"key":"Key-02","provider":"agnes"},{"key":"key-01","provider":"agnes"}]` —
**both entries the same host.**

### The retry is attached to the wrong arm

`egress.rs:584-587`: `Ok(Err(e))` — a transport error — does `return Err(e.into())`, **no retry**. Only
`Err(_)` (the timeout) loops. So a reset socket gets no second chance, while a slow-but-alive upstream
gets one that re-sends the identical prompt to the identical host. Backwards.

**The retry does work when given time** — two measured recoveries: request 4, stall at `02:59:23.718`,
attempt 2 delivered `02:59:26.516` (**2.80 s**); request 16, stall at `03:02:22.547`, delivered
`03:02:31.149` (**8.60 s**). One stall is survivable; the *second* consecutive stall is what exhausts
the inner loop.

**The failure is filed as `CANCELLED`.** Our own 30 s bound → `BridgeMsg::Error{503}` → handler drops
the receiver → cancel flag fires → `router.rs:991`/`:995` write `CANCELLED`. Rows
1652/1655/1656/1658, 30 010–30 025 ms. A timeout recorded under the name of a client abort, which is
why it took a database query plus a log to explain.

**Proposed fix (no second provider):** one wall-clock deadline for the whole plan; per-attempt cap
≈ 20 s (covers 54/54 observed successes); retry moved to the transport-error arm; the second chain
entry spent only on a *fast* failure, never on a timeout; and a distinct class for a first-message
timeout. Skill §5d carries the detail. **Not implemented.**

## Increment 35 — the fourth defect: the pre-first-byte budget (2026-09-27, later)

**The report.** `12:11:28 UTC+8`, `custom-local:agnes-3.0-flash`, *"the router produced no response
within 30000ms — the request was abandoned; retry"*. The operator asked whether WorkBuddy had stopped
waiting for us.

**Answer: no.** That string is **ours** — `core/gateway.rs:1381`. The 30 s was our
`FIRST_MSG_TIMEOUT`, not the client's. (The operator's broader worry — that a client with a tighter
deadline would truncate any recovery we attempt — is a different question and is **not** measured.)

**Row 1671, and the proof rather than the guess.** `error_class = CANCELLED`, `latency_ms = 30005`,
`fallback_chain_json = []`, `http_status = NULL`, `tokens_in/out = 0`, and **no egress line of any
kind** for the request (`04:10:57.919` dispatch → `04:11:27.921` `bridge produced nothing for
30000ms`, nothing between). Only two engine paths give `CANCELLED` with an empty chain, and the
first-iteration cancel check (`engine.rs:1013`) is excluded by timing: `t0` measured at
`04:10:57.922Z` against the dispatch line at `04:10:57.919040Z` — **3 ms**, so the task started
promptly — and the only awaits before `execute_text` are `sync_concurrency` (synchronous) and
`plan_waiting_out_cooldown`, budgeted at 5 s and returning *immediately* on a non-empty plan (an
empty one would have written `NO_ROUTE`). What remains is `break 'plan Ended::Served(candidate)`
(`engine.rs:1158`) with zero chunks and zero attempts → `write_text_ledger`'s `Ok(success)` arm
(`router.rs:986`) → `if cancelled { "CANCELLED" }`.

**Cause.** `egress.rs:577` bounds **each** chunk wait with `UPSTREAM_IDLE_TIMEOUT` (**120 s**), and
that loop starts immediately after headers — so the *first* body byte inherited a budget **4×** the
gateway's. The gateway always won the race, `Slot`'s `Drop` called `bridge.cancel`,
`egress_port`'s watcher (`CANCEL_POLL = 25 ms`) aborted the driver, and the `lines` stream ended
**cleanly** — no error item, so no attempt was ever pushed. The 25 ms poll phase explains `30005`
exactly: polls land at `25k + 30`, the cancel fires at 30000, the watcher notices at 30005.

**This is increment 34's defect one phase later, and increment 34 is what hid it.** Its own comment
claimed *"Only this one is subject to the gateway's first-message bound"* — false. And it silently
**inverted a live test**: `a_stall_after_headers_is_not_retried` drove a no-body-at-all shape and
asserted the message contained `went silent`, i.e. it asserted the *mid-stream* arm for a
*pre-first-byte* case. A green suite, with the wrong phase in both the name and the assertion.

**Fix.** `UPSTREAM_FIRST_BYTE_TIMEOUT = 20 s`, stamped **before** `b.send()` so one deadline encloses
the header wait instead of following it; `UPSTREAM_HEADER_TIMEOUT` stays the header sub-bound so the
two failure modes keep distinct log lines. The loop takes the phase deadline until the first byte and
`idle_timeout` after it. **No new number was invented**: `first_msg_ms` runs from dispatch to the
first *bridge message* — the first content delta — so the n=54 distribution increment 34 measured is
an end-to-end measure of **this** phase, and bounding the phase is what that calibration always
meant. New field `EgressState::first_byte_timeout` so a test can set the three budgets apart.
`a_stall_after_headers_…` **renamed** to `a_stall_before_the_first_byte_is_not_retried` (the rename is
the finding); new `Stall::AfterFirstByte` as the **control**.

**Falsification.** Loop budget reverted to `state.idle_timeout` (one line): the new ordering test
fails with `exactly one error reaches the consumer: []`; the control passes both ways. Two things
learned: `Err(_) if !saw_byte` selects on **phase, not on which budget expired**, so
`a_stall_before_the_first_byte_is_not_retried` passes in both versions too — it pins the
*classification*, the ordering test pins the *budget*.

**A third route to an empty chain, found by accident.** The first run of the new test failed with
`messages: []` because `state()` left `first_byte_timeout` at its 20 s default while the harness's
listener holds only 2 s — the socket closed first and the stream ended `Ok(None)`, which sends **no
error at all**. So an upstream that closes after headers with no body produces the same empty-chain
signature by a different route. Recorded in `state()`'s doc.

**Gates.** `cargo test --lib` **1335 passed / 0 failed**; `cargo fmt -- --check` exit **0**;

**Deployed.** Built `--release --no-default-features` (exit 0). **The marker instrument had to be

## M4 landed — the vault's staleness gate moves from metadata to content (user: "start m4")

**The measurement that reframed it.** M4 says the vault's `(mtime, len)` stamp can miss a same-length
rewrite because "mtime granularity is coarse on some filesystems". Measured on this machine
(macOS/APFS): **0 collisions in 5000** same-length direct rewrites, and **1500/1500 distinct mtimes**
across rapid consecutive writes. So it does not arise spontaneously here. Honest limit: the loop's
minimum inter-write delta was 2.68 ms — that is write latency, not the granularity floor, so the probe
measures the practical rate, not the theoretical floor.

**But it is real where the service runs.** `ci.yml:145` — the `headless-service` matrix is
`os: [macos-latest, windows-latest, ubuntu-latest]`, with the comment "the service has never been
compiled anywhere but this Mac". On Linux, file timestamps come from the coarse clock, so two writes
inside one tick share an `mtime`. The vault belongs to that binary. M4 is real and **platform-scoped**.

**The report's own recommendation has a flaw.** It says "add a cheap content hash to `FileStamp` (the
file is small and is already being `stat`ed)". Being `stat`ed is not being *read* — hashing requires
reading, which is the cost the stamp exists to avoid, so "negligible cost" is wrong for the hot path.
Its `(mtime, len, inode)` alternative is the same metadata class (`ctime` is quantised too). Only its
third option — verify once per N seconds — actually bounds the window. **The fix taken is a fourth
option the report did not consider: compare the file's bytes.** One read where the stamp cost one
`stat`, exact on every filesystem, and it deletes `FileStamp` and its reasoning outright. `serde_json`
still runs only when the bytes differ, so the common path parses nothing.

**The test constructs the collision instead of hoping for one.** `set_modified` puts the second write on
the first write's exact timestamp, so the reproduction is deterministic on any filesystem. Falsified
both ways: **red** against the old stamp (`assertion left == right failed: a same-length rewrite with an
unchanged timestamp must not be missed`), **green** against content comparison. 1342 → 1345 lib tests.

**My first fix was wrong, and the pre-existing tests caught it in one run.** I used
`std::mem::replace` to avoid cloning and then parsed its **return** value — which is the *old* value, so
I parsed the bytes I was discarding. On the first reload `seen` was `None`, so `previous = None` →
`unwrap_or_default()` → an empty map, on every change. Three tests went red in seconds, two of them
written for the original two-process defect and unrelated to M4. Corrected to compare under the lock,
clone the fresh bytes in, and parse them after releasing it.

**A second defect in the same function, closed as a side effect.** The old gate latched the new stamp
*before* reading, so one transient read failure cleared the cache **and** then compared equal forever —
unrecoverable until the file's metadata changed again. The new version distinguishes the two failure
modes: `NotFound` means "no file", so the map is cleared; any other error returns early and changes
nothing, so the next call retries. Both halves are pinned by new tests
(`a_deleted_file_clears_the_cache`, `a_transient_read_failure_leaves_the_cache_alone_and_does_not_latch`),
the latter using `EISDIR` (a directory at the path) because it needs no permissions trick and behaves
the same on macOS and Linux CI.

## The egress stall failures — a harness race, measured, not "flaky" (user: "it's smoothly working")

**The user's evidence, and what it settled.** Tushu reported building a complete portfolio site end to
end through the router with no errors. That is genuine evidence about the **production** path — a retry
that replayed a status would have shown up — but it does not speak to whether the *tests* were sound,
and the gate was red. So it was diagnosed rather than waved through.

**It is not load-sensitivity.** Ten runs of `egress::stall_tests` with `--test-threads=1` (six tests,
nothing else running): **4 failed**. The failing test *rotates* across all three `silent_listener`
tests, and every failure is the same symptom — `connections: 2` where `1` is expected.

**What that symptom can mean, established by reading every arm.** The only `continue` in `stream()`'s
attempt loop is `Ok(Err(e))` at `:797`, gated on `retryable_transport(e) = is_connect || is_request`.
All three stall arms — header timeout (`:802`), pre-first-byte (`:711`), mid-stream silence (`:733`) —
`return Ok(())`. So a second dial **cannot** come from a stall: `send()` itself must have failed.

**The cause.** `silent_listener` wrote the response head **on accept, without reading the request at
all**. That races the client's request write — hyper can see a response before it has finished writing,
classify the dial as a pre-response transport error, and retry. The code under test was behaving
correctly on an input the harness invented.

**Falsified before it was trusted.** Draining the request before answering: **0 failures in 10 runs**,
against 4/10 without. `a_transport_error_before_headers_is_retried_once` — which uses
`closing_listener` and *expects* 2 connections — passes throughout, which is what shows the retry path
itself was never the problem.

**Why this is the right fix rather than a mask.** A real server always reads the request first, so the
old harness shape exercised a sequence the production path cannot produce. The fix makes the fake
server behave like a server; it does not weaken the assertion.

**The lesson, and it is M4's lesson again:** *"the test is flaky"* is a claim, and here it was wrong in
the direction of **under**-diagnosis. A 40% failure rate with no load is not flakiness — it is a race in
the instrument. And "it works in production" was true and still not the question being asked.

## The vault's lost-update race — fixed with a std file lock, no new dependency

`put`/`delete` were `load → mutate the shared map → save`, and `save` writes the **whole map**, with
nothing excluding a second process. Measured, not inferred: the new
`two_processes_writing_different_accounts_lose_nothing` drives **two real processes** through a start
barrier and found it fails **both ways at once** — **26 of 50** `put`s returned `No such file or
directory` (both processes wrote the same `.secrets.json.tmp`, so one `rename`d it out from under the
other) and **25 of 50** accounts were gone from the file, with both calls returning `Ok`. The loud half
is what the first run hit, which is why the child now *reports* instead of asserting.

**The dependency question dissolved on measurement.** `fs4`'s docs say its exclusive lock "mirrors
`std::fs::File::lock`" — and std stabilised file locking in **1.89**; this toolchain is **1.98.1**. So
the fix is `std::fs::File::lock()`, zero new crates. The API is `lock()`/`try_lock()`/`unlock()`, **not**
`lock_exclusive()`/`try_lock_exclusive()` — I would have written a compile error from the trait name
alone.

Measured semantics, each with its own probe: excludes across **processes** (WouldBlock while held, Ok
after release); excludes **two fds in one process** (so threads serialise too); **blocks** rather than
failing (a second process's `lock()` returned after 3.0026 s against a 3 s holder); released on drop.

**The trap worth keeping: my own probe lied, and the reason was a `remove_file`.** A child leg that
unlinked the lock file and re-created it locked a **different inode**, so it excluded nobody — and the
probe reported "not excluded" until the unlink was moved below the child branch. *A lock file that can
vanish is not a lock*, and that is now a load-bearing property of the implementation: the lock file is
never unlinked, and `save` renames only `.secrets.json.tmp`.

Also needed, and not redundant: one in-process `Mutex` around each public op, because a concurrent `get`
calls `load`, whose `*map = fresh` is a *replace*, and would otherwise erase a `put`'s un-saved mutation.
Falsified both ways on identical test code — lock stubbed out **3/3 red**, lock in place **5/5 green**.

**Two of my own mistakes, both caught by the harnesses I built for exactly that.** `--exact` needs the
**full path**, so my first manual run matched **0 tests and exited 0** — the same "a filter matching
nothing exits 0" hole the test's marker file exists to close. And `libtest` writes an assertion failure
to **stdout**, not stderr, so a child whose stderr I captured reported only a bare exit code.
