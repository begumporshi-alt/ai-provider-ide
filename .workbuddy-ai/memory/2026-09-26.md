## Increment 26aa — Start's handover gets an undo, and the EIO that is not a defect (14:55)

**Naming note:** this first went in as "26z", which was already taken by the earlier
`launchd_live` label-collision entry above. Increment labels live in **two** places — this log and
`docs/dev-book/` — and the check for a free one has to cover both.

**Found by the operator in the first minute of real use.** Clicking **Start** with the app gateway
running turned the gateway off and *then* failed:

```
launchctl bootstrap gui/501 /Users/…/dev.aiprovider.router.plist failed (5): Bootstrap failed: 5: Input/output error
```

leaving the app gateway **off and** no service — nothing serving, worse than either state Start was
pressed from.

**The real defect (D63).** 26y's handover is destructive-first by necessity — the service cannot bind
while the app holds the port — but it shipped with **no undo**. `serviceAction` now takes
`{ run, undo }` and runs the undo when the action throws *after* `run` succeeded. Start undoes with
`gateway_enable` (runtime-only, symmetric with `gateway_disable`) and **not** `toggle(true)`, which
would persist an `enabled: true` the handover never changed. A failed undo is reported *alongside*
the original error rather than replacing it.

**Why the suite missed it:** the spec asserted `["gateway_disable", "service_start"]` — an assertion
that **stops at the failure**, so it could not see what followed. The class is D55's one level out:
D55 was a fixture asserting a non-load-bearing invariant; here the *assertion itself* ended exactly
where the defect began. New test asserts the full three-call log, and was **falsified** by neutering
the undo (which reddens it).

**The EIO is not a defect — three measurements, in this order:**
1. A **trivial** plist (`/usr/bin/true`, `plutil -lint: OK`, sharing nothing with the app) bootstrapped
   into the same `gui/501` fails **identically** → rules out the app's plist, its binary and its code
   in one step.
2. The project's own `launchd_live` harness, run from this shell, prints
   `SKIP: no Aqua session in this process` with the identical EIO — and the same two tests **pass**
   from Terminal.app (the 12:50 run).
3. So the domain refuses *every* bootstrap from a process outside a real GUI session. The app under
   test had been started by me from an agent shell (`pnpm dev`), so it inherited exactly that.
   **Operator's fix: launch the app normally.** Nothing to repair in `service.rs`.

**Reusable diagnostic order:** reproduce with a control that shares nothing with the suspect, then
hand the question to an instrument that already distinguishes the two cases — rather than reasoning
about which cause is likelier.

**Also:** `pnpm dev` needs `PATH="$HOME/.cargo/bin:$PATH"`; without it `cargo metadata` fails with
"No such file or directory" and tauri exits immediately.

**Measured:** full browser suite **114 passed / 0 failed** (113 + the new rollback test). The earlier
112/1 was `ui.spec.ts:87` dying in `browserContext.close` on the sandbox file broker — it passes in

## Increment 26ab — the handover revoked the UI's credential, and nothing minted it back (15:20)

**Live symptom:** after a successful Start, every admin call from the app answered
`401 {"code":"invalid_api_key","message":"invalid gateway key"}` — e.g. `POST /admin/api-keys`.

**Diagnosis, each step measured rather than inferred:**
1. `lsof` on the port → the listener was **`aiproviderd`** (the agent), not the app. So Start had
   actually **worked** — launched from the operator's own session, exactly as 26aa concluded it must
   be. The 401 was the app's *own* admin calls being rejected by the agent.
2. The secrets file held `masterkey` and two `key:` entries but **no `key:ak-ui`**.
3. `gateway_keys` held **only** `ak-fc85350a2fb1dc67` ("Work buddy") — no `ak-ui` row.
4. `gateway_disable` calls `ui_session::revoke` (`gateway_cmds.rs:296`), and the handover calls
   `gateway_disable`.

**Mechanism.** `uiSessionKey()` caches the credential in a module-level `let` and returns it for the
life of the webview. `clearUiSession()` — whose own comment reads *"Called on gateway stop so the
next start mints a fresh one"* — had **zero call sites** (Grep returns its definition and the test
fake, nothing else). So the credential was revoked host-side, correctly and by design (D51), while
the client went on presenting it. The revoke was never wrong; the re-mint was never wired.

**Why 26y is what exposed it.** `gateway_disable` was previously reachable only by the operator
deliberately switching the Gateway off — rare, and followed by a switch back on that also reads as a
fresh start. 26y made it the **first half of one button press**, so the ordinary act of bringing the
service up began silently invalidating the UI's own credential. D64, and it is **D63's mirror
image**: D63 was a compensating step with no compensation; D64 is a teardown step whose paired setup
was never wired.

**Fix.** `fetchAdmin` retries **once** on a 401 after dropping the cached credential, re-minting
against whichever process now holds the port — the point of `ak-ui` being an ordinary app key. Not a
loop: a second 401 is a real refusal, and re-minting against it would dress a refusal up as a retry.
A non-401 failure is not retried. The tests assert the retry's `Authorization` header **differs**
from the first attempt's — a retry that re-sent the same stale key would satisfy a call count while
fixing nothing — and were **falsified** by disabling the retry, which reddens exactly the two retry
tests.

**Instrument note (again).** `grep 'a\|b'` in bash returned a **false zero** while searching for
`clearUiSession`; BRE `\|` alternation matches nothing. The Grep tool found it at once. The working
memory already records this trap, and it still cost a step — the lesson is that the *first* search
for an absence claim must be the instrument that is known to report presence.

**Measured:** vitest **185** (181 + 4). Rust 1304, browser 114 unchanged.

## Increment 26ac — the 429 the retry didn't cover, and the boot screen's destructive advice (15:30)

**Live symptoms (three, in sequence).** After 26ab's 401 fix: `POST /admin/api-keys` → 401 (resolved
by 26ab). Then on next boot: `GET /admin/api-keys` → **429 too many failed auth attempts — backing
off**, and the boot screen displayed its unconditional *"restore from the newest dated backup"* line
for a transient rate limit.

**Diagnosis.** The 429 is a **consequence of the 401 storm**, not an independent fault. The
brute-force backoff is checked *after* the key match (`core/gateway.rs:1487`), so a valid credential
never reaches it — pinned by `r4_valid_key_not_throttled_by_another_callers_failures`. A 429
therefore means the credential was *still* bad. 26ab's retry covered 401 but **not** 429, so the
first poll after the re-mint presented the new key, the server matched it and cleared the window —
but only if the retry was triggered by the *first* 429. Without 429 in the retry condition, the app
locked itself out for the backoff duration (caps at 32 s).

**Fix.** Two parts:
1. `gateway-client.ts:116`: retry condition extended from `res.status === 401` to
   `(res.status === 401 || res.status === 429)`.
2. `boot-failure.ts` (new): `bootFailureHint(error)` chooses advice from the error string —
   429 → "reload, the backoff clears by itself"; 401 → "reload mints a fresh credential";
   5xx → "check the log"; no listener → "the gateway did not answer"; unknown → backup advice,
   now **hedged** rather than asserted. Wired into `App.tsx:77`.

**Tests.** Two new in `gateway-client.test.ts` (429 retry + second-429 no-retry), five in
`boot-failure.test.ts` (one per branch + hedged fallback). 429 branch **falsified**: disabling it
reddened both 429 tests, 401 and 500 tests stayed green.

`09-status.md` Tests row updated (464 → 471 TS unit; desktop 185 → 192).

## Increment 26ad — the launchd error now says what it means (16:00)

Pays the debt 26aa filed: *"the card surfaces `Bootstrap failed: 5: Input/output error` verbatim."*

**Two measurements changed the shape of the fix.**
1. **"Map status 5" is the wrong key.** launchctl *exits* 5, and launchd separately embeds **its own**
   status code inside the message (`Bootstrap failed: **5**: …`). The same number appears twice meaning
   two different things → key on the **pair** (exit status **and** message text), not the number.
2. **The verbatim problem was never confined to `bootstrap`.** Live `launchctl bootout gui/501/<label>`
   of a job launchd doesn't hold → exit **3** `No such process`, not 5. A mapping keyed on 5 alone would
   have left `stop`'s most common failure just as opaque.

**A fixture was pinning a shape launchctl cannot produce.** `a_stop_launchd_refuses_…` used
`(5, "Bootout failed: 5: Input/output error")` — copied from the `bootstrap` fixture above it. Green
against a shape the tool cannot emit; it could not have caught *any* real `bootout` failure. D61's
instrument class in a new place: not "an instrument that cannot report presence" but "a fixture
asserting a property of a fabricated input".

**Design.** One `describe_failure(what, out)` at all three sites (`service.rs:351/419/444`). Note is
**appended, never substituted** (a wrong cause is discountable; a dropped raw message is not) and
**hedged** — "Most common cause: this process has no GUI session (Aqua)" — because the cause was
established by *excluding* alternatives (trivial plist failed identically; `launchd_live` printed
`SKIP: no Aqua session`), not by observing a success under it.

**Falsification, both directions.** Disabling the note reddened the 3 positive assertions and left the
2 negative ones **green** — which is exactly why the negative tests needed their own probe: **an absence
assertion passes trivially when the thing is absent for the wrong reason.** Making the note unconditional
reddened both. **My first attempt at that probe was worthless**: it returned `"PROBE"`, which does not
contain the substrings the negative tests assert on, so it could not have failed them. Lesson:
**a probe must be built to fail the assertion it targets**, not merely to differ from the correct code.

## Increment 26ae — the app could not authenticate to its own service (17:50)

**Context.** Full write-up in `10-headless-service.md` and D67; committed and pushed this session.
The app's admin calls answered `401 invalid gateway key` against the service it had just started, and
the 401 storm behind that is what turned the next boot into the `429` that 26ac had only made
*legible*.

**Two per-process caches, one layer apart.**
1. `vault::load` was `static LOADED: Once` — *"Runs once per process."* 26y moved the listener into a
   second process, so the app minted `gwkey:ak-ui` into a file `aiproviderd` had already snapshotted;
   the service was asked to honour a credential it did not hold. It failed in the **worse** direction
   too: a *revoked* credential kept authenticating in any process that had loaded it, so
   `ui_session::revoke` did not do what its comment promises.
2. `AppKeyCache` keyed on the active **id set**, but `ak-ui` is re-minted *under the same id*
   (`ui_session` deletes the row, inserts a fresh one), so a rotation left the fingerprint identical
   and the memo served the pre-rotation secret for its full 60 s TTL.

**Fix.** `load` re-reads on the file's `(mtime, len)` stamp, replacing rather than merging (`save`
writes the whole map; a merge would resurrect an account another process deleted). The memo keys on
