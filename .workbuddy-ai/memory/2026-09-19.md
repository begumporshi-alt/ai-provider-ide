## Closed: the zero-cost bug (it was three defects, not one)

Yesterday's note ended with tokens still recording 0 "STILL UNEXPLAINED". Resolved. Three
independent defects sat on the same path, which is why each fix looked like it hadn't worked:

1. Nothing asked the provider for usage on a stream (`stream_options` never sent). Fixed in
   `29ba465` via `stream.requestUsage` + a dialect default for manifests stored before the flag.
2. `execution-engine` swallowed the caller's `onUsage`, so the gateway bridge never learned the
   counts even when the engine had them.
3. **The real cause:** the interpreter `return`ed as soon as it saw `finish_reason`, but
   OpenRouter delivers usage on a *later* chunk. Measured order:
   `content -> finish_reason=stop, usage=null -> usage={...}, choices=[] -> [DONE]`.
   Fixed by `continue`-ing past finish_reason when usage was requested.

`1c149e0` covers 2 and 3. Runtime proof: `tokens_in 311 / tokens_out 3` where every row had
been 0/0.

## Bare `openai/gpt-4o-mini` did not route — real bug, now fixed

Tushu added a WorkBuddy custom model with `{"id":"openai/gpt-4o-mini"}`. It 404'd:
`no route for model "openai/gpt-4o-mini" (no enabled provider carries it)` — even though the
model WAS in the cached catalog. `openrouter/openai/gpt-4o-mini` worked fine.

Cause: `resolveWanted` read everything before the first `/` as a provider slug. No provider named
`openai`, so it pushed no candidate — and the bare-native-id branch was gated on
`!model.includes("/")`, so it never ran either. OpenRouter's native ids contain a slash, which
makes a bare native id indistinguishable from a qualified one on the wire.

Fix (`ef98827`): track whether the id actually qualified. Read the slash as a qualifier only when
it names a real provider; otherwise fall through to the bare-id lookup. A genuinely qualified id
still short-circuits, so nothing can be silently rerouted to another provider. 3 tests, incl. a
guard that a qualified id is not rerouted even when a model literally named
`openrouter/openai/gpt-4o-mini` exists in the catalog.

Verified on the rebuilt app: `openai/gpt-4o-mini`, `custom-local:openai/gpt-4o-mini` and
`openrouter/openai/gpt-4o-mini` all return 200 with usage.

## That follow-up is now built (`5934511`)

Model Browser rows carry Expose/Unexpose, backed by `workbuddy_status` / `workbuddy_set_models`,
which persist and rewrite the client file immediately instead of waiting for the next launch.

**The subtle bug I had to design around:** "never configured" (`None`) and "explicitly empty"
(`Some(vec![])`) must be different. Without that distinction, unpublishing everything gets
re-seeded from the client file on the next launch and the entry silently comes back. Related: sync
had an early return on an empty list, which meant unpublish would *skip* and leave our entries in
the client's picker. Empty now runs the merge so it removes.

Verified across three real restarts: 2 published (deepseek got `maxInputTokens 163840` — its real
context window, not the 128000 fallback, which proves the values are catalog-derived) -> 0
published with the other 6 entries untouched -> 1 published; then 4/4 chat 200.

**One transient to be aware of:** a 401 appeared on the first request after a rapid
pkill/relaunch cycle. Re-reading the key gave 200, and 4/4 passed after. Don't read a single 401
right after a restart as a key problem — retry before investigating.

## A null-usage scare that was NOT a usage bug

deepseek came back with `usage: null` and 0 tokens on one request. Looked like the same class of
bug again. It was not:

- Direct upstream check (non-stream AND stream): deepseek reports usage exactly like gpt-4o-mini
  does — finish_reason on chunk N, usage on chunk N+1. Identical shape.
- The failing ledger row was `status=error, error_class=NO_ROUTE` — **no request was ever sent**,
  so of course there was no usage. Rapid-fire requests had tripped OpenRouter's rate limit, the
  key went to cooldown, and the planner had no candidate.
- Re-ran: deepseek 892/2 and gpt-4o-mini 316/2, both with usage, both with correct cost.

Lesson: `error_class` in the ledger is what distinguishes "usage was dropped" from "nothing ran".
Check it before assuming the capture path broke again. Also: `usage: null` on a *successful*
response and `usage: null` on an error response look identical from curl — read the ledger row.

## Verification techniques that paid off (and one that cost time)

- **Decisive technique: query the live feed, then replay it in a unit test.** Fetching
  OpenRouter's real `/models` and running `selectAll` + `parsePricing` over it proved the
  capture path was sound in one shot, which narrowed the search to persistence immediately.
- **A schema column that appears only in the schema and in tests is a smell.** Grepping for
  `pricing_json` and finding no INSERT/SELECT was the whole answer.
- **Cost me time:** the sandbox `grep` shim silently returns nothing for alternation (`a|b`).
  It looks like "no matches" rather than "unsupported". Use the Grep tool for anything with `|`.
- **Making a cache row stale is the way to exercise the boot self-heal.** `refreshStaleCatalogs`
  only fires on rows that are missing or past the 24h TTL, so a cache written by a pre-fix build
  stays priceless until the TTL expires. Setting `fetched_at = 0` triggers a legitimate re-list
  through the product's own path — no speculative code needed. (DB backed up first.)
